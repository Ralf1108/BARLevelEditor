# Specification: Level Editor

Status: 2026-10-28 (LAN Play: version number and checks, maps from the host; before that 2026-10-27: review: one versioned extra game for the scenarios, the LAN lobby without editor updates, the gadgets led_gadgets.lua and unit_indestructible.lua, the Tower Defense page led_td.lua, the clean-up of key 8). This document describes the current state; how things were checked is at the end.

Level editor for Beyond All Reason (BAR): place units and buildings on the map with the mouse, create and place blueprints (layouts), save and load levels, build Tower Defense, Capture the Flag or Reclaim the Fame levels, forbid units for the player. The result is a `unitloadout` list for scenarios.
Shared code: `..\shared\editor_common.lua` (see `..\shared\SPECIFICATION.md`). Sister project: `..\BluePrinter\SPECIFICATION.md`.

## 1. Goals and basic rules
- **Language of the interface:** all visible texts in the game are English (widget, gadget messages, tooltips, help board, help topics, chat messages), because the project is meant to be international. Console menus, scripts, comments and these documents are English as well. Game texts stay without umlauts. File and folder names are English as well (`scenario`, `scenarios`, `template`, `Start Scenario.bat`, `_trash`).
- The official game stays unchanged. The editor is an **extra game** (`data\games\LevelEditorMod.sdz`, name "Level Editor") that builds on the official BAR, plus a start file and folders for levels and blueprints.
- In editor mode (game option `leveleditor=1`) **no /cheat and no /globallos** are needed (the editor switches on the cheat mode and the god mode itself, see 3.1). Everything is free and finished instantly. Legion, the extra pack and release candidates are switched on. The unit limit is raised (`maxunits=32000`).
- Source code and texts contain no reference to persons or private matters. Player name in the start script: "Player".
- Structure: **widget** `lvl_level_editor.lua` (controls, menu, saving/loading), **gadget** `unit_level_editor.lua` (places, deletes, blows up, build mode, orders for units of other teams), shared code `editor_common.lua` and `bar_rules.lua`; the pages and games: `td_waves.lua` and `led_td.lua` (11a), `ctf_game.lua` and `led_ctf.lua` (11b), `unit_restrictions.lua` and `led_restrictions.lua` (11c), `rtf_game.lua` and `led_rtf.lua` (11d), `unit_indestructible.lua` (the buildings marked with FX), `led_gadgets.lua` (what the gadgets share). There is **no backward compatibility**: old fields in level files are dropped when loading (`knownFields`, section 10), old names and formats are not read.
- After every change to the widget, gadget or shared code, or a BAR update, the extra game has to be built again. `start_level_editor.bat` does it: before every start it calls `ensure_installed.ps1`, which compares the stamp `data\games\LevelEditorMod.stamp` (SHA-256 over the game version and every source file of the setup: the packed files, the setup scripts and the LAN Play files, `Get-EditorStamp` in `editor_manifest.ps1`, written by `install_editor.ps1` after building) with the current files and runs `install_editor.ps1 -Quick` (builds only the extra games and the stamp and brings LAN Play up to date; does not rewrite the start file, because the batch file is running) when the stamp or the extra game is missing or differs. While a game is running (`spring` process) the update is skipped with a note. `install_editor.bat` still does the whole setup (start file, shortcut).

## 2. Installation and start

### 2.1 Setup (`install_editor.bat` → `scripts\install_editor.ps1`; all scripts live in `scripts\`, `$root` = the main folder is their parent, the repository folder their grandparent)
- Searches BAR on all fixed drives (e.g. `C:\Games`, `D:\Games`, Program Files, `%LOCALAPPDATA%\Programs`), finds the engine and game version, builds `LevelEditorMod.sdz` with `modinfo.lua` (name "Level Editor", short "LevelEd", game "LevelEditorMod", depends on the installed BAR), the gadgets (`unit_level_editor`, `td_waves`, `ctf_game`, `rtf_game`, `unit_restrictions`, `unit_indestructible`, the lootbox stub), the widget (with `enabled = true`) and in `luaui/Include`: `editor_common.lua`, `bar_rules.lua`, `led_gadgets.lua`, `led_td.lua`, `led_ctf.lua`, `led_rtf.lua`, `led_restrictions.lua`, `led_help_texts.lua`. **One list of the files** (`editor_manifest.ps1`): `$EditorGameFiles` (folder key, file, path in `LevelEditorMod.sdz`) plus the gadgets of `$ScenarioGameFiles` (`shared\bar_common.ps1`, the files of the extra game of the scenarios: the setup, the starter, the scenario builder, the bundle of the lobby and the LAN test take them from there), `$StampExtraFiles` for the stamp; `Get-EditorGameEntries`, `Get-EditorSourceFiles`, `Get-EditorStamp` read them. A missing file stops the setup with its path. After building it writes the stamp `data\games\LevelEditorMod.stamp`; with `-Quick` (called by `ensure_installed.ps1`) it stops there and does not rewrite the start file or the shortcut.
- The widget is switched on in the extra game by replacing only the first `enabled = false,` of `lvl_level_editor.lua` (the line in `GetInfo`); the same text also appears in the code as data (default of the tower defense settings), which must stay untouched.
- Replaces the extra game of a previous setup, creates junctions: `data\LevelEditor` → `levels`, `data\LevelEditorBlueprints` → `blueprints`, creates `blueprints\_trash` (trash), writes `start_level_editor.bat` and the desktop shortcut "BAR Level Editor" (no other shortcut; the BAR launcher creates its own). It does not check for or download any map; the maps are chosen in the start menu.
- **LAN Play (2026-10-24):** the setup also builds the extra game of the scenarios **"Level Editor Scenarios <version>"** (`data\games\LevelEditorScenarios_<version>.sdz`, `Write-ScenarioGame` in `shared\bar_common.ps1`: `modinfo.lua` with `depend = { "<installed game>" }`, the gadgets `td_waves.lua`, `ctf_game.lua`, `rtf_game.lua`, `unit_restrictions.lua`, `unit_indestructible.lua`, the lootbox stub as `pve_supply_drops.lua` and `luaui/Include/bar_rules.lua`; the version = the first 8 hex digits of a SHA-256 over the BAR version and the texts of these files, the zip entries have the fixed time 2000-01-01; an existing file of that version is not built again) (the gadgets switch on only by the game options of a scenario; the quick setup builds it together with `LevelEditorMod.sdz`, the same stamp) and writes its name into `data\games\LevelEditorScenarios.txt` (file name, game name; read by LAN Play). Different files give a different version and a file of its own, so a version received from a LAN host or built by an older package never replaces another one; other versions stay until key 8 of the start menu removes them. The files of the older fixed names (`LevelEditorScenarios.sdz`, `TowerDefenseScenario.sdz`) are removed by the setup. It makes the junction `data\LevelEditorScenarios` -> `scenario\scenarios` and runs `lan_lobby\install_lan_play.ps1` (see 14.2; a failure there only prints a warning). `uninstall_editor.ps1` removes the editor's own version of it, the pointer file, the junction and the widget.
- Requirements on the computer: BAR installed and the launcher started once. The folder `shared` must lie next to `LevelEditor`.
- **Removing (`uninstall_editor.bat` → `uninstall_editor.ps1`):** finds BAR like the setup, refuses while the game runs, lists what is there (`data\games\LevelEditorMod.sdz`, its stamp, `LevelEditorScenarios.sdz`, the junctions `data\LevelEditor`, `data\LevelEditorBlueprints` and `data\LevelEditorScenarios`, the LAN Play widget `LuaMenu\Widgets\lan_lobby.lua`, the game widgets `LuaUI\Widgets\shared_start.lua` and `scenario_briefing.lua` (copies of older versions), desktop shortcut "BAR Level Editor", `start_level_editor.bat`, `editor_script_installed.txt`, `Last Map.txt`, `Online Maps Cache.json` and `Scav Units.txt` in `%LOCALAPPDATA%\BAR-Level-Editor`), asks (`-Yes` skips) and removes it. Junctions are only unhooked with `rmdir` (the content of `levels` and `blueprints` stays); if one of the places is a real folder it is skipped. `-WithSettings` additionally deletes `LuaUI\Config\LevelEditorRecent.lua` and `LevelEditorUI.lua`. At the end `install_lan_play.ps1 -Uninstall` switches `loadLocalWidgets` of the lobby off again. The desktop shortcut "Beyond All Reason", the folder itself and the cache `%LOCALAPPDATA%\BAR-Scenario` (scenarios and maps from other players; key 8 of the start menu) stay.

### 2.2 Start menu (`scripts\choose_map.ps1`)
At the start always a menu in the console. Controls: arrow up/down (Home/End) choose the item, Enter runs it, a digit key jumps straight to it, Esc cancels; grayed-out items are skipped, the first possible one is preselected (normally 0). Checked with real key presses in a console:
- **Key 0** (most common action): continue the last saved map (the state `_last`, saved every 2 minutes and when leaving).
- **Map preview:** the lists of keys 1, 2 and 3 show the picture of the highlighted map on the right (window wide enough: the list keeps 55 characters, the picture gets at most 64 columns). The pictures are not downloaded: the lobby package of the game (`byar-chobby`) contains `LuaMenu/configs/gameConfig/byar/minimapThumbnail/<map name with _>.png` for about 770 maps. `map_preview.ps1` reads the newest `data\packages\*.sdp` that lists them (gzip; per file name length, lower case name, 16 bytes md5, crc, size), takes the file `data\pool\<md5 byte 1>\<rest>.gz`, unpacks it into memory and draws it with the half block character (two pixels per character, 24-bit colour; the console mode for escape sequences is switched on; 16 colours as fallback). Nothing is stored on disk: the index (name to md5) is built at the start (about 0.2 s), a picture is unpacked when its map is highlighted and kept in memory for the next visit. Under the picture a line with size, players and terrain is shown (data of the filters below). Without package, thumbnail or enough width nothing ("no preview") is shown and the menu works as before. Test: `choose_map.ps1 -Data <BAR\data> -TestPreview "Map name"`.
- **Map filters (key 1):** a row above the search line with three filters `Size`, `Players` and `Terrain` (all `all` at the start). `Tab` / `Shift+Tab` choose a filter (highlighted), `Left` / `Right` change its value, typing still searches, the counter counts the maps that pass all filters and the search. Values: size `XS` to `XXXL` (the classes of the lobby: area = `Width` x `Height` against the quantiles 0.08, 0.24, 0.40, 0.60, 0.78, 0.92 of all maps), players `2`, `3-4`, `5-6`, `7-8`, `9-12`, `13-15`, `16`, `17+`, terrain `Flat`, `Hills`, `Water` and the specials `Metal`, `Lava`, `Air`, `Asymmetrical` (a map has the special of its entry plus Flat, Hills and Water as flags). The data are in `configs/gameConfig/byar/mapDetails.lua` of the same lobby package (`Get-MapDetail` in `map_preview.ps1`, parsed once, about 50 ms); a map that is not in the file is hidden as soon as a filter is set. Under the picture a line shows e.g. `12 x 12 (S), 4 players, Air, Hills`. The other fields of the file (author, description, start boxes, certification) are not used. The levels lists have no filters.
- **Key 1:** new level – map selection with search while typing. The list contains **all BAR maps from the internet** (cached in `Online Maps Cache.json`, see section 12: with a cache the menu starts at once from it and a hidden background process fetches the new list for the next start, writing the cache through a temporary file; only without a cache the list is fetched at the start, 10 s at most), missing maps are only downloaded **after** the selection, offline only installed maps appear. The list shows only the name with its version (no file name, no note about missing maps; the title counts the maps and the installed ones).
- **Key 2:** load an existing level (list from `levels`, with search). Every line shows name, map, number of units and features ("195 units, 94 features"; `Read-Level` counts the entries before and after `featureloadout` separately), date and a note if the map is missing. The same format is shown for the last state in the main menu. A single level is treated as a list (`@(Get-Levels)`, `@($items)`), otherwise PowerShell counted the property `Count` of the level object. The editor starts on the saved map and sets up the units automatically (`levels\_autoload.txt`).
- **Key 3:** create a scenario package (ZIP) from a level (only if levels exist): level selection as with key 2, then `scenario\scenario_builder.ps1 -Level name -Auto -AskName` runs (at the end of the questions, so after the values: a list "Scenario info stored in the level" (title, author, summary, briefing, roles, tech, AI, win condition, resources, grace period, ID, Tower Defense), then the title is asked with `AskLine`, Enter keeps it; a changed title proposes the ID `Get-Slug <title>`, otherwise the saved ID stays; then `Confirm-ScenarioId`: shows the target `scenarios\<id>`, Enter takes the name or another one is typed (`Get-Slug`, written into the level block as `sid`), if the folder or zip exists: y = overwrite, n = another name, c = cancel) (PowerShell, no Python needed; see 14) without further questions, the info comes from the level (edited in the editor with button I, defaults apply if it is missing); then back to the menu. The info is changed in the editor.
- **Key 4:** start a built scenario (only if `scenario\scenarios` holds folders with a `scenario.txt`): list of the scenarios with ID, title (first line of the `README.txt`), map, a note "Tower Defense" if the folder has `td_waves.lua`, and date (`Get-Scenarios`, `-TestScenarios` lists them), search while typing; Enter opens a second list (Single player / Host a game for others in the same network / Join a game hosted by another player / Split screen; Esc goes back to the scenarios) and then runs the **current** `scenario\template\start_scenario.ps1 -BarPath <BAR folder> -ScenarioDir <folder of the scenario> -EditorDir <LevelEditor folder>` (not the copy in the package, see section 14), with `-HostGame -Lobby` for Host, `-Join -Lobby` for Join (the same as `Host Game.bat` / `Join Game.bat`) and with the games of the split screen started from the menu itself (section 14.1) (finds the engine and game, builds the extra game of a Tower Defense scenario, downloads a missing map after a question, starts the game); when the game ends the menu comes back (the next scenario can be tried at once; the other keys still end the menu with exit code 0 to start the editor).
- **Key 5:** upgrade a built scenario package (only if there are built scenarios): the same list of scenarios as key 4; Enter finds the level the scenario came from (`Find-ScenarioLevel`: the level whose saved scenario info has `"sid"` = the ID of the scenario, otherwise the level whose name gives that ID: lowercase letters and digits) and runs `scenario\scenario_builder.ps1 -Level <level> -Auto` (the saved info, no questions, the folder and the ZIP of that ID are replaced), then "Continue with any key" and back to the menu; without a matching level a message says to build it again with key 3. Checked on a copy of the folders (no real package touched): `level002` -> `level_002`, `level8` -> `Level8`, the rebuilt package has the current starter, lobby, stub and gadgets.
- **Key 6:** play a level at once (see 14.1).
- **Key 7** (after an empty line): switch the **Scavenger and Raptor units** of the Place menu on or off (`Scav Units.txt` in `%LOCALAPPDATA%\BAR-Level-Editor`, off at the start). Those units exist in the game only with the game option `forceallunits` (the `_scav` copies of all units are made by BAR's `unitdefs_post.lua` only when a Scavenger AI, `ruins`, `zombies` or `forceallunits` is on; the raptors load with `forceallunits`), and the option makes the game start about 10 s slower (measured: 24 s without, 34 s with). The entry says so. `Write-StartScript` adds `forceallunits=1` to the game options when the switch is on **or** the level to load holds such units (`Read-Level` finds `forceallunits` in the `requiredmodoptions` of the level file). Scenarios and tests need nothing from the switch: a level that holds such a unit carries `forceallunits = "1"` in its `requiredmodoptions` (written by `saveLevel`), the scenario builder copies it into the game options of the scenario.
- **Key 8:** clean up (`Invoke-CleanMenu`, `Get-CleanItems`, `Remove-CleanItem` in `choose_map.ps1`). A list with kind, name, size and date: own levels (`levels\*.lua` without the internal `_` files) and own built scenarios (`scenario\scenarios\<id>` with its zip), scenarios and maps from other players in the cache `%LOCALAPPDATA%\BAR-Scenario` (`Cache\<hash>`, `Cache\Maps\maps` with the `.mapinfo`), and versions of the extra game `LevelEditorScenarios_<version>.sdz` in `data\games` that are not the editor's own (the one in `LevelEditorScenarios.txt`). Up/Down, Page up/down move, Space marks, A marks or unmarks all of the kind under the cursor, Enter removes the marked ones (or the one under the cursor) after y, Esc goes back. Own levels and scenarios are moved into a `_trash` folder next to them (with the time in front of the name when it is taken; never deleted for good), the rest is deleted (fetched again when needed). The maps of BAR itself (`data\maps`), the game, the editor and the backups are never offered. The entry of the menu shows the size of the cache. Old things go by themselves when the menu starts (scenarios after 30 days, maps after 60 days or beyond 3 GB). Checked: the list of the real folders, a level moved into `levels\_trash`.
- The map list must stay smooth: the filtered list is cached, only changed lines are redrawn, a backlog of key presses is discarded, resizing the window is handled (no slowdown, not even at the end of the list).
- Writes `editor_script_installed.txt` (start script for the engine, player "Player", game "Level Editor 1", game options including `maxunits=32000`, and `forceallunits=1` when key 7 is on or the level needs it).
- `start_level_editor.bat` prints its three steps (`[1/3] Checking the installation`, `[2/3] Checking the links`, `[3/3] Loading the map list and the levels`), so a slow start shows where it waits. Measured on 2026-10-27: the three steps need about 1.5 s together, the game start 24 s.

### 2.3 At the start of the game
- Shortly after the start (frame 6) `widget:Update` sends `cheat 1` and `godmode 3` once, so units of every team can be selected and commanded (3.1).
- At the start only the commander stands there. All mobile **builders of every faction** are created by the user when needed with Ctrl+D at the mouse pointer, grouped by kind, on **reachable spots** (check by grid and `TestMoveOrder`; no water, no cut-off mountains). Do not use: `Spring.RequestPath` (leads to a crash).
- The start script has **ten teams** (0 to 9), each in its own ally team; only teams 0 and 1 keep their start commander (the gadget removes the others in the first frames), so the other teams are empty until something is placed (11f). Per team 3150 units at most (`maxunits` 32000 is shared by the teams).
- The menu is visible at the start, with the Units tab first.

**Selecting units of every team:** BAR only lets you select your own units, unless the god mode is on. `widget:Update` sends `cheat 1` and `godmode 3` once (frame 6 or later, only with the game option `leveleditor`); checked: then `Spring.SelectUnitArray` takes units of other teams (21 commands in the menu; `godmode 1` = allied teams only, `2` = enemies only, `3` = all, other values switch it off). The engine sends no orders for units of other teams (checked: the order of the command menu and `Spring.GiveOrder` have no effect), so `widget:CommandNotify` forwards every order for selected units of other teams as `led|order|cmdID|options|params|ids` and the gadget gives it with `Spring.GiveOrderToUnit` (checked with the message: units of team 0 and team 2 drove; that the engine calls `CommandNotify` for orders of the command menu is not checked here). Delete, blow up, `assign`, copy and saving a blueprint use the selection of the game; without a selection delete/blow up still act on the unit at the mouse pointer (any team). There is no selection of its own and no Ctrl selection any more.

Notes:
- **Ctrl shortcuts:** `ctrlEdit(key, shift, isRepeat)` is called by the action handler `gridmenu_key` (in front of the build menu) and by `widget:KeyPress` when Ctrl is held without Alt; search fields and chat take precedence. Checked in the game with a chosen commander (builder, build menu active): Ctrl+C reports "units copied", Ctrl+V starts the blueprint stamp, Ctrl+X copies and deletes, Ctrl+Z works and Ctrl+Y redoes (also Ctrl+Shift+Z); Ctrl+B blows up (wrecks stay; Ctrl+B is neither used in the editor nor in the BAR default keys, Ctrl+D creates the builders). The keys were sent to the game window with real key presses (German layout: Z and Y swapped). The BAR default keybind `Ctrl+v = pastetext` (chat) stays untouched because the editor consumes the key first.
- **Key conflict with the BAR build menu:** BAR uses Z X C V / A S D F (with "Any+") for the build menu and eats Ctrl letters as soon as a builder or factory is selected (`actionHandler:KeyAction` runs before `widget:KeyPress`). Solution: widget layer −1, own handler for `gridmenu_key` that passes Ctrl (without Alt) + C/V/X/Z/Y/B/S on to `ctrlEdit` (a held key does not repeat).
- There are still no Alt-letter bindings that override BAR default keys.

### 3.2 Chat commands (prefix `/led_`)
- `help [topic]`: short version or the topics `start`, `keys`, `place`, `units`, `blueprint`, `save`, `team`, `edit`, `features`, `search`, `scenario`, `build`.
- The grid is no longer a chat command: it is a setting (button O, see 4.4). Unit and team are only chosen through the menu and the team buttons (0 = you/Armada, 1 = enemy/Cortex).
- **Team assignment** (click on a team button with selected units; the chat command `assign` no longer exists). **Technique:** the handover runs as a takeover (`Spring.TransferUnit(id, team, false)`, "capture"), because several BAR rules block gifts to enemies/teams without a player when no cheat is on. The message "N units changed team" comes from the game and only counts units that really changed; the message when sending says "… sent".
- `clear`: clears the map (units; undoable).
- `ghost [gl|wg|auto]`: state and mode of the 3D preview.
- Removed (the functions run through keys, buttons and the menu; the Generate tab replaces the group commands, Create and the tiles the blueprint commands, Ctrl+S and the settings page save/load, Ctrl+D builders): `units`, `buildings`, `turrets`, `air`, `ships`, `blueprint`, `save`, `load`, `builders`, `place`, `delete`, `boom`, `undo`, `redo`, `copy`, `paste`, `rotl`, `rotr`, `mirror`, `rotate`, `assign`, `unit`, `team`, `bp_quick`, `bp_next`, `bp_prev`, `bp_place`, `bp_menu`, `spacing` (and the sub-command `blueprint menu`).

## 4. Menu (at the right screen edge)

### 4.1 Structure
- Position: right edge, top edge at 94 % of the screen height (below the menu bar of the game at the top), bottom edge at most at 12 % (for settings, scenario, Generate and Tower Defense 5 %); the collapsed menu sits at the same height. Minimum width 560·S, at most half the screen width.
- **Movable:** the title row is the handle (`panelPress`: left button starts, right click resets; `MouseMove` / `MouseRelease` end it). `basePanelRect()` is the place at the right edge, `panelRect()` = `basePanelRect()` moved by the offset of `panelMover` (`Shared.newPanelMover`) and kept on the screen (room `2·HB + 12` for the team strip on the left and `HB + 2·PAD` for the button column on the right, at least 40·S above the bottom edge). Everything (strip, button column, content, 3D preview) is built from `panelRect()` and moves along. The offset is stored as a fraction of the screen size in the config data (`widget:GetConfigData` / `SetConfigData`).
- Header: above everything a **title row** with the text "Level Editor" at the top left (like "BluePrinter" in the other widget; `titleH()`, 44·S high, not shown when collapsed). ## 6. Editing the selection, moving, redo
- **Edit buttons** (only visible while units are selected) stand in the strip at the left (see 5), above N and the teams: `L` rotates the selection 90° to the left, `R` to the right, `S` mirrors left-right, each around the center of the selection. The gadget sets the units up again (team, neutral flag, height stay), replaces their IDs in the undo stack and reports the new IDs through the game rules parameters `led_newids` / `led_newids_n`; the widget selects them again. At most 2000 units per operation (rotating, mirroring, moving).
- **Moving:** hold Alt, click a selected unit (radius 48 Elmo), drag, release; the offset is rounded to the grid (`led|move|dx|dz|ids`). Preview: green frames at the target. A click outside a selected unit drags the selection rectangle as before.
- **Undo / redo (history in the gadget):** `Ctrl+Z`, `Ctrl+Y` (the chat commands `led_undo` / `led_redo` no longer exist). The gadget keeps a history of steps (at most 300); a step is an action of the user (a row, a blueprint, a delete of the selection …). Before every action the widget sends `led|step`; everything up to the next `led|step` belongs to this step. All messages run in order through the queue (`led()`) so nothing overtakes a not yet sent part of a row. Operations of a step: `add` (unit placed), `del` (deleted or blown up; when blowing up the wrecks that appear are noted through `gadget:FeatureCreated` and removed on undo), `swap` (moved, rotated, mirrored: state before/after), `team` (team change), `fadd` / `fdel` (feature placed / deleted). Units are created anew on undo and redo and get new IDs; `replaceId` then swaps the ID in all steps (through an index ID -> operations, `opsByUnit` / `opsByFeature`, so it does not walk through the whole history), and before every access it is checked whether the ID still belongs to a unit of this type. A new action empties redo. Not in the history: loading a level (`led|load` without suffix, `led|loadfeature`), `led|clear` (empties the history), creating builders (Ctrl+D). Blueprints and paste send `led|load|…|1` (suffix 1 = remember in the history). Checked in the real game: placing, blowing up (wreck gone and back), deleting, team change; in the mock additionally moving, rotating, features, a row as one step and long chains with changing IDs.
- **Selection info:** at the top center the number of selected units, up to four types with count and the sum of metal and energy are shown.

## 10. Levels

- Ctrl+S writes `levels\<name>.lua`: all units (position, height, team, neutral, rotation, `indestructible = true` where set) **and all features** (wrecks, trees, rocks). The file states which game options (e.g. extra pack) must be on in the main game.
- Loading a level (level list in the settings) clears the map (except the builder rows) and sets the level up again (features are replaced if the file contains any). `/led_clear` only clears units.
- Autosave: every 120 seconds and when leaving as `_last`, only when editing is allowed, the load queue is empty and from game frame 100. It saves to `_last`, not to the named level: the named level only changes with Ctrl+S or "Save" in the settings page. `_last` is the state at that moment: units destroyed in a fight in the meantime are gone (wrecks and heaps remain as features). Save under a name of your own before experimenting.
- **Save as new:** a new level made from another one (the level loaded last) takes over the scenario info of that level, but not its title and ID: they are made from the new name (`level_002` → title "Level 002", ID `level002`), so the scenario package of the new level is not built into the folder of the other one (found when a Tower Defense level made from Level8 was built into `scenarios\level8`). Autosaves (`_last`, `_beforeplay`) keep the block unchanged. Checked in the real game.
- The sections `towerdefense = { ... }` (settings of the tower defense page, 11a), `capture = { ... }` (Capture the Flag, 11b), `reclaim = { ... }` (Reclaim the Fame, 11d) and `restrictions = { banned = { ... } }` (11c) are written when the page has been used or the list is not empty; they follow the scenario block in the file. When loading only the known fields of each section are taken over (`knownFields`: the keys of the defaults, plus `spawn` / `goal`); a missing field gets its default, everything else is dropped and not saved again.
- Air units in the air are loaded in the air (with the saved height, otherwise cruise height) and stay in flight mode, air units saved on the ground are loaded landed.
- The gadget places factories anywhere (checked on a test map, steep slopes, water, overlaps).

## 11. Gadget (`unit_level_editor.lua`)

- **No gravestone when a unit is taken away:** moving, rotating, mirroring, deleting and undoing set the unit rules parameter `remove_decorations = 1` before `Spring.DestroyUnit` (`destroyUnit`); the game's gadget `unit_tombstones.lua` leaves a tombstone feature (e.g. `armstone`) next to every destroyed commander unless that parameter is 1. A real explosion (`boom`) keeps wreck and tombstone. Checked in the sandbox: the move of a commander left one `armstone` before, none after.

- Messages through `Spring.SendLuaRulesMsg` with the prefix `led|`: `step`, `place`, `delete`, `deleteids`, `boomids`, `boom`, `undo`, `redo`, `clear`, `clearrect`, `clearcircle`, `clearline`, `clearids` (units `u<id>` and features `f<id>` that are in the way), `fix` (indestructible on / off for buildings in a rectangle), `tdroute` (undo step for the Tower Defense route), `ctfpts` (undo step for the Capture the Flag points), `order` (an order of the player for units of other teams: `led|order|cmdID|options|params|ids`, `Spring.GiveOrderToUnit` in the gadget, see 3.1), `load`, `generate`, `generaterect`, `builders`, `assign`, `feature`, `loadfeature`, `clearfeatures`, `move`, `xform`.
- Only works with cheat or in editor mode; otherwise the message "Cheat mode is off: please type /cheat".
- `GG.LevelEditor` offers the same functions for tests; `GG.LevelEditorSpawnBuilders(x, z, team)` creates the builders (manually without markers, in the team of the call).
- Handovers (`assign`) by takeover, message with the actual count.
- **Loaded stockpile:** units that can stockpile (nuclear silos, anti-nuke ...) get `max(10, queued)` missiles through `Spring.SetUnitStockpile` when the editor places them (`place`, `generate`; also after undo/redo and when a level is loaded). Checked in the real game: a Rector resurrects a wreck, the new unit has `movestate = 0`, a normally placed one `movestate = 1`.

## 11a. Tower Defense (button **TD**, gadget `td_waves.lua`)

Waves of enemy land units walk from a spawn point through waypoints to a goal; the player builds towers next to the route. The level author builds corridors, sets the route and the waves and says what the player may build. The page can start a test in the editor (**Start**); the scenario builder packs it for the official game (section 14).

- **Widget:** the page is the table `td` of the widget; its functions are in `led_td.lua` (`luaui/Include/led_td.lua`, a function that gets `td` and a host table `H`: getters such as `H.S()`, `H.team()` for values that change, the functions and tables of the widget, and `H.armUnit`, `H.disarmModes`, `H.restoreBeforePlay` for what changes its state): `td.layout` builds buttons and labels (also used by `td.press`, `td.height`, `DebugLayout`), `td.draw` / `td.drawTiles` draw, `td.press`, `td.key`, `td.text`, `td.wheel` handle input, `td.drawWorld` (also with the page closed, as `ctf.drawWorld`, as soon as something is set; only the highlight of the point under the mouse needs the open page) draws spawn point (green circle), goal (red circle of 120 Elmo), the waypoints and the line spawn → waypoints → goal (only to look at), `td.hud` the status at the top. Checked in the real game: 1000 / 1000 during the test, 1e9 / 1e10 after Stop. In a finished scenario the resources come from its game options. Checked in the real game: a tower deleted during the test is back after Stop; 1 commander before, 0 during, 1 after Stop.

- **Enforcement (gadget):** payload `enemyTeam;playerTeam;spawnX;spawnZ;goalX;goalZ;leaks;path;waves;restrict;fog;metal;energy` (see the head of `td_waves.lua`; `restrict` = "economy" when the Economy toggle is on, else "towers"), by message `tdw|start|…` or the game option `tdconfig`. Checked in the real game: banned towers are marked, a build order for `armllt` banned / `armsolar` with towers only / `armpb` with tech 2 banned was refused with the message, `armllt` T1 was not refused when only T2 was banned. Not tested: that an allowed tower is queued (a scripted order was not queued in the control run either).
- **Gadget (waves):** `tdw|stop`; waves start `gap` seconds after the previous one (the first after the start); the units of a wave appear one after the other (every 12 frames) at the spawn point, get `MOVE` orders along the path to the goal, health scaled by `hp`. A kill pays the metal and energy cost of the unit to the player team (player = first team with role Player, enemy = first with role Enemy, otherwise team 1). An enemy within 120 Elmo of the goal is removed and counts as through; more than `leaks` = lost, all waves gone and no enemy alive = won (outside the editor the gadget ends the game with `Spring.GameOver`). Status in the game rules parameters `tdState`, `tdWave`, `tdWaves`, `tdLeaks`, `tdMaxLeaks`, `tdKilled`, `tdAlive`.

Deleting or blowing them up with the editor still works (it is not damage). ## 11b. Capture the Flag (button **CF**, gadget `ctf_game.lua`, page `led_ctf.lua`)

**Transports (2026-10-27):** a flag or collection point cannot be loaded (`AllowUnitTransport`, and `AllowCommand` refuses `CMD.LOAD_UNITS` on one); a transport that holds a flag carrier (loaded with it, or the loaded unit takes a flag on the way) is slowed down to the carrier speed (`slowTransport`, `UnitLoaded`) until it unloads it, the flag is delivered or lost, or the game stops (`unslowTransport`). The top speed of an aircraft is set through `Spring.MoveCtrl.SetAirMoveTypeData(maxSpeed)` (Elmo per frame), of other units through COB `MAX_SPEED`; the aircraft way is not checked in the game yet.

**Counted per alliance (2026-10-27):** everything is counted per ally team (`allyOf`): a carrier delivers at any collection point of its alliance (`g.homes[ally]`), allied teams do not take each other's flags, `g.score[ally]` / `g.parked[ally]` are the flags held by the alliance (game rules `ctfScore<ally>`, `ctfTeams` = the ally teams), an alliance whose flags all lie at the collection points of others loses as a whole (`eliminate`, `blowUp` of all its teams), the winner is an alliance (`GameOver({ ally })`). The income of the flags at a collection point goes to the team that owns that point. The score line says "Alliance N". Reclaim the Fame counted per alliance already; its score line says "Alliance N" too.

Flags lie at flag points; units pick them up, carry them to the collection point of their team and are paid (metal per second for every flag that lies at the collection point, nothing else: no one-time reward, no experience); the delivered flag stays at the collection point (`f.parked`, `unpark`), where units of other teams take it (`check`); in mode "own" the owner of the flag only brings it back to its flag point; the pod is not blocking (`SetUnitBlocking`: a blocking pod pushed the carrier into a zigzag); a team that holds enough flags at the same time wins (`g.score` = flags held): `finish` then blows up the units of every team that is not on the winner's side (`blowUp`, flags and collection points stay; checked in the game: 8 units of the other team, 1 left = its own collection point), the same as when the last team standing wins. A destroyed carrier drops the flag where it died (it goes back only after `returnTime` seconds if that is above 0). Humans only: nothing in the code makes a computer opponent play it. Idea and open questions: issue 1 of the repository.

- **Widget part:** `led_ctf.lua` is a Lua file that returns a function; the widget loads it (`VFS.Include("luaui/Include/led_ctf.lua")`, packed by `install_editor.ps1`) and calls it with a `host` table (the services of the widget: `Shared`, `S()`, `say`, `canEdit`, `team()`, `serialize` (= `td.lua`), `disarm` (ends the other modes), `beforePlay` / `afterPlay` (save and restore `_beforeplay`)). It returns the page `ctf` (the widget keeps only one local variable for it; the file is at the limit of 200 locals): `ctf.layout(rect)` (buttons, labels, height, also `DebugLayout`'s eighth value), `ctf.draw`, `ctf.press`, `ctf.key`, `ctf.text`, `ctf.click(x, z)` (left click on the map in the pick mode `ctf.pick` = "home" | "flag"), `ctf.cancel`, `ctf.deleteAt` (Del), `ctf.grab` / `ctf.sample` / `ctf.endDrag` (Alt + drag moves a point (like units and features; also with the page closed)), `ctf.state` / `ctf.applyState` / `ctf.commit` / `ctf.poll` (undo, see below), `ctf.pointAt`, `ctf.drawWorld` (rings), `ctf.toggle` (test), `ctf.payload`. The widget hooks are the same places as for `td`: header button (`kind = "ctf"`, `sideTop(9)`, the area attacks and FX / FD moved down one slot), size of the panel, title ("Level Editor - Capture the Flag"), drawing, press, map click and right click, text and key input, Del, mouse wheel, world drawing, pick mode ended when another mode starts, save and load of the level.
- **Exclusive with the other game modes:** ticking `ctfon` calls `host.excludeOthers()` (switches Tower Defense and Reclaim the Fame off, with a message), ticking `tdon` sets `ctf.data.enabled = false` and `rtf.data.enabled = false`; all three can be off, never two on (checked in the game, see 11d).
- **Data:** own section `capture` of the level file (written by `saveLevel` through `td.lua`, read by `load_level` into `ctf.data`): `enabled`, `amount` (metal, 0 to 99999), `score` (flags to win, 0 to 99, 0 = never), `radius` (Elmo, 10 to 2000), `returnTime` (seconds, 0 to 3600, default 0 = the dropped flag stays), `speed` (top speed of a flag carrier in Elmo per second, 0 to 2000, default 50, 0 = no limit), `visible` (boolean, default true), `homes` (`{ team, x, z }`, as many as you like per team), `flags` (`{ team, x, z }`, team -1 = neutral = Gaia chosen in the strip, otherwise the team chosen in the strip); neutral flags are units of the Gaia team, which has its own unit limit (checked in the editor game: `Spring.GetTeamMaxUnits` is 500 for Gaia, 15750 for the other teams with `maxunits` 32000), so with very many Gaia units in the level a neutral flag could not be created.
- **Page, top to bottom:** checkbox `ctfon` (at the very top, the switch of the mode); Places: `ctfhome` + X, `ctfflag` + X and two lines of what is placed; the box `ctfvisible`; Income: the field `amount`; fields `score`, `radius`, `speed`, `returnTime` (`ctfedit`: click, type digits, Enter accepts, Esc cancels, limits as above); at the bottom `ctfplay`.
- **Gadget:** payload `amount;radius;score;returnTime;speed;homes;flags;visible` (homes and flags as `team,x,z/team,x,z`; visible "1" or "0"), by message `ctf|start|...` (`ctf|stop`; only with cheats or in editor mode) or the game option `ctfconfig` (base64url, decoded by `decode64` of `bar_rules.lua`; the game starts at frame 30). Flags are real units (`lootboxsilver`, the silver pod of the scavengers), collection points are `lootboxnano_t1_var1`, both created neutral, with no selection, always visible (`Spring.SetUnitAlwaysVisible`, flags only when the option `visible` is on: checked with the global line of sight off, four flags in the corners, two in sight of the player's units: with the option off only those two are seen, with it on all four), indestructible (the gadget has its own protection: no damage, no reclaim, capture or self destruction) and with the unit rules parameter `led_nosave` (so the editor does not save them) and frozen with `Spring.MoveCtrl.Enable` (the pod is a drifting unit with the speed 0.03, which would be its only movement); in mode "own" a flag belongs to a team (created for that team: its color), otherwise it is created for the Gaia team. Every 5 frames: a flag that nobody carries is taken by the first mobile unit (not a building, not a Gaia unit, not a unit being destroyed) within the radius; in mode "own" only by a unit of another ally team, a unit of the owner's ally team brings a dropped flag home. A carried flag follows its carrier every frame (`SetUnitPosition` to the position plus one frame of the carrier's speed: measured with the view positions in the game, one frame halves the lag, more makes it worse; the rest is the interpolation of the drawing; air units and units in a transporter work, the position of a loaded unit is the one of its transporter). A carrier within the radius of the collection point of its own team delivers: *once* = `AddTeamResource(team, "metal", amount)` and the flag goes back to its flag point; *income* = the flag stays at the collection point and every second every team gets `amount` times the number of flags it holds. **Carrier:** while a unit carries a flag its weapons have the range 0 (`disarm` saves the ranges in the flag record, `rearm` puts them back on delivery or when the game stops). A destroyed carrier (`UnitDestroyed`) leaves the flag where the carrier died (`f.dropped`); it goes back to its flag point after `returnTime` seconds only when that is above 0. **Lost team:** with mode "own", when all flags of a team are parked (`f.parked`) at collection points, `eliminate(team)` blows up all its units (`Spring.DestroyUnit(id, true)`, not the flags and collection points) and every 30 frames what the team built since; when only one team of the collection points is left it wins ("last one standing"). With reward "once" the flags always return, so no team is lost that way. A team with `score` delivered flags wins (`Spring.GameOver` of its ally team in a finished scenario, only a message in the editor).
- **Undo of the points:** like the route of Tower Defense: `ctf.state()` writes collection points and flag points as text ("t,x,z/t,x,z;t,x,z/..."; "-" for none), every change (`ctf.commit(before)`: click, Del, X buttons, end of a drag) sends `led|step` and `led|ctfpts|before|after`; the editor gadget records the op `ctfpts` (with the unit steps, so Ctrl+Z / Ctrl+Y keep the order) and hands the state of an undo or redo back through the game rules parameters `led_ctfpts` / `led_ctfpts_n`, which `ctf.poll()` reads every frame. The settings (buttons, fields) are not part of the undo.
- **Carrier speed:** `disarm` (a unit takes a flag) saves `ud.speed` in the flag record and calls `Spring.SetUnitCOBValue(unitID, COB.MAX_SPEED, speed * 65536 / 30)` when the unit is faster than `cfg.speed`; `rearm` (delivery, lost flag, stop) sets `ud.speed * 65536 / 30` again. Checked in the game (an `armflash`, `ud.speed` 101): 50.7 Elmo/s while carrying with the cap 50, 101.0 after the delivery; the value is Elmo per second * 65536 / 30 (a first test with `MoveCtrl.SetGroundMoveTypeData("maxSpeed")` had no effect on the speed, `SetUnitCOBValue` has). Not checked: air units and hovercraft.
- **Minimap:** the pods get `Spring.SetUnitNoMinimap` (no engine icon); the unsynced part draws a square per flag in the color of its owner (light grey: neutral) and a ring of the capture radius around every collection point over the minimap (`drawMiniMap`, from `DrawScreenPost` with `Spring.GetMiniMapGeometry`: BAR's minimap does not call `DrawInMiniMap` of gadgets, and `DrawScreen` comes before the minimap). The flag ids come in `ctfFlagIds` ("id:owner,..."); with the option `visible` off a flag is only drawn when `GetUnitLosState` says los or radar (spectators see all). Checked in the game with fog: four flags in the corners, with the option on all four, off only the two next to the player's units.
- **Display:** game rules parameters `ctfState` ("", "running", "won by team N"), `ctfScore<team>`, `ctfTarget`, `ctfTeams`, `ctfOut` (lost teams), `ctfRadius`, `ctfHomes`, `ctfSpots`; the unsynced part of the gadget draws the rings (`DrawWorldPreUnit`) and the score line (`DrawScreen`), so a finished scenario needs no widget.
- **Scenario:** a level with Capture the Flag on becomes a scenario with the settings in the game option `ctfconfig` (teams renumbered like the units, a team with a collection point but without units is added); `ctf_game.lua` and `bar_rules.lua` are in the package and the starter builds them into the small extra game (section 14). The computer opponents get no AI (NullAI), the win condition is "no end" (the gadget decides). A level with both modes on is refused by the script (they exclude each other in the editor).

## 11c. Restrictions of the level (what the player may not build)

- **One list for the whole level** (`rst`, `led_restrictions.lua`, a file of its own because the widget is close to the limit of 200 locals): `rst.data = { banned = { "armllt", ... } }` (names only: every X of the Place menu and of the Tower Defense page puts single units into this list), saved in the section `restrictions` of the level file (only when not empty; `rst.load(data.restrictions)` when loading, no backward compatibility). `rst.set` is the set of the names. Functions: `isBanned`, `setBanned(names, on)`, `toggle`, `allBanned(names)`, `payload()` ("name,name", "-" for none), `start()` / `stop()` (messages `rst|start|payload`, `rst|stop`). The Tower Defense page (`td.isBanned`, `td.techBanned`, the corner buttons) and the Place menu use the same object: what is forbidden in one is forbidden in the other.
- **Place menu (Units tab):** `Shared.newUnits({ restrict = { isBanned, setBanned, allBanned } })` (only the Level Editor passes it; the BluePrinter does not): every symbol has an X box in the upper right corner (`u:xBox`, `u:xAt`; click = `rst.toggle`), a forbidden unit is dimmed with a big red X and "- forbidden" in the title line. `u:filterRects` adds an X box (kind `factionx` / `groupx` / `techx`, `label = "X"`, red when set) to every faction, group and tech button (the button keeps room for it: `reserve`); `u:applyFilter` handles them: faction = all units of it (`u:namesOf`: all groups and tech levels), group = all tech levels of that group of the chosen faction, both ban all or allow all (`rst.allBanned`); the tech X works the same way with all units of that level in all factions and groups (`u:namesOf("tech", t)`; the level as the Place menu counts it: `clamp(floor(techLevel(ud)), 1, 3)`, Epic = 3, half levels count down; there is no rule of its own for a tech level any more). The state of every X button (and the red tint of its button) is computed with `rst.allBanned(names)` at every drawing: forbidding the last unit of a group turns its X on, allowing one unit turns it off. Header clicks and tooltips take the last rectangle under the mouse (the X lies over its button). The favorites view has no X.
- **Gadget `unit_restrictions.lua`** (synced; in the extra game `LevelEditorMod.sdz` and in every scenario package with restrictions): message `rst|start|name,name,...` (only with cheats or in the editor game) or at frame 5 the game option `restrictions` (base64url of the same payload; `GamePreload` reads it). It turns the names into a set of unitDefIDs, tells `GG.BuildBlocking.AddBlockedUnit(unitDefID, team, "level_restrictions")` of BAR for every team except Gaia (BAR then greys the units out in the build menu and refuses the build order itself: checked, the team rules parameter `unitdef_blocked_<id>` = `level_restrictions`; `rst|stop` removes it again) and refuses build orders itself in `AllowCommand` (cmdID < 0; builders and factories; "Not allowed in this level: name"). Without `GG.BuildBlocking` only the second part works. The editor sends `rst|start` when a Tower Defense or Capture the Flag test starts and `rst|stop` when it stops; in the editor itself nothing is blocked.
- **Who and how:** the list holds for **every team**, also for the computer players (they do not know it and may get stuck trying to build a forbidden unit; accepted). `AllowCommand` refuses build orders of builders and factories, also the ones inserted into a queue (`CMD.INSERT` with a negative command in its second parameter). Only a human team gets the message "Not allowed in this level: ..." (`Spring.SendMessageToTeam`), at most once per unit type every 5 seconds; refused orders of AI teams and Gaia stay silent.
- **Scenario:** `Read-Restrictions` in `scenario_builder.ps1` reads the section; with a non-empty list the package gets the game option `restrictions`, the gadget file and `bar_rules.lua`, and `start_scenario.ps1` starts it, like every scenario, with the extra game "Level Editor Scenarios <version>".
- **Checked in the real game:** every X (tech, group, faction, tile) sets and clears the list through simulated clicks; after `rst|start|armllt,armack` both units are blocked in the rules parameters and `armwin` is not, a second `armllt` was refused while the first one built before the block exists, an allowed unit was built; `rst|stop` released the block (the parameters are gone); the tech X of T2 put 319 units into the list, allowing one turned the X off, forbidding it again turned it on, the second click allowed all. Not checked: a real mouse click on an X, the build menu greyed out in a real game.

## 11d. Reclaim the Fame (button **RF**, gadget `rtf_game.lua`, page `led_rtf.lua`)

Crystals stand on the map. A **construction unit of an allowed kind (ground and ships by default) that reclaims a crystal earns points for its ally team**: 1 point per second for every 100 build power, times the rate of the level and times the factor of the crystal size (small 100 %, medium 200 %, large 400 % by default); linear, no diminishing returns. The crystal is never used up and gives no resources. The first ally team that reaches the score limit wins (default 100000; 0 = never). Idea and open questions: issue 2 of the repository (points per second per 100 build power, score limit, odd number of nodes in the middle third of the map, no cap of builders per node: the space around it limits them, air builders reach it from above).

- **The nodes are features:** the crystals `pilha_crystal1` (small), `pilha_crystal2` (medium) and `pilha_crystal3` (large) of the game, each also in ten colors (`pilha_crystal_blue1` ... `_violet3`: 33 feature defs). Every feature of the map whose name matches `^pilha_crystal[%a_]*([123])$` is a node (the digit is the size), so the crystals are placed, moved, deleted and saved like any other feature (Place menu, tab Features, new kind **Crystals**: `featureKind` in `editor_common.lua` puts `pilha_crystal*` there before the rule for rocks, `M.FEATURE_KINDS` has the new entry between Rocks and Wrecks) and the crystals of a map count too. There is no list of nodes in the level file.
- **Widget part:** `led_rtf.lua` (packed as `luaui/Include/led_rtf.lua`, loaded like `led_ctf.lua`; the widget keeps one local variable `rtf` for it) gets a `host` with `Shared`, `cfg` (settings of the widget, for the size of the lists), `S()`, `say`, `canEdit`, `serialize` (= `td.lua`), `armFeature(name)` (arms placing of a feature like a click on its tile in the Features list: ends the other modes, sets `armedFeature`), `armedFeature()`, `disarmAll`, `excludeOthers`, `restrictStart` / `restrictStop`, `beforePlay` / `afterPlay`. The page: `rtf.layout(rect)`, `draw`, `press`, `key`, `text`, `finish`, `height`, `payload`, `toggle`, `counts`, `grid`, `cfg`, `lua`; hooks in the widget as for `ctf` (button `kind = "rtf"` at `sideTop(10)`, the area attacks and FX / FD moved down one slot, panel size, title "Level Editor - Reclaim the Fame", press, text and key input, mouse wheel, saving and loading, blueprint save closes the page, `DebugRtf`, the ninth value of `DebugLayout`). No pick mode, no undo (nothing is placed by the page itself: the crystals are features and have the undo of features).
- **Exclusive with the other two game modes** (`host.excludeOthers()` of the page switches Tower Defense and Capture the Flag off; `tdon` and `ctfon` switch Reclaim the Fame off). Checked in the game by clicks: TD on turns RF off, RF on turns TD off, CF on turns RF off, RF on turns CF off.
- **Data:** own section `reclaim` of the level file (`saveLevel` through `td.lua`, `load_level` into `rtf.data` with `knownFields`): `enabled`, `score` (0 to 9999999, default 100000), `rate` (percent, 1 to 10000, default 100), `f1`, `f2`, `f3` (factor of a small / medium / large crystal in percent, 0 to 100000, defaults 100 / 200 / 400), `visible` (default true), `statics` (buildings, default false), `ground` (default true), `ships` (default true), `air` (default false). Number fields as on the other pages (`rtfedit`, up to 7 digits).
- **Page, top to bottom:** checkbox `rtfon` (switch of the mode); the line "On the map: n small, n medium, n large" (`rtf.counts()`: the features of the map, counted at most twice a second) and, in orange, a hint when the number of crystals is even and above 1 (both sides could farm in peace); the three factor fields; score limit; rate; box `rtfvisible` (crystals always visible) and the four buttons "Builders that score" (`rtfcat`: **Buildings, Ground, Ships, Air**, in that order, each a switch, the data fields above); `rtfplay` (Start / Stop / Reset); **at the very bottom the crystals**: the size filter All / Small / Medium / Large (`rtfsize`, `rtf.sizeFilter`) and a tile list of the crystals (a `Shared.newFeatures` instance with `kind = "crystal"`, its `list` replaced: ordered by size, then by name, so the view "All" shows all small ones first, then the medium and the large ones; the filter shows one size). The tiles are the pictures of the Features tab (with 3D preview at the mouse pointer, the armed crystal is blue); a click arms placing, left click on the map places, right click ends, Del deletes. The list has no scrolling: `rtf.layout` computes its height (`colsFor`, `geom`) and keeps the rectangle in `rtf.gridRect`; the panel is as high as the page.
- **Gadget** `rtf_game.lua`: payload `rate;score;f1;f2;f3;visible;cats` (`cats` = four digits for buildings, ground, ships, air; "0110" by default) by message `rtf|start|...` (`rtf|stop`; only with cheats or in editor mode) or the game option `rtfconfig` (base64url, decoded by `decode64` of `bar_rules.lua`; starts at frame 30 so that the features of a scenario exist). `start` collects the crystals of the map, **makes every one of them again** (same place and heading) and sets metal and energy of the new feature to 0 (the old values are kept and given back by `clear`): BAR's widget `gui_reclaim_field_highlight` shows the metal and the energy of a reclaimable feature on it (two numbers, as soon as a reclaimer is selected), reads them when the feature is created and ignores features below 9 (`minFeatureValue`); setting 0 afterwards on the old feature only changed the numbers to "0" (checked). The unsynced part writes one number over each crystal instead: its factor ("x5" = 5 points per second for every 100 build power at the basic rate, billboard text from `DrawWorld`).
- **Reclaim counting:** `AllowFeatureBuildStep(builder, team, feature, defID, part)` with `part < 0` on a node returns `false` (no resources move, the crystal is not used up) and records the frame of that builder; **it also sets the reclaim fraction back to 1** (`Spring.SetFeatureReclaim`): the engine lowers the fraction of the feature even when the step is refused, and at 0 the reclaim order ends (found in the game: the points stopped after 5 to 7 seconds, the fraction ran from 0.945 to -0.001 while the crystal was still there). `GameFrame` gives every builder whose last step is at most 3 frames old `buildSpeed / 100 * rate / 100 * factor / 30` points (the engine reports the step every frame while the builder reclaims, so "only while actively reclaiming" needs no more logic). Which builders count is a setting of four kinds (`category(ud)` in the gadget, from the unit def): **static** = `speed` 0 (nano turrets; note that `isBuilding` is false for them), **air** = `canFly` (builder aircraft, seaplanes), **ship** = movement class `boat*` or `uboat*` (surface ships and submarines), otherwise **ground** (bots, vehicles, hovercraft `hover*`, amphibious `atank*`, commanders). Ground and ships are on by default: a ring of cheap nano turrets (range 400) would farm a crystal without any builder to hunt, and builder aircraft reach a crystal from anywhere and ignore the space around it, which makes the game dull (decided by the maker of the issue). `FeaturePreDamaged` returns 0, 0 for nodes. The points belong to the ally team of the builder's team (`g.score[ally]`).
- **Win:** score limit reached: `finish(ally)`: every ally team that is not the winner loses, its units blow up (and what it builds later, every second), `Spring.GameOver` outside the editor. Checked: the units of the other team were gone after the win.
- **Display:** game rules parameters `rtfState` ("", "running", "won by team N"), `rtfScore<ally>`, `rtfRate<ally>` (points per second at the moment, published twice a second), `rtfTarget`, `rtfTeams`, `rtfOut`, `rtfNodes` ("x,z,size,factor/..."), `rtfVisible`; the unsynced part draws a gold ring around every crystal (the area from which a builder with a reach of 130 Elmo reaches it, plus a thin inner ring), gold diamonds on the minimap (bigger for bigger crystals; with `visible` off only where a unit or radar sees, `IsPosInLos` / `IsPosInRadar`; the crystals themselves are `SetFeatureAlwaysVisible` with `visible`) and the score line "Team 0: 123/100000 (+21.0/s)" (`DrawScreen`, 175 pixels below the top edge, below the chat lines), so a finished scenario needs no widget.
- **Start** (page) as for the other modes: `beforePlay` (saves `_beforeplay`), `restrictStart`, `rtf|start|...`; Stop sends `rtf|stop`, `restrictStop` and `afterPlay` (loads `_beforeplay`: the crystals, which a builder may have used up after Stop, and the settings come back).
- **Scenario:** `Read-Reclaim` in `scenario_builder.ps1` reads the section (on only; the crystals must exist in `$level.features`, otherwise a note and the scenario is built without the mode); `rtfconfig` (base64url of the payload), `rtf_game.lua` and `bar_rules.lua` go into the package, the computer opponents get NullAI and the win condition is "no end" (the gadget decides), the starter starts it with the extra game "Level Editor Scenarios <version>", the bundle of the lobby holds it (`BundleFiles` come from `$ScenarioGameFiles`); the extra game of the setup (`install_editor.ps1`) holds the gadget too (the setup stamp of `editor_manifest.ps1` covers `rtf_game.lua` and `led_rtf.lua`). The crystals are normal features of the level, so the scenario mechanism of the game creates them. A level with Reclaim the Fame and another mode on is refused by the script.
- **New feature IDs:** at the start the gadget destroys every crystal and creates it again with 0 metal and energy (BAR shows the resources of a feature that are read when it is created; the number over the crystal is the points factor). In the editor it tells the editor gadget the new IDs (`GG.LevelEditor.replaceFid(old, new)`), so the steps of the undo history (placing, deleting, moving of a crystal) still find the crystal after a test.
- **Checked in the real game (2026-10-24, sandbox):** (1) gadget with scripted builders: team 0 with two 210-build-power builders on a large crystal 16.8 points per second (factor 4), team 1 with one on a small one 2.1 (factor 1), a nano turret next to the crystal with a reclaim order scored nothing, the crystal stayed at full reclaim fraction and the score grew linearly until the limit, the winner was announced and the units of the other team were gone; (2) page: the Reclaim the Fame button, tiles (the tile numbers of "All" and of the "Large" filter), placing with the tiles on the map (2 small, 1 medium, 2 large counted by the page), number fields typed, switch on, Start, Stop (crystals and settings back after the reload of `_beforeplay`: 2/1/2, score, rate, factor, enabled); (3) saving and loading the section `reclaim` (read back from the file written by the editor); (4) scenario package built by the script from that level (`rtfconfig` decodes to the payload) and played from `scenario.txt` with the extra game: the same points, win at the limit; (5) no number from BAR's reclaim fields on the recreated crystals, the factor label instead; (6) exclusion of the three modes by clicks; (7) the kinds of builder (2026-10-25): one builder of each kind (ground bot 210 build power, builder aircraft 120, nano turret 200, a ship 125 placed on land next to the crystal) at one large crystal with factor 400 %, seven settings sent one after the other: "0110" 13.4 points per second, "1111" 26.2, air only 4.8, buildings only 8.0, ground only 8.4, ships only 5.0, nothing 0.0, all as computed; the page buttons in the order Buildings, Ground, Ships, Air with the defaults, a click switches one, the payload of the page ends with "0110"; a scenario built from a level with `air = true` carries "0111" and the builder aircraft of the second team scored in the game (3.3 instead of 2.1 points per second). Pictures: `docs/level-editor-reclaim-the-fame.jpg`.
- **Not tested:** real ships on water (the test ship stood on land, its movement class `boat3` is what counts), several builders of different teams on one crystal in the same moment (each scores for its own ally team), a very large number of builders, play with two human clients over the network (the test used one human and scripted builders of the second team: the gadget does not depend on who gives the orders), builders with a modified build speed (the points use `UnitDefs[..].buildSpeed`), the counting of crystals that a map brings itself.
- **Open:** balance (default factors 1 : 2 : 4, rate, score limit), whether nano turrets should score, random places for the crystals at the start (the issue wants an odd number in the middle third of the map; today the level maker places them), a computer opponent that farms crystals, a custom crystal model.

## 11e. Arena (button **A**, page `led_arena.lua`)

**Status: implemented and checked 2026-10-28 in a sandbox game (`test-data\tools\arena_test.ps1`, results at the end of this section); the look and the clicks with the mouse are not seen by the user yet.** User page: `tools\arena.md` (the folder `LevelEditor/tools` is for tools, `game-modes` for modes). A tool like Generate (not a game mode, no scenario, no winner, no result display): it sets up armies of different teams around one point and lets them fight there, so that one can watch units against each other (for example 100 Behemoths against 100 Juggernauts). Its settings are saved in the level, the march order is not.

- **Button and page:** **A** in the button column between **G** and **TD** (same colors as the other pages: lighter while its page is open). The page is the table `ar` of the widget; its functions live in `led_arena.lua` (`luaui/Include/led_arena.lua`, a function that gets `ar` and the host table `H`, like `led_td.lua`; the widget is close to the limit of 200 locals). A new file is added to the lists in `editor_manifest.ps1` and `$ScenarioGameFiles` only where needed (the page is widget only; the gadget part is in `unit_level_editor.lua`).
- **Page, top to bottom:**
  1. **Radius** (one input over the full width, Elmo, default 1000): the distance of every army from the Arena Point (a radius, not a diameter).
  2. **Budget for all rows**: Metal and Energy (inputs, shown as "M 5000" and "E 5000").
  3. **Table of 10 rows** (row n = team n-1, same numbers and colors as the team buttons at the left; the editor game has **ten teams** (see below), a team the game does not have is gray and is skipped by Generate and Start with a message; Gaia is no row): **On / Off** (the first two rows are on at the start, the others off), the button **Units**, **Count** (input), **Metal** and **Energy** (inputs), and the **remaining budget** (see below). The **team number** of a row is a button: it opens the menu **Copy to** with the other teams; a click on one copies on / off, count, budget and allowed units of this row to that team. Under the column heads is a row of buttons **C**, one per column (the Team column has "-"): a button writes the value of its column into all other rows, also the rows that are off: Metal / Energy take the two fields of the budget, On, Count and Units take the value of the first team (Units copies its allowed list). The row values stay editable. Default **Count** of a row is 50.
  4. **Buttons:** **Generate** (left), **Arena Point** (sets / moves the point), **X** (deletes it), **Clear**; below them **Formation attack** (toggle, green when on) and **Start** (red **Stop** while it runs).
- **Row off:** nothing is generated for it, and its units do not get the fight order at **Start**. They stay where they are.
- **Units button:** green with the number of allowed unit types ("Units 12"), gray when it is 0. A new row allows **nothing**. Pressing it opens the **unit window** left of the team strip, as wide as the Place menu (`uGrid:size()`: three columns of tiles by default); the same button again closes it.
- **Unit window:** the Place menu without the tabs Recent / Features / Blueprints, so only the Units tab with the filters (faction, group, tech) and the search. Every unit tile has a **green check box** in the upper right corner instead of the red X of the level restrictions (click = allowed / not allowed for this army, an allowed unit has a bright green check; a click anywhere on the tile does the same); the check boxes of the faction, group and tech buttons allow or remove all units of that filter at once (a button of which only some units are allowed has a light green shade, all of them a stronger one: `restrict.anyBanned`) (same logic as the X boxes of 11c, `Shared.newUnits` gets an allow variant of its `restrict` hook: green, no dimming). The head is a row in the color of the team ("Team n: allowed units"), then **Clear Allowed Units** (empties the list) and the reddish **Close**; copying between teams is done with the team number in the table. Hovering a tile shows the 3D preview and the text under it, like the Place menu (the same code). Only units that **move** and **turrets** (armed buildings) are offered; factories, economy buildings, walls and other buildings are hidden. The lists are **independent** of the level restrictions (11c) and of Tower Defense; while the unit window is open the check boxes change the army list, not the level restrictions.
- **Arena Point:** a point on the map, drawn as a thick red circle (about 64 Elmo) and, while the page is open, a thin red ring of the radius (where the armies will stand). **Arena Point** arms the mode (click on the map sets or moves the point; right click ends the mode). **Alt + left mouse button held** over the point (64 Elmo, also with the page closed) moves **only the point**, like the points of Tower Defense and Capture the Flag. **Shift + Alt + drag** over the point moves the **whole setup**: the point and all armies (see "Moving"). **Del** with the mouse over the point and the button **X** delete it.
- **Generate:** arms the mode (the Arena Point hangs half transparent at the mouse pointer while Generate or Arena Point waits for the click, `ar.drawWorld`); a click on the map **sets the Arena Point there** (it moves if it existed) and places all armies of the rows that are on around it. It is a single action: after the click on the map the button is off again (press Generate again for another round). One undo step.
  - **Geometry:** the armies stand on equal angles around the point at the distance **radius** (2 armies opposite each other, 10 like the slices of a pizza), every army as a **rectangle** (rows and columns of cells of the largest footprint in the army plus the spacing of the editor), facing the point. The units of an army are ordered by type.
  - **What and how many:** units are drawn **at random** from the allowed units of the row that still fit into its remaining budget, until the **count** is reached or no allowed unit fits any more. A budget field left empty means unlimited (Metal and Energy separate: 5000 Metal and Energy empty is allowed); both empty = no budget, no message. Count empty = no limit by count (then the budget decides). Count empty **and** no budget: nothing is generated for that row and a message says so. An army never has more than **3000** units on the map (or the engine limit of the team, `Spring.GetTeamMaxUnits`, if that is lower).
  - **Remaining budget** (column at the end of the row): budget minus the cost (metal and energy) of **all** units of that team on the map, also the ones placed by hand and the commander; it may be negative. Generate fills only what is left.
  - **Every unit is placed:** a unit that does not fit its spot (water depth and slope against its move definition: `minWaterDepth`, `maxWaterDepth`, `maxSlope`; ships only in water; air units anywhere; turrets by `Spring.TestBuildOrder`) goes to the **nearest free ground**, like a ring around the block, as long as count and budget are left. Trees, rocks and other units are ignored (the switch **W** does not count). Only when no fitting ground exists at all (for example ships on a map without water) the rest is dropped, with a message such as "Army 3: 87 of 100 placed (no fitting ground)".
  - **Map edge:** an army (its rectangle) that lies outside the map is shifted as a whole onto the map with at least **100 Elmo** distance to the edge.
  - **The units are marked** (`arena` flag, saved in the level file like `indestructible`, a unit rules parameter) so that **Clear** knows them.
- **Clear:** deletes **only the units that Generate placed** (all rows) and the Arena Point; units placed by hand stay. One undo step.
- **Moving the setup:** every army keeps its **natural spot** (point + radius * direction, as generated) and its actual spot is the natural spot pushed onto the map (100 Elmo margin). **Shift + Alt + drag** moves the point and every natural spot by the same offset; the units of an army move by the change of its actual spot. An army that was pushed inward therefore stays where it is until the point is far enough inside that its natural spot is on the map again; then it follows. One undo step.
- **Start / Stop:** like the Tower Defense test. **Start** needs an Arena Point (else the red message "Set the Arena Point first" and a chat message, nothing happens) and no running Tower Defense test (both use `_beforeplay`). It saves the level as `_beforeplay`, then sends `led|arenastart|<x>|<z>|<teams>` to the gadget (it sets the game rules parameter `arenaState` = `running`), which gives every unit of the teams whose row is on that can move (Gaia not) the **fight order** (`CMD.FIGHT`, so they attack on the way). **Formation:** every army (team) keeps its rectangle: the target of a unit is its own position shifted by the vector from the center of its army to the Arena Point, so every unit walks straight ahead and the center ends on the point (a front, no heap); targets are kept 16 Elmo inside the map. **Formation attack (button of the page, `formation` in the section arena, default on; `led|arenastart|x|z|teams|formation`):** the fighting is the engine's: `CMD.FIGHT` attacks everything that comes into the range of the weapons on the way (a unit with a long range, artillery, stops early and fires, the others walk on), `CMD.PATROL` does the same between two places again and again. *Phase 1 (only with the button on; `startArena` and `arenaStep` in `unit_level_editor.lua`, `arenaStep` runs every 10 frames):* every unit walks at the speed of the slowest unit of all armies until the center of its army is at **25 %** of its first distance from the point (`CMD.FIGHT` to its own place shifted by 75 % of the vector to the point); the cap is the data of the move type (`Spring.MoveCtrl.SetGroundMoveTypeData` / `SetGunshipMoveTypeData` / `SetAirMoveTypeData`, `maxSpeed` and `maxWantedSpeed`; the command `CMD.SET_WANTED_MAX_SPEED` alone did not limit the speed: after 7 s the three armies had walked 262, 263 and 262 Elmo with the cap, 609, 458 and 619 without). *Phase 2 (`arenaFight`; with the button off it starts at once, without a cap):* full speed, `CMD.FIGHT` to **250 Elmo in front of the Arena Point** (every unit to its own place shifted along the line of its army to the point), then a queued `CMD.PATROL` to **250 Elmo behind it** (through the other army): the units go back and forth through the point and fight on the way, whoever is not fighting walks on. **Seen in the test (2026-10-28, `zz_arena_fight.lua`, two armies of 20, radius 1000):** with fight and patrol no unit fires at the ground (the area attack `CMD.ATTACK` with a radius, used before, made part of the units fire at the ground while enemies were out of range); with the button off the first shots fall about 300 frames earlier. The camera stays. **Stop** sends `led|arenastop` and loads `_beforeplay` again (`load_level`, like `td.toggle`): everything is as before the start, destroyed units are back and every run starts the same. What the user changes **on the pages** while the fight runs is kept (settings of the pages, the teams of the page T, the restrictions, the scenario info: `reloadBeforePlay` in `lvl_level_editor.lua` takes them over after loading `_beforeplay`, the same for the Stop of Tower Defense, Capture the Flag and Reclaim the Fame; checked 2026-10-28 with `zz_keep.lua`); what the user places or deletes on the map meanwhile is lost with the fight.
- **Undo:** every action of the page is one history step and can be undone with Ctrl+Z / Ctrl+Y: set / move / delete the point, Generate, Clear, move of the setup. The state of the point and the armies is written as text (`ar.state()`) and sent as `led|arenastate|before|after`; the gadget keeps it as the operation `arena` of the history next to the unit steps (as `tdroute` does for Tower Defense). Start / Stop are not in the history.
- **Data:** own section `arena` of the level file (written by `saveLevel`, read by `load_level` into `ar.data`; only the known fields, no backward compatibility): `radius`, `budget` (`{ metal, energy }`, global fields), `point` (`{ x, z }`, missing = none), `rows` (10 entries by team: `on`, `count`, `metal`, `energy`, `allowed` = list of unit names) and `armies` (list of `{ team, nx, nz, ax, az, hw, hh }`, one entry per team, the one of its last Generate: natural spot, actual spot and half width / height of the block, so that moving works after loading). The march order is not saved. The scenario builder does not read the section; the units with their flag are normal units in a scenario.
- **Messages and gadget:** `led|place` gets a tenth field (`1` = placed by Arena) and `led|load` a twelfth; `led|arenastart|x|z|teams` and `led|arenastop` (the gadget has nothing to undo, the widget reloads the level); the gadget keeps the flag in the snapshot of a unit (undo, redo and the move of a selection keep it); `led|arenastate|before|after` for the history. Clear sends the ids as `led|clearids` in one step.
- **Checked in the game (2026-10-28, sandbox, 4 teams, flat map; `arena_test.ps1` with `zz_arena.lua`):** the button A sits between G and TD; Generate with radius 3000: armies of 30, 30 and 55 units (count, count, budget 12000 minus the commander) at 2995, 2994 and 3010 Elmo from the point, three armies at equal angles; a budget below the cost of the commander gives "nothing fits into the budget"; a row that is off gets nothing; moving the whole setup by 600 moves every unit by exactly 600 and keeps the flag; Ctrl+Z / Ctrl+Y bring back the move, the Generate (units with the flag, point and armies) and the state text; Start gives every unit of the rows that are on the order to fight to the point (they march, the centers move toward it), Stop brings back all units; Clear removes exactly the marked units and the point; the unit window with its check boxes, the copy buttons and the filters is drawn (screenshot). **Found by the test:** the table showed the Gaia team as a row; the move of a selection (`transformUnits`) dropped the flag; a helper declared after its first use broke the whole widget (Lua local scope: the test log showed it as `attempt to call global`).
- **Not checked:** clicking with the real mouse (Alt + drag, Shift + Alt + drag, the clicks in the table and the window), the number fields typed by hand, ships and air units, a fight that really takes place (the armies were 3000 Elmo apart, they only marched), 3000 units per army (the largest test was 55), the saved level after reload (the flag and the section are written and read by the same code as the other sections; a reload through `_beforeplay` at Stop worked).

## 11f. Teams: alliances, human or AI, start resources (button **T**, page `led_teams.lua`)

**Status: implemented and checked 2026-10-28 in the sandbox (`test-data\tools\zz_teams.lua`, `zz_modes.lua`, results at the end of the section).**

- **Ten teams:** the editor game always has ten teams (`choose_map.ps1`, `Write-StartScript`), each in its own ally team of the engine (see 2.3). Only teams 0 and 1 keep their start commander; the gadget removes the ones of teams 2 to 9. A team belongs to a scenario only when it has units (the editor's builders and Gaia do not count), **or** when it is the spawner of a Tower Defense level (see below).
- **Data per team** (section `teams` of the level file, read with `knownFields`; no other place holds it any more): `group` (alliance, 0 = none, 1 to 10 = one of ten colors), `ai` (`""` = a human, else the name of an AI: `NullAI`, `BARb`, `CircuitAI`, `CircuitAI easy`, `SimpleAI`, `SimpleDefenderAI`, `SimpleConstructorAI`, `ScavengersAI`, `RaptorsAI`), `metal` and `energy` (start resources, default 1000 each). **Defaults:** team 0 is a human, every other team is an AI with `NullAI` (it does nothing), nobody has a group, so everybody is an enemy of everybody. The old scenario fields `roles`, `tiers` (tech per team), `ai`, `teamai`, `metal` and `energy` of the scenario block are gone (no compatibility).
- **Alliance (group) in the editor:** the engine cannot move a team into another ally team, so the widget sends the groups to the gadget (`led|teams|...`) and the gadget sets the alliances between the ally teams with `Spring.SetAlly(a, b, true/false)`: two teams are allied when both have the same group (> 0), else they are enemies. Allied teams do not shoot each other. The groups are applied on every change and after loading a level.
- **Strip at the left (see 5):** a **right click** on a team button opens a small menu with the ten colors and "none" (nothing else: AI and human are chosen on the page **T**). Every team button is drawn as: outer frame in the color of the group (none: no frame), a thin black border, inside the team color with the number. The **chosen** team is no longer marked by a light background and a white frame (that would hide the group frame) but by the full color inside (the others are dimmed) and a bright number. The tooltip names group, human or AI and the start resources.
- **Page T** (button **T** in the button column, where the button AI was; panel like the page I): one row per team 0 to 9 with the columns **Team**, **Human / AI** (a click switches; a new AI is NullAI), **AI** (the name, a click opens the list of the AIs above; "-" for a human), **Alliance** (a click opens the same color menu), **Start metal** and **Start energy** (numbers, click and type). Teams without units are shown too (gray), so the AI and the alliance can be set before units are placed. The page and the strip show the same data. The page I (scenario info) keeps title, author, summary, briefing, win condition, grace period and ID.
- **The AI in the editor:** the editor game starts with the AI of team 1 (`Read-Level` gives `Ai1`, as before) and ignores the others; the choice is used by the scenario (below). Without a human on a team the AI named there plays it.
- **Level restrictions (11c)** hold for **everybody** (no tech or restriction per team any more).
- **Alliance of a team in the code:** one function (`GG.LedAlliance(team)` in the gadgets, a function of the same name in the widget; `led_gadgets.lua`): in the editor the group (a team without a group is its own alliance), in a scenario the ally team of the engine. Tower Defense, Capture the Flag and Reclaim the Fame use it (before: the ally team directly).
- **Tower Defense:** **all teams that are an AI are enemies**; the **first AI team** (lowest number) spawns the waves (`enemyTeam` of the gadget payload); every human team is a player (the build rule of the gadget holds for all humans). In the scenario the spawner is part of it even without units. The enemy AI stays `NullAI` in Tower Defense (the gadget moves the units along the waypoints). **Capture the Flag and Reclaim the Fame** use the AI that is set (it does not know the modes and will not fetch flags or reclaim crystals; that is accepted: an own AI would have to be written).
- **Scenario builder:** reads `teams` from the level: teams = those with units, plus the Tower Defense spawner and the teams with a collection point of Capture the Flag; a team with `ai = ""` has no `[ai]` section in `scenario.txt` (a human, the lobby puts the players in), a team with an AI gets the `[ai]` section (or `LuaAI=`), as in `Get-AiSpec`. Teams with the same group get the same `allyteam` in `scenario.txt`, a team without a group its own. The start resources of a team are written as `StartMetal` and `StartEnergy` of its `[team]` section (to be checked in the game: BAR also reads the game options `startmetal` / `startenergy`; if the engine ignores the keys of the team section, the largest values of the teams go into the game options).
- **Files:** `led_teams.lua` (data, page, menu, frames; a function that gets the host, like `led_arena.lua`), the gadget message `led|teams|g0,...,g9` and `GG.LedGroups` in `unit_level_editor.lua`, `G.allyOf`, `G.teamsOfAlliance`, `G.allianceList`, `G.allianceName` in `led_gadgets.lua` (`ctf_game.lua`, `rtf_game.lua` and `td_waves.lua` call them instead of the engine's ally team functions), `led_td.lua` (`td.payload`: player = first human team, enemy = first AI team, start resources of the player), `scenario_builder.ps1` (`Read-Teams`), `choose_map.ps1` (`Read-Level`: `Ai1` is the AI of team 1 from the section `teams`).
- **Checked (2026-10-28, sandbox, window next to a running game):** the editor game with ten teams (only teams 0 and 1 have a unit at the start, `maxunits` gives 3150 units per team and 500 for Gaia, before 15750 with two teams); right click on a team button opens the menu, a click chooses the group; the Alliance cell of page T does the same; `Spring.AreTeamsAllied(0, 1)` is true after both are in group 3 and false for team 2; Human / AI, the AI list and a number field work; save and load bring the section back and apply the alliances again; Tower Defense payload "1;0;..." (enemy 1, player 0) and the test runs; Capture the Flag with both teams in one group runs with the one alliance 103; Reclaim the Fame with two enemy teams has two score entries (alliances without units are left out); the scenario builder on `demo_td_serpentine` and on a level with groups: both teams of a group get `AllyTeam=0`, a human has no `[ai]`, `StartMetal` and `StartEnergy` are written per team. **Not checked:** the start resources per team in a real scenario game (whether the engine takes `StartMetal` of the team section), several humans in one scenario in the lobby, allied armies and enemies in a real fight, Capture the Flag and Reclaim the Fame with allied teams to the end.

## 14. Scenario builder (`scenario\`, start menu key 3)

- **Button I in the game** (button column at the far right, below O; page of its own like O): edits the scenario info in the widget (`scenario` table, fields as in the block below). Rows: title, author, summary, briefing (Shift+Enter = new line), win condition, grace period (m:ss), ID (a–z, 0–9) (the roles, tech per team, AI behavior and start resources of the page I moved to the page T, 11f; tech is now only the restrictions of 11c, for everybody). Text fields take the input through `OwnText`; Enter accepts, Esc discards. Changed info (`scenarioDirty`) is written by `saveLevel` as a block (`Json.encode`) instead of the block from the file; loading resets it. There is no save button on this page any more: the info is written with Ctrl+S (or "Save" / "Save as new" in the settings page O). Line endings `\r` in the level file are tolerated when reading the block (editor and script). Checked with mocks and in the real game (button, typing, saving; the block was in the level afterwards).
- **Button T in the game** (button column, between I and ?; same panel as I, `scenarioPage = "teams"`, drawn by `led_teams.lua`): see 11f. The AI per team is part of the section `teams`; `scenario_builder.ps1` writes per AI team an `[ai]` section (BARb and CircuitAI version `stable`, NullAI `0.1`, `CircuitAI easy` with `[Options] profile=easy`) or, for the Lua AIs, `LuaAI=<name>;` in the `[team]` section; in Tower Defense every AI team is NullAI (the gadget steers the waves). `choose_map.ps1` uses the AI of team 1 for the editor start (without an entry NullAI). It takes effect only at the next start (see section 15). BARb has only its default profile, as `AIOptions.lua` offers no other.

- `choose_map.ps1` (key 3) starts `scenario\scenario_builder.ps1` (PowerShell 5.1, without Python; the target computer needs only PowerShell as well) for the chosen level (also directly: `powershell -File scenario\scenario_builder.ps1`, without `-Level` with a level selection): asks title, author, summary, briefing, win condition, grace period, ID (human or AI, alliances and start resources come from the section `teams` of the level, 11f). `-Level name -Auto` asks nothing.
- The answers are in a block `scenario = [==[ <json> ]==],` directly after `return {` in the level file (keys `title`, `author`, `summary`, `briefing`, `roles` per team number, `ai`, `win`, `metal`, `energy`, `sid`) and are the defaults on the next run. The editor copies the block unchanged and does not know the fields. The editor (`saveLevel`) reads the block of the target file before overwriting and writes it back unchanged; if it is missing there it takes the block of the level loaded last (`keptScenario`). Autosave `_last` included.
- `-Edit` (by hand): shows the info saved in the level numbered (title, author, summary, briefing, role per team, tech per team, AI, win condition, metal, energy, grace period, ID); choose a number and change the value, every change is saved in the block at once (only with exactly one player team); Enter ends, then the question whether the package should be rebuilt. Without a block: note, create a scenario first (key 3). Checked with test data.
- **Grace period** (field `grace`, minutes as a number, also fractional, input `m:ss`, `2,5` or `3`): with `grace > 0` the script writes per alliance `StartRectLeft/Top/Right/Bottom` (frame around the units of the alliance plus 300 Elmo margin, with 30 or more units without the outer 3 % of each edge; overlapping frames or ones closer than 500 Elmo are separated, the one of the alliance with the smaller number (player) stays, divided by the map size; double values, because `[math]::Max` rounds with integers), the game option `norushtimer = grace` (dot as decimal separator) and `startpostype=2`. The game (`game_startbox_config.lua`) widens the start boxes to the whole map for every other start mode, that is why `startpostype=2` is needed; then `game_no_rush_mode.lua` (commands and damage outside the start area) and the start position choice take effect. The editor writes `mapsize = { x, z }` (Elmo) into the level file; if it is missing the script stops with a message (save the level again in the editor). `scenario_briefing.lua` does the start position choice itself (`Spring.RequestStartPosition` in the middle of the own start area, then `SendLuaRulesMsg("ready_to_start_game")`; only if `grace > 0` is in `scenariooptions`). Checked in the game (level 8, 2:30): the game starts without input, the start boxes match the fractions, `norushtimer=2.5`; a move command into the enemy area and an attack command on an enemy unit are discarded, a command in the own area is accepted.
- **Resurrected units: Hold Position.** In the scenario the briefing widget (`widget:UnitCreated`) does this for the units of the player (see 11); for AI teams it is not possible in the official game, because widgets only control own units.
- **Tech restriction** (field `tiers`, per team number a string of allowed tiers, e.g. `"12"`; if a team is missing or it is `"123"`, there is no restriction): switches T1/T2/T3 per team in button I (green = allowed, red = off) and a question in the script. The script writes `tiers` with the new team numbers into `scenariooptions` (only teams with a restriction; the briefing shows them) and the game option `techtiers` (base64url of `team:digits/team:digits`) and packs `unit_restrictions.lua`. At frame 5 the gadget `unit_restrictions.lua` blocks per team all units outside the allowed tiers: at the build blocking of BAR (`GG.BuildBlocking.AddBlockedUnit(id, team, "scenario_tech")`, greyed out in the build menu) and in `AllowCommand` (build orders of builders and factories, also inserted ones). No cheat mode is needed any more (until 2026-10-27 the briefing widget switched cheats on for a few frames and sent `/luarules buildblock`); packages built before have no `techtiers` and are rebuilt with key 5. Tier 1.5 counts as T2; all units without the field count as T1; Epic units count as T3 (`techLevel`). Existing units stay. Checked in the real game with the earlier widget (player T1+T2: only T3 locked; enemy T1: T2 and T3 locked); the gadget way is not checked in the game yet.
- **Tower Defense scenario** (the level has the section `towerdefense` with `enabled = true`, spawn point, goal and waves; `Read-TowerDefense`, `Find-CloseBrace` in `scenario_builder.ps1`): the waves run in the gadget `td_waves.lua`, which the official game cannot load. So the package contains a copy of the gadget, and `start_scenario.ps1` starts every scenario with the extra game **"Level Editor Scenarios <version>"** (`data\games\LevelEditorScenarios_<version>.sdz`, `Write-ScenarioGame` in `shared\bar_common.ps1`: `modinfo.lua` with `depend = { "<installed game>" }`, the gadgets `td_waves.lua`, `ctf_game.lua`, `rtf_game.lua`, `unit_restrictions.lua`, `unit_indestructible.lua`, the lootbox stub as `pve_supply_drops.lua` and `luaui/Include/bar_rules.lua`; the version = the first 8 hex digits of a SHA-256 over the BAR version and the texts of these files, the zip entries have the fixed time 2000-01-01; an existing file of that version is not built again) instead of the plain game version (`gametype=Level Editor Scenarios <version>`; the official files stay unchanged). From the editor's menu its files are the current ones of the editor (the setup has built the same game already), from an unpacked package the package's. The builder writes two more game options into `scenario.txt`: `tdconfig` = base64url (no `;` inside) of the payload `enemyTeam;0;spawnX;spawnZ;goalX;goalZ;leaks;path;waves;restrict;fog` (team numbers as renumbered for the scenario: the player is 0, the enemy team the first one with the role Enemy, otherwise the first other team) (the indestructible buildings, the corridor walls among them, go into the game option `fixedunits` of every scenario, see 11a). The scenario script `UNIT_RX` reads the flag from the unit lines (without it the flagged units would be skipped). Further settings for a Tower Defense scenario: the AI of the enemy team is NullAI (BARb would take the wave units over), `deathmode` is `neverend` (the gadget ends the game: all waves beaten = won, too many through = lost; a destroyed start commander must not eliminate the player), a level with only one team gets an extra enemy team without units (the waves belong to it), and the grace period is switched off (`$grace = 0` after saving the info; with `norushtimer` the no-rush gadget of the game blocks orders to targets outside the start area, so the wave units stood still at the spawn point: checked in the real game with the same level, 3 of 8 wave units moved with the grace period of 2:30, 8 of 8 without; the start areas of the sides were also wrong for the extra enemy team). The info page (button I) stays the same; the saved `ai` and `win` answers are not changed.
- **Capture the Flag and restrictions in the scenario:** a level with Capture the Flag on gets `ctfconfig` and `ctf_game.lua` (11b), a level with a non-empty list of restrictions gets `restrictions` and `unit_restrictions.lua` (11c); both need the small extra game of the starter. Tower Defense and Capture the Flag on in the same level file are refused by the script (`throw`, they exclude each other in the editor); the same for Reclaim the Fame with one of them. ### 14.1 Several players: lobby, split screen, direct host and join (tested only on one computer)

- **Entries:** start menu key 4 → scenario → **Single player** (`start_scenario.ps1` without options), **Host** (`-HostGame -Lobby`), **Join** (`-Join -Lobby`) or **Split screen** (below). Every package also has `Host Game.bat` and `Join Game.bat` with the same options (written by the builder next to `Start Scenario.bat`, together with `player_mapping.ps1` and `lobby.ps1`, which the starter dot-sources at its start). All players need the same BAR version and the same scenario folder; every computer builds the extra game itself.
- **Options of `start_scenario.ps1`:** `-HostGame`, `-Join` (asks for the address and the name), `-JoinIp <address>`, `-Name <name>`, `-Lobby` (the lobby below), `-LobbyPort` (TCP, 8453), `-LobbyAutoStart n` (the host starts by itself when n players are in: tests), `-Port` (UDP game port, 8452, fixed for the user), `-Wait` (seconds the game waits after the host has loaded before it starts: 90 without a lobby, 15 with a lobby, 10 is given by the split screen), `-Mapping "PlayerA=0,Anna=2"` (who plays which team, first = host), `-Players n` (without a lobby and without `-Mapping`: number of humans for the dialog), `-HostIp` (0.0.0.0; the split screen gives 127.0.0.1), `-WindowRect x,y,w,h`, `-NoBuild`, `-WaitForHost`, `-ScriptOnly`.
- **Join:** the address comes from a list of the last 10 addresses (`%LOCALAPPDATA%\BAR-Scenario\Last Joined Addresses.txt`, one per line, newest first, shared by all scenarios): a number picks one, Enter = the newest, anything else is a new address; the used one moves to the top. The name is asked next (default: the Windows user name cleaned to letters, digits and `_-[]`, afterwards the last one used, `Last Player Name.txt`).
- **Lobby (`lobby.ps1`):** runs right after the scenario is read, before the extra game is built and the map is fetched. The host listens on TCP `-LobbyPort` (all network cards) and shows the screen of `Get-LobbyLines`: a title line (host, addresses, port, number of players), one box per team (`Get-TeamInfo` reads `Side` and `AllyTeam` of `scenario.txt`: "Team n: Side, ally team m"; players below, "(host)" behind the host; two free lines between the boxes, one or none if the window is not high enough) and the last box "[ Start game ]" ("ready" or the reason); **the focus starts on "Start game"**, so Enter or F5 starts at once once two players are in. Everybody who joins is put into a team box at once: the team of the last mapping (by name, `%LOCALAPPDATA%\BAR-Scenario\Last Player Mapping.txt`) if nobody is there, otherwise the first team without a player, otherwise team 0; a team may hold several players; a joiner whose connection breaks (also without `BYE`) is removed. **Keys of the host:** `Tab` / `Shift+Tab` or `Left` / `Right` = next / previous box (the last stop is "Start game"), `Up` / `Down` = player in the box, `Enter` = pick the player up (yellow, "<- moving"), then `Up` / `Left` / `Down` / `Right` move them into the neighbouring team box, `Enter` drops them, `Esc` puts them back; `Enter` on "Start game" or `F5` = start (two players are needed, otherwise the reason is shown), `Esc` twice = cancel. **Protocol** (TCP, one UTF-8 line each): joiner `HELLO <name>`, `BYE`, later `READY`; host `OK <name as the host knows it>` or `ERR <reason>` (name used already or empty after cleaning: the connection is closed), then `TEAM <n> <text>` and `ROSTER name=team;...` whenever something changes, at the end `START` or `CANCEL`, and `GO`. The joiner (`Join-Lobby`) shows address, status, their team and the players; `Esc` leaves.
- **Start from the lobby:** the host sends `START` and keeps the connections; the roster (entries name, team; host first) is saved as the last mapping and becomes `-Mapping`. Everybody prepares: the host builds the extra game, checks the map and writes their start script, every joiner does the same (extra game unless `-NoBuild`, map; a missing map is only fetched after a question) and sends `READY` (`Wait-JoinerGo`). The host waits for all of them (`Wait-LobbyReady`, up to 300 s; if somebody went away or does not come, nothing is started and the others get `CANCEL`), starts `spring.exe`, waits 5 s (the engine listens after about 3 s) and sends `GO`; the joiners then start `spring://<name>@<address>:<port>` and the game begins `-Wait` (15) seconds after the host has loaded.
- **Version and the game of a hosted game (2026-10-27):** everybody who plays together runs **the host's game**: in every hosted game with the lobby the host offers a bundle (`New-HostBundle`: `scenario.txt` of the scenario and the Lua files of the extra game they run, i.e. the gadgets, `bar_rules.lua`, `scenario_briefing.lua` and `shared_start.lua` from the editor or the package), the joiners take it and build their extra game "Level Editor Scenarios <version>" from it (`$gameDirs` = the bundle); the host builds their own from the same bundle. So the version of the gadgets does not have to match, only the **lobby version** `$script:LobbyProtocol` of `lobby.ps1` (the protocol of the lobby and what a joiner does with it; raise it when that changes). The joiner sends `VERSION <protocol>` before `HELLO`; a host with another protocol answers `ERR ... please update the Level Editor manually` and closes the connection (an older joiner sends a hash there and is refused the same way); the host answers after `OK` with `VERSION <protocol>` and the joiner checks it as well. The start menu shows the lobby version in its first line. There is **no update of the editor through the lobby any more** (until 2026-10-27 a joiner could take the host's `.ps1` and `.bat` files): nothing that runs on the computer itself comes from another one; whoever has another version updates the editor by hand. Checked: host and joiner on one computer (the bundle with all 10 files went through, the roster came back), a joiner with lobby version 1 was refused with the message.
- **Play a level at once, bundle, transfer through the lobby (start menu key 6, 2026-10-23):** `scenario_builder.ps1 -Level <name> -BundleDir <folder>` (implies `-Auto`) writes only `scenario.txt` and the gadgets the scenario uses into the folder (no starters, bats, readme, zip, **nothing is written into the level**; checked: the level file is unchanged). `Install-Bundle` (`lobby.ps1`) puts those files into the cache `%LOCALAPPDATA%\BAR-Scenario\Cache\<hash>\` (finished when `complete.txt` is there); the **hash** (SHA-256 over file names and bytes of the allowed files in a fixed order, `Get-BundleHash`) is the id, so the same level gives the same folder on every computer. `start_scenario.ps1 -Bundle` (needs `-EditorDir`; the BAR path is remembered in `%LOCALAPPDATA%\BAR-Scenario\bar_path.txt`): the host gives `-ScenarioDir <cache folder>`; a joiner gives no `-ScenarioDir`, takes the bundle from the lobby (as in every hosted game, see the version above) and then reads `scenario.txt` from the cache. **Who may connect (2026-10-27):** the host's lobby (`Update-LobbyNet`) closes every connection whose address is not this computer or in a network of one of its network cards (`Test-SameLan`, the networks read once by `Get-LocalNets`; the VPN ranges 100.64.0.0/10 and 25.0.0.0/8 count as a whole when a card has an address there), with the note "A connection from ... (outside the local network) was refused." **Protocol (additional lines):** host after `OK` and `VERSION`: `OFFER <hash> <size of the zip>`; joiner with the hash in their cache: `HAVE <hash>`; otherwise they open a **second connection** to the lobby port (so the text lines of the first one never see binary data), sends `FETCH <hash>` and gets `SIZE <n>` and the n bytes of a zip (`New-HostBundle` makes it from the bundle in the cache; the host sends 256 KB per round with `WriteAsync`, so a slow joiner never blocks the lobby), shows the progress (`PROGRESS <percent>` to the host every 5 %: "(loading the scenario: 45 %)" in their box), unpacks, **checks the hash** and says `HAVE <hash>`. The host cannot start until everybody has said `HAVE` ("Anna has not loaded the scenario yet."). **Safety:** no program code comes from another computer. `Expand-BundleZip` accepts only the names of `$script:BundleFiles` (`scenario.txt` and the Lua files of the extra game) (no paths, no `..`, no subfolders, nothing else) and at most 64 MB in total, the hash of the unpacked files must be the offered one, otherwise everything is thrown away, and an id from the network is only used as a folder name if it is 64 capital hex digits. Checked: lobby with a 6 MB bundle: a joiner with an empty cache fetched it (hash equal), one with the bundle in their cache took it without a transfer; zips with `evil.ps1`, `..\scenario.txt` and `sub/scenario.txt` are refused; the whole way with games: split screen of two players where the joiner has an empty cache of their own, the bundle went through the lobby, both games loaded and were in the game (Level8). **The map (2026-10-23):** after the bundle the joiner reads `mapname` from `scenario.txt` and looks whether the map is installed (name in the archive cache of their data folder, or a map from a host in the extra data folder, `Test-MapInstalled`); they say `MAPOK`; otherwise **nothing is asked** (2026-10-23): if they are in the **same network as the host** (`Test-SameLan`: the host's address is on this computer or in the subnet of one of their network cards, address and prefix length from `Get-NetIPAddress`; link-local addresses are ignored) and the host offers the map, they get it from the host over the network (**H**); in every other case they download it from the internet (**D**, `pr-downloader --download-map`, the official map service; `MAPOK` when it ends with exit code 0). Only if that fails the lobby shows them the choice D (again) or H. The host offers their archive only if they find it (`Get-HostMap`: the file of the map in the archive cache of their data folder, a name of letters, digits and `._()- ` ending in `.sd7` or `.sdz`, at most 1 GB; the SHA-256 is made once when the lobby opens): `MAP <size> <sha256> <file>` after `OFFER`. **Official hash (2026-10-23):** the maps of the game have no hash that is stored in the game (`checksum` in `ArchiveCache22.lua` is mostly zeros: the engine fills it only when it needs it), but the file server of BAR, which `pr-downloader` uses, knows MD5 and size of every official map: `GET https://files-cdn.beyondallreason.dev/find?category=map&springname=<name>` gives `[{"filename","springname","md5","size",...}]` (the `<map>.sd7.md5.gz` files next to the maps in `data\maps` hold the same MD5; all 25 of the maps checked match the file). With **H** `Get-OfficialMap` asks that service (timeout 6 s) **before** `MAPREQ`: `official` (md5, size), `unknown` (empty answer: a map of your own) or `offline`. For `official` a host file of another size is refused at once, and `Complete-MapFetch` compares the MD5 of the received file as well (besides the host's SHA-256); a difference throws the file away and the lobby shows "NOT the official map ..." with the choice D. For `unknown` and `offline` only the host's SHA-256 counts and the lobby says so ("not an official map: only the hash of the host is checked" / "official hash not reachable ..."). Checked with a local fake service: matching md5 (accepted, "checked against the official hash"), wrong md5 (thrown away, nothing in the cache), wrong size (refused before the transfer), empty answer and no service (accepted with the note); the real service answered for "Angel Crossing 1.5.1" with the md5 of the local file. **Exact size of every transfer (2026-10-23):** `Start-BundleFetch` gets the size that was offered (`OFFER`, `MAP`) as `$expect`; `Step-BundleFetch` refuses a `SIZE` line with another number ("the host sends another size than they offered") before any byte is read, and reads at most `SIZE` bytes, so a host can never make the joiner take more than they offered (beyond that the upper limits stay: 1 GB map, 64 MB scenario). Checked with a fake host: size 5000 and 10 against 1000 offered refused with 0 bytes read, 1000 accepted, header 1000 followed by 3000 bytes: only 1000 read. With **H** the joiner sends `MAPREQ`; the host does not ask anybody: if the address of the joiner's connection is in their own network (`Test-SameLan`) they answer `MAPYES` at once, otherwise `MAPNO` (the map of a joiner from outside comes from the internet); after `MAPYES` the joiner fetches the file on a second connection (`FETCHMAP <sha256> <their name>`, only for a joiner the host has agreed to, and only that file), shows the progress (`MAPPROGRESS <percent>` to the host: "(loading the map: 45 %)" in their box), checks the hash and puts the file with a small `.mapinfo` file (name of the map, hash) into `%LOCALAPPDATA%\BAR-Scenario\Cache\Maps\maps\`. **The engine finds it there** because `start_scenario.ps1` adds that folder to `SPRING_DATADIR` (the data folder of the player stays untouched). The host cannot start until everybody has said `MAPOK` ("Bob has no map yet."). Option for tests: `-LobbyMapKey D|H` (the joiner takes this answer at once instead of the automatic one). Checked: `Test-SameLan` (127.0.0.1, localhost and an address of the own /24 network: yes; 8.8.8.8 and 10.99.99.99: no); lobby with a 12 MB fake map: Anna (no key, same network) got it from the host without any question (hash equal), Carl "downloaded" it (fake downloader called with the right arguments), Dora had it installed, the game could start; a joiner from outside the network could not be tried on one computer; **with games**: split screen of two players, the joiner's data folder has no map and an empty cache, the map (20 MB `hooked_1.1.sd7`) came through the lobby into their cache, the engine scanned `Cache\Maps\maps`, loaded "Hooked 1.1" from there and both games started (the test ran in two sandbox data folders that see the real engine, game and maps only through links, nothing of the real data folder was written). **The cache and faults (2026-10-23):** what hosts gave lives in `%LOCALAPPDATA%\BAR-Scenario`: `Cache\<hash>` (scenarios), `Cache\Maps\maps` (maps with `.mapinfo`), `Update\<16 digits>` (unpacked updates of older versions, which could update the editor from a host), `Backup\<time>` (files such an update replaced). **Looking after it** (`lobby.ps1`): `Use-CacheItem` marks a scenario or map as used (its time is set when the cache is hit); `Remove-OldCache` runs when the start menu starts (`choose_map.ps1`) and deletes scenarios not used for 30 days, maps not used for 60 days and, oldest first, more maps while the maps are beyond 3 GB, `.part` / `.tmp` leftovers and unpacked updates older than a day and zips of hosts (`bar_bundle_*.zip`, `bar_update_*.zip` of older versions) older than a day in TEMP; **`Backup` is never deleted**. Start menu **key 8** (clean up, see 2.2) lists the scenarios and maps of the cache one by one and deletes the marked ones (what is needed again is fetched again from the host). The zips a host made for the joiners are deleted when their lobby closes (start, cancel or error). **Faults:** a transfer that breaks off (`Step-BundleFetch` sees the closed connection, a wrong answer, a size beyond the limit) ends with the reason shown (scenario: the joiner leaves the lobby with "refused: scenario - error: the host closed the connection"; map: back to the question with the reason) and `Close-Fetch` removes the half-finished file; a failing hash, name or unpacking throws everything away. A joiner who breaks off in the middle of a transfer is removed by the host (the failed write ends the transfer) and the lobby goes on. Checked: pruning with fake ages (an old scenario, an old map with its `.mapinfo`, an old `.part`, an old unpacked update and an old zip in TEMP went; a fresh scenario, a fresh map, an old scenario that had just been used and the backup stayed); a fake host that closes after 1 of 5 MB (clear reason, no file left); a real host with a 30 MB bundle and a joiner who read 1 MB and left (the host removed them, a second joiner got the scenario and the game could start, the zip was removed afterwards). **Not checked:** a full disk, a transfer over a real network (only loopback), two computers.
- **Who plays which team (start script):** every human gets `[playerk]` with the name and the team of their entry (the host `player0`, `Name` and `Team` replaced); a team with a human loses its `[ai]` block, a team without human keeps its AI or gets one (copy of the first AI block: `ShortName`, `Version`, `Name=<ShortName>_<team>`, a new index); `numplayers` = humans, `numusers` = humans + AIs, `hostip`, `hostport`, `GameStartDelay` = `-Wait`. ### 14.2 LAN Play (lobby widget `lan_lobby\lan_lobby.lua`, 2026-10-23/24; checked with two sandbox lobbies on one computer)
**Aim:** play with computers in the same network with the multiplayer battle room of the game, without a server in the cloud and without changing the official game.
- **Way in:** the lobby of the game (Chobby, a Lua program in the game) loads widgets from `data\LuaMenu\Widgets` when the lobby setting `["Chili lobby"].loadLocalWidgets` is true (`data\LuaMenu\Config\IGL_data.lua`; `VFS.RAW_FIRST`). `install_lan_play.ps1` copies the widget (only when it differs), sets that setting (backup of the file first, only when it is not set; refuses while the game or launcher runs because the lobby writes the file when it ends), `-Uninstall` removes it. No file of the game is changed.
- **Small lobby server in the host's widget** (TCP 8453, the text protocol of the official lobby; `localAddress` takes only connections from 127.x, 10.x, 172.16-31.x, 192.168.x, 169.254.x, 100.64-127.x (Tailscale) and 25.x (Hamachi), every other one is closed at once): the lobby of the host connects to it and joins the battle, the lobby of every joiner connects to the host's address. So the official multiplayer room works unchanged. Answered: `LOGIN` (+ `ACCEPTED`, `ADDUSER`, `CLIENTSTATUS`, `BATTLEOPENED`, `JOINEDBATTLE`, `LOGININFOEND`), `PING`, `JOINBATTLE` (+ `REQUESTBATTLESTATUS`, `SETSCRIPTTAGS`, bots), `LEAVEBATTLE`, `MYBATTLESTATUS` (relayed as `CLIENTBATTLESTATUS`), `SAYBATTLE`/`SAYBATTLEEX` (chat), `ADDBOT`/`REMOVEBOT`/`UPDATEBOT`, `WHO` (discovery) and the autohost commands the room sends as chat from the host only: `!map`, `!bSet` (game options), `!cv start`/`!start`. The founder of the battle is the pseudo user "LANHost" (bot). Everything else of the real server (scores, ratings, friends, channels, queues) is not answered.
- **Login:** the lobby does not log in by itself: the widget adds an `OnConnect` listener that sends `Login` (as the login window does).
- **The server address of the lobby is never changed:** the lobby saves its configuration when it ends. An early version changed `serverAddress`/`serverPort` for the LAN game; the lobby saved `127.0.0.1:8453`, and the official games were gone from the normal Multiplayer (repaired in the user's `IGL_data.lua`). Now only the LAN connection (`lobby:Connect(ip, 8453, ...)`) goes to the LAN server; leaving a LAN game disconnects it and does what the settings window does after a server change (`lobby.host = <configured address>`, `WG.LoginWindowHandler.TryLogin()`).
- **Menu entry:** `WG.Chobby.interfaceRoot.GetSingleplayerSubmenu().AddTab("LAN Play", "LAN Play", panel, nil, 1.5)` (rank 1.5: right below Multiplayer; the menu is one column). The config list of the menu is read only once when the lobby is built, so the tab is added to the finished menu and checked every second (the lobby builds its menu again at times). Pitfall found: `WG.Chobby.GetInterfaceRoot()` is the constructor (it builds a new interface); the existing one is `WG.Chobby.interfaceRoot`. `OpenTabByName` skips the entry check of the Skirmish tab.
- **Player name:** `lan_name.txt` (typed on the page, only when it differs) > `Configuration.userName` (the name of the last login, loaded from the lobby settings even when not logged in; e.g. the user's `IGL_data.lua` has it) > `suggestedNameFromSteam` > "Player"; cleaned to letters, digits and `_-[]`, 20 characters; the server refuses a name that is already in the game or is "LANHost".
- **LAN Play page:** a field "Your name", Host a LAN game, Find LAN games, an address field + Join, the list of found games (a click joins), Leave LAN play, Back. While the page is open and the computer neither hosts nor plays a LAN game, it looks for games every few seconds: `WHO` on port 8453 at the addresses x.y.z.1..254 of the own /24 network (the lobby cannot ask for the netmask; 24 connections per frame, 8 s at most); a host does not scan, so it never finds itself; the results replace the list when a scan ends.
- **Start of the game:** `!cv start` makes the autohost "in game" (`CLIENTSTATUS LANHost 65`); every lobby in the battle then connects as for a game on a server (`ConnectToBattle`, script password from the `JOINBATTLE`). The host's lobby runs the game server: its `ConnectToBattle` is wrapped and starts `Spring.Reload` with a script built from the room (game, map, options, players with password, teams, ally teams, colours, sides, AIs, `HostIP=0.0.0.0`, port 8452). After leaving the room the player is on the LAN Play page again; the lobby is rebuilt after a game, so a marker file `lan_return.txt` (written when the widget ends during a LAN game) makes the widget open the LAN Play page then.
- **Sockets of the lobby (checked):** TCP listen and TCP connect to any address are allowed (`TCPAllowListen`/`TCPAllowConnect` = `*`), UDP receive is allowed, UDP send is refused (`UDPAllowConnect` empty; `Spring.SetConfigString` at run time does not help; the config line works but is a change of the user's settings), so everything uses TCP.
- **Copilot (2026-10-25):** a second floating button for the host (next to Custom Scenario): numbers per human inside an ally team, the same number = one player together; kept as `c.slot` of the connection on the server of the widget, `effectiveSlots` (default = place in the team, a chosen number overrides it, so the one who takes the number of another joins them and the other keeps their), `nextSlot`, `sharedGroups` (pure functions between `-- SHARE-BEGIN` and `-- SHARE-END`, loaded by the test of the Level Editor), `cycleSlot` (chat line to the room); `buildScript` makes one team of the start script for every "ally:number" group of humans, puts the host first (player 0) and uses `StartPosType=0` when a group exists (a game widget starts such a game: `shared_start.lua`, see `lan_lobby\README.md`). The test hook `widget.DebugShare` lets the Level Editor test load the file in a stub environment.
- **Custom Scenario:** the host has a floating button at the top left (only while the LAN room is open). Scenarios come from `data\LevelEditorScenarios` (junction; the lobby cannot read folders outside the game folder): `VFS.SubDirs`, `scenario.txt`. A choice sets the map (`UPDATEBATTLEINFO`), tells the clients through the game option `lanscenario`, and forces the ally team of every player to the one of the scenario's first player (status codes decoded and encoded as the lobby does: ready bit 1, team bits 2-5 and msb 2-5, ally bits 6-9 and msb 12-15, player bit 10, handicap bits 11-15 and msb 0-1, sync msb 6-7, side msb 8-11; the corrected `CLIENTBATTLESTATUS` goes to everybody, also the sender; spectators stay). The room still shows its team controls, the server undoes a change. `!map` (an official map) drops the scenario. The start script is the scenario's own with `__GAMETYPE__` = "Level Editor Scenarios 1", `__PLAYERNAME__` = the host, every other human as a further player in the team of player 0 (`Password` from the lobby, spectators as spectators), `hostip=0.0.0.0`, `hostport=8452`, `numplayers`/`numusers` corrected. A joiner without the game "Level Editor Scenarios 1" gets a message instead of a failed start.
- **Same extra game on every computer (checked 2026-10-24):** with the scenario the host announces version, hash and size of their own extra game (the one named in `games\LevelEditorScenarios.txt`; game option `lansync` = `<version>|<hash>|<size>`, hash by `VFS.CalculateHash`). A joiner who has that version already (`VFS.HasArchive("Level Editor Scenarios <version>")`) uses it; one who has not is asked (a confirmation popup: the file holds gadgets of the scenarios, only from a host you trust); on yes they open a second connection to the host's lobby port and sends `FETCHGAME <hash>`; the host answers (after the usual greeting line) `SIZE <n>` and the bytes, 64 KB per frame. The joiner takes at most the announced size (at most 4 MB), checks size and hash, writes `games\LevelEditorScenarios_<version>.sdz.part` and renames it to `games\LevelEditorScenarios_<version>.sdz` (a file of its own: their own version is never replaced; a version that is not 8 hex digits is refused), calls `VFS.ScanAllDirs()` and the game is there. The host's start script names the host's version. A host without a version in `lansync` (an older editor) gets the message "please update the Level Editor manually". The start of the game waits for it (`ConnectToBattle` is postponed until the file is loaded); declined or failed means: no start for them, with a message. Checked in the sandbox: the joiner had no extra game, got 17647 bytes, the file equals the host's byte for byte, both engines loaded the extra game with the Capture the Flag gadget (then still with the fixed name "Level Editor Scenarios 1"). Not exercised: declining, a failing transfer, the postponed start (the transfer was faster than the start).
- **Version check of the lobby and the game widget (2026-10-28):** at every join (scenario or official map) the host answers the command `LANVER` (before the login, like `COPILOT`; a game option would be shown as a text line in the room and push the buttons away) with `<lobby>|<shared>|<number>|<date time>` where the last two are `LAN_VERSION` of `lan_lobby.lua` (a version number that is raised with every change, with date and time; the message says who is newer) and the first two are (the first 8 characters of `VFS.CalculateHash` of `LuaMenu/Widgets/lan_lobby.lua` and of `LuaUI/Widgets/shared_start.lua`, carriage returns removed, `-` when the file is missing). The joiner compares them with his own files once per join and logs `version check: same ...` or `version check: DIFFERENT, host ..., own ...`; on a difference he gets exactly one message window (`bigPopup`, 640x320, with OK; the lobby's `InformationPopup` was too small) that names the file that differs and asks to update the Level Editor on all computers. A host that sends no `lanver` (an older lobby) gives the same one warning after 4 s. Only Lua files are compared and sent, no scripts. Nothing is replaced: the lobby widget is never fetched from the network. The extra game of a scenario is checked as before (`lansync`) and now logs `scenario game check: same version as the host ... no transfer needed` or `... different`.
- **Findings behind the LAN Play checks (2026-10-28):** (1) a game option set by the widget is shown by the room as a text line and pushed the buttons of the room away: checks and transfers use short connections to the server of the widget instead (`LANVER`, `MAPINFO`, `FETCHMAP`, `FETCHGAME`, `COPILOT`, `WHO`). (2) The lobby has no HTTP client (LuaSocket without TLS; the file servers answer plain HTTP with a redirect to HTTPS): it downloads through `WG.DownloadHandler` (the launcher or `VFS.DownloadArchive`), which checks the official checksum itself, and a widget can not fetch a checksum alone: the setup (PowerShell) saves the official list of map md5 (`data\games\LevelEditorMapHashes.txt`) and the joiner compares with it; a map that is not in it is taken on the host's word after a question. (3) The lobby starts the online download of a missing map by itself when it joins a room; the widget holds that call back until it knows where the map comes from. (4b) The speed of one connection is bounded by the frame rate times the buffer of the socket (about 64 KB a frame): 1.7 MB/s in the tests, not the network; the map is therefore fetched on 8 connections (about 100 Mbit). The length of a file as the lobby's Lua counts it (`#`, `seek`) was 3 bytes more than the file (69333408 against 69333405; the content and its md5 are right), so the map is cut in blocks and not in bytes. (4) `read("*a")` and `seek` of a file in the lobby return 3 bytes more than the file has; the widget reads in 64 KB chunks. (5) Messages longer than a line need their own window (`bigPopup`, 640x360): the lobby's `InformationPopup` is too small. (6) Each game instance needs 8-10 GB of RAM: LAN tests run with host plus one joiner. Details of the tests: `test-data\TESTING.md`.
- **Maps over LAN Play (2026-10-28):** a joiner who has not got the map of the room (`VFS.HasArchive`, the name from `battles[1].mapName`) asks the host at once on a short connection (the lobby would start its own online download of the map as soon as it knows the map of the room: the widget holds that call of `WG.DownloadHandler.QueueDownload` back until it is known where the map comes from, drops it when the map comes from the host and lets it through when it does not, after 30 s at the latest): `MAPINFO <name>` is answered with `<size>|<md5 base64>|<file>` or `none` (the host serves only the map of its room, only a `.sd7` / `.sdz` file of `maps\`, at most 300 MB; size and md5 are worked out once, reading the file in 64 KB chunks). When the md5 of the host is in the official list the file is fetched from the host at once (no online traffic); otherwise the player gets a window: **From the host** (over the LAN, the checksum is only the host's word and cannot be compared with the official one from here; the md5 is shown) or **Online** (the lobby's own download, which `pr-downloader` checks against the official checksum). A Lua widget cannot make an HTTPS call (LuaSocket has no TLS; the file servers redirect http to https), so the Level Editor setup (`install_editor.ps1`, full run; `Update-MapHashes` in `shared\bar_common.ps1`) fetches the official list `https://maps-metadata.beyondallreason.dev/latest/live_maps.validated.json` (about 60 KB, 227 maps, `springName` / `fileName` / `md5`) and saves it as `data\games\LevelEditorMapHashes.txt` (`# etag=`, `# fetched=`, then `<spring name>|<md5>`); the next setup asks with `If-None-Match` and gets a 304 when nothing changed; offline or on any error the old list stays and nothing fails. The joiner looks the map up in this file: **the md5 of the host equals the official one** = no question (the received file is hashed anyway and must give that md5); **different** = the window warns (the host or the list is out of date: run `install_editor.bat` on both, or the map is changed); **not in the list or no list** (own maps, `hooked_1.1`, offline setup) = the window as before, the md5 is only the host's word. On yes the file is cut into blocks of 64 KB and fetched on 8 connections at once (`MAP_STREAMS`, all to the one port 8453): every connection sends `FETCHMAP <first block> <count> <name>`, the host answers (after the usual greeting line) `BLOCKS <first> <count>`, the blocks (up to 4 MB a frame) and closes; the joiner writes every run at its place in `maps\<file>.part`. A Lua widget moves about one buffer (64 KB) per connection and frame, so one connection gave 1.7 MB/s (69 MB in 41 s) and 8 give about 10 MB/s (69 MB in 7 s, on one computer); size and md5 are checked, then it is renamed and `VFS.ScanAllDirs()` makes the game know it. The start of the game waits for it (`ConnectToBattle` is postponed). Test keys: `noOnline=1` in `lanlobby_cfg.txt` (the lobby cannot download), tool `lan_test.ps1 -NoMap`. Checked (sandbox, joiner with an empty maps folder, Full Metal Plate 1.7, 69 MB): the md5 of the received file is the official `21028d58...`, the game started after the load. **Not checked:** the window (autoAccept in the test), the answer Online, declining, a failing transfer, a host that has the map as a folder (`.sdd`, not served).
- **Checked** (sandbox: two real lobbies with the widget, `lanlobby_cfg.txt` in the write dir drives them: `auto`, `name`, `map`, `players`, `ip`, `openTab`, `clickFirst`, `leaveAfter`, `scenario`): join and scan, both on the server, room, chat message sent, map and start through the room's own Start call, two players loaded the game (`Player ... finished loading and is now ingame`); leaving the room returns to the LAN page; the normal-start lobby is unchanged (nothing appears when the widget is not installed; with it the tab is the only change); the menu button position measured (Multiplayer y 171, LAN Play y 245, Skirmish y 319); scenario `level8` chosen: map Hooked 1.1, ally team 0, start script with both humans in team 0, game "Level Editor Scenarios 1", both logs "Loaded synced gadget: Capture the Flag".

### 14.3 What LAN Play sends and how it is checked

- **Who talks to whom.** Port 8453 (TCP) is the small server in the lobby widget of the host; port 8452 is the game itself. The server takes connections from local addresses only (see "How it works"). Every joiner's lobby speaks the usual lobby protocol (login, battle room, chat, map name, options, teams) with that server. Besides that, short connections ask single questions before any login: `WHO` (the search for games), `COPILOT` (the numbers of the humans), `LANVER` (the version), `MAPINFO <name>`, `FETCHGAME <hash>` and `FETCHMAP <first> <count> <name>` (files, see below). Nothing is shown to the players as a game option that is not meant to be read (the room would print it as a line and push its buttons away).
- **Which files are sent: two kinds, never more.** (1) The extra game of the scenarios (`LevelEditorScenarios_<version>.sdz`: only Lua files, at most 4 MB). (2) The file of the map of the room (`.sd7` / `.sdz` from the `maps` folder, at most 300 MB). No PowerShell, no batch file and never the lobby widget itself or any other program: updates of the Level Editor are done by the players (git pull, or copy the folder and run `install_editor.bat`).
- **Version check (nothing is sent, only compared).** A joiner asks the host with `LANVER` for `<hash of lan_lobby.lua>|<hash of shared_start.lua>|<version number>|<date time>` and compares it with his own. The same: no message. Different: exactly one window with the version of the host and of the joiner one below the other, who is newer, and how to update. The game can still be played; it is a warning, not a lock.
- **The extra game of a scenario.** The host announces version, hash and size (`lansync`); a joiner who has that version uses it; one who has not is asked (a window: only from a host you trust), fetches it with `FETCHGAME <hash>`, and keeps it as a file of its own after the check of size and hash; his own version is never replaced.
- **The map of the room.** (1) The lobby of the joiner would start its own online download of a missing map; the widget holds that call back until it knows where the map comes from. (2) The joiner asks the host `MAPINFO <name>` and gets size, md5 and file name of the map of the room (the host answers only for the map of its room and only for a `.sd7` / `.sdz` file in `maps`). (3) He looks the map up in the official list of map checksums that the Level Editor setup saved (`data/games/LevelEditorMapHashes.txt`, fetched online when the editor is installed, only when it changed). **Same md5**: the map is fetched from the host at once, without a question and without online traffic. **Other md5**: a window warns (host or list out of date, or a changed map) and asks. **Not in the list or no list** (own maps, offline setup): a window asks and says that the md5 is only the host's word. In the window the player chooses **From the host** or **Online** (the lobby's own download, which the engine checks against the official checksum). (4) The file is fetched in blocks of 64 KB on 8 connections at once (`FETCHMAP`), written into `maps/<file>.part`, and its size and md5 are checked against the announcement; only then it is renamed and the game scans its folders. A failed check deletes the part file and lets the lobby download the map online. The start of the game waits for the map.
- **What stays trust.** A map that is not in the official list and the extra game of a scenario are taken on the word of the host after a question: the checks (size, hash, md5) prove that the file is the one the host announced, not that the host is honest. The Lua gadgets of a scenario game run in the game of every player, so use LAN Play with hosts you trust.

## 15. Known limitations and open points

- The look of the menu was mostly only checked with mocks; acceptance happens in the game.
- LAN Play (14.2): open points: the scenario's AI is not shown in the room, the place and look of the Custom Scenario button, the scan assumes a /24 network, a joiner without the map, a check that both computers have the same version of the LAN Play widget itself (the console lobby compares its lobby version; the scenario game comes from the host in both), the map download only by the lobby's own mechanism, two computers.
- **Menu tests (2026-10-27):** all side buttons (O, I, AI, P, G, TD, CF, RF) were switched pairwise in a sandbox game (56 pairs, each time exactly the chosen page active; `test-data\tools\zz_menu.lua`, method in `test-data\TESTING.md`). `G` does not close on a second click (leave with `P`). Esc closes the help board; the Place button closes the I, O and AI pages.
- **No BluePrinter update at the editor start (2026-10-27):** `ensure_installed.ps1` only keeps the extra game of the editor up to date. An earlier version also copied the BluePrinter files; that coupling was removed again, because the BluePrinter has its own `start_blueprinter.bat` that installs and updates it. The editor does not need the installed BluePrinter (its shared code is packed into the `.sdz`).
- **Lua limit of 200 local variables per function:** the main part of `lvl_level_editor.lua` has 195 top-level `local`s (checked 2026-10-28 after the Arena page, the Tower Defense page is in `led_td.lua` now; the other Lua files have at most 57). New features should go into a module (like `led_ctf.lua`) or into a table instead of new top-level locals; the AI page keeps its constants in the one table `TeamAi`. A load error shows as `Failed to load: lvl_level_editor.lua` in `infolog.txt`.
- **No AI can be given to a team during the game (checked 2026-10-27, game with `cheat 1`):** the engine commands work only half: `aikill <team>` removes the AI of a team at once (`isAI` turns false), but `aicontrol <team> <AI> <version>` is refused by the server (`[GameServer::ProcessPacket][NETMSG_AI_CREATED] player 0 not allowed to use /aicontrol`), for team 1 and for team 2, also with cheating on; without a version the command only prints its help line. BAR has no Lua call to start a Skirmish AI. So the AI of a team is chosen **before the start** (`[ai]` in the start script: the editor writes NullAI for team 1; scenarios take the AI of their scenario info). The AI page (button AI) writes the choice into the level for the next start.
- The fallback `gl.UnitShape` of the 3D preview is not finally confirmed in the real game (`/led_ghost` helps with the diagnosis).
- Damage per shot uses the default armor class and ignores special effects (area damage, slowing).
