# Specification: Level Editor

Status: 2026-10-22. This document describes the current state; how things were checked is at the end.

Level editor for Beyond All Reason (BAR): place units and buildings on the map with the mouse, create and place blueprints (layouts), save and load levels, build Tower Defense or Capture the Flag levels, forbid units for the player. The result is a `unitloadout` list for scenarios.
Shared code: `..\shared\editor_common.lua` (see `..\shared\SPECIFICATION.md`). Sister project: `..\BluePrinter\SPECIFICATION.md`.

## 1. Goals and basic rules
- **Language of the interface:** all visible texts in the game are English (widget, gadget messages, tooltips, help board, help topics, chat messages), because the project is meant to be international. Console menus, scripts, comments and these documents are English as well. Game texts stay without umlauts. File and folder names are English as well (`scenario`, `scenarios`, `template`, `Start Scenario.bat`, `_trash`).
- The official game stays unchanged. The editor is an **extra game** (`data\games\LevelEditorMod.sdz`, name "Level Editor") that builds on the official BAR, plus a start file and folders for levels and blueprints.
- In editor mode (game option `leveleditor=1`) **no /cheat and no /globallos** are needed (the editor switches on the cheat mode and the god mode itself, see 3.1). Everything is free and finished instantly. Legion, the extra pack and release candidates are switched on. The unit limit is raised (`maxunits=32000`).
- Source code and texts contain no reference to persons or private matters. Player name in the start script: "Player".
- Structure: **widget** `lvl_level_editor.lua` (controls, menu, saving/loading), **gadget** `unit_level_editor.lua` (places, deletes, blows up, build mode, orders for units of other teams), shared code `editor_common.lua` and `bar_rules.lua`; the pages and games: `td_waves.lua` (11a), `ctf_game.lua` and `led_ctf.lua` (11b), `unit_restrictions.lua` and `led_restrictions.lua` (11c). There is **no backward compatibility**: old fields in level files are dropped when loading (`knownFields`, section 10), old names and formats are not read.
- After every change to the widget, gadget or shared code, or a BAR update, the extra game has to be built again. `start_level_editor.bat` does it: before every start it calls `ensure_installed.ps1`, which compares the stamp `data\games\LevelEditorMod.stamp` (SHA-256 over the game version and the packed files, `Get-EditorStamp` in `editor_stamp.ps1`, written by `install_editor.ps1` after building) with the current files and runs `install_editor.ps1 -Quick` (builds only the extra game and the stamp; does not rewrite the start file, because the batch file is running) when the stamp or the extra game is missing or differs. While a game is running (`spring` process) the update is skipped with a note. `install_editor.bat` still does the whole setup (start file, shortcut).

## 2. Installation and start

### 2.1 Setup (`install_editor.bat` → `scripts\install_editor.ps1`; all scripts live in `scripts\`, `$root` = the main folder is their parent, the repository folder their grandparent)
- Searches BAR on all fixed drives (e.g. `C:\Games`, `D:\Games`, Program Files, `%LOCALAPPDATA%\Programs`), finds the engine and game version, builds `LevelEditorMod.sdz` with `modinfo.lua` (name "Level Editor", short "LevelEd", game "LevelEditorMod", depends on the installed BAR), the gadgets (`unit_level_editor`, `td_waves`, `ctf_game`, `unit_restrictions`), the widget (with `enabled = true`) and in `luaui/Include`: `editor_common.lua`, `bar_rules.lua`, `led_ctf.lua`, `led_restrictions.lua`, `led_help_texts.lua`. The list of the files is `$EditorFiles` / `$SharedFiles` in `editor_stamp.ps1`. After building it writes the stamp `data\games\LevelEditorMod.stamp`; with `-Quick` (called by `ensure_installed.ps1`) it stops there and does not rewrite the start file or the shortcut.
- The widget is switched on in the extra game by replacing only the first `enabled = false,` of `lvl_level_editor.lua` (the line in `GetInfo`); the same text also appears in the code as data (default of the tower defense settings), which must stay untouched.
- Replaces the extra game of a previous setup, creates junctions: `data\LevelEditor` → `levels`, `data\LevelEditorBlueprints` → `blueprints`, creates `blueprints\_trash` (trash), writes `start_level_editor.bat` and the desktop shortcut "BAR Level Editor" (no other shortcut; the BAR launcher creates its own). It does not check for or download any map; the maps are chosen in the start menu.
- Requirements on the computer: BAR installed and the launcher started once. The folder `shared` must lie next to `LevelEditor`.
- **Removing (`uninstall_editor.bat` → `uninstall_editor.ps1`):** finds BAR like the setup, lists what is there (`data\games\LevelEditorMod.sdz`, the junctions `data\LevelEditor` and `data\LevelEditorBlueprints`, desktop shortcut "BAR Level Editor", `start_level_editor.bat`, `editor_script_installed.txt`, `Last Map.txt` and `Online Maps Cache.json` in `%LOCALAPPDATA%\BAR-Level-Editor`), asks (`-Yes` skips) and removes it. Junctions are only unhooked with `rmdir` (the content of `levels` and `blueprints` stays); if one of the places is a real folder it is skipped. `-WithSettings` additionally deletes `LuaUI\Config\LevelEditorRecent.lua` and `LevelEditorUI.lua`. The desktop shortcut "Beyond All Reason" and the folder itself stay.

### 2.2 Start menu (`scripts\choose_map.ps1`)
At the start always a menu in the console. Controls: arrow up/down (Home/End) choose the item, Enter runs it, a digit key jumps straight to it, Esc cancels; grayed-out items are skipped, the first possible one is preselected (normally 0). Checked with real key presses in a console:
- **Key 0** (most common action): continue the last saved map (the state `_last`, saved every 2 minutes and when leaving).
- **Map preview:** the lists of keys 1, 2 and 3 show the picture of the highlighted map on the right (window wide enough: the list keeps 55 characters, the picture gets at most 64 columns). The pictures are not downloaded: the lobby package of the game (`byar-chobby`) contains `LuaMenu/configs/gameConfig/byar/minimapThumbnail/<map name with _>.png` for about 770 maps. `map_preview.ps1` reads the newest `data\packages\*.sdp` that lists them (gzip; per file name length, lower case name, 16 bytes md5, crc, size), takes the file `data\pool\<md5 byte 1>\<rest>.gz`, unpacks it into memory and draws it with the half block character (two pixels per character, 24-bit colour; the console mode for escape sequences is switched on; 16 colours as fallback). Nothing is stored on disk: the index (name to md5) is built at the start (about 0.2 s), a picture is unpacked when its map is highlighted and kept in memory for the next visit. Under the picture a line with size, players and terrain is shown (data of the filters below). Without package, thumbnail or enough width nothing ("no preview") is shown and the menu works as before. Test: `choose_map.ps1 -Data <BAR\data> -TestPreview "Map name"`.
- **Map filters (key 1):** a row above the search line with three filters `Size`, `Players` and `Terrain` (all `all` at the start). `Tab` / `Shift+Tab` choose a filter (highlighted), `Left` / `Right` change its value, typing still searches, the counter counts the maps that pass all filters and the search. Values: size `XS` to `XXXL` (the classes of the lobby: area = `Width` x `Height` against the quantiles 0.08, 0.24, 0.40, 0.60, 0.78, 0.92 of all maps), players `2`, `3-4`, `5-6`, `7-8`, `9-12`, `13-15`, `16`, `17+`, terrain `Flat`, `Hills`, `Water` and the specials `Metal`, `Lava`, `Air`, `Asymmetrical` (a map has the special of its entry plus Flat, Hills and Water as flags). The data are in `configs/gameConfig/byar/mapDetails.lua` of the same lobby package (`Get-MapDetail` in `map_preview.ps1`, parsed once, about 50 ms); a map that is not in the file is hidden as soon as a filter is set. Under the picture a line shows e.g. `12 x 12 (S), 4 players, Air, Hills`. The other fields of the file (author, description, start boxes, certification) are not used. The levels lists have no filters.
- **Key 1:** new level – map selection with search while typing. The list contains **all BAR maps from the internet** (cached in `Online Maps Cache.json`, see section 12), missing maps are only downloaded **after** the selection, offline only installed maps appear. The list shows only the name with its version (no file name, no note about missing maps; the title counts the maps and the installed ones).
- **Key 2:** load an existing level (list from `levels`, with search). Every line shows name, map, number of units and features ("195 units, 94 features"; `Read-Level` counts the entries before and after `featureloadout` separately), date and a note if the map is missing. The same format is shown for the last state in the main menu. A single level is treated as a list (`@(Get-Levels)`, `@($items)`), otherwise PowerShell counted the property `Count` of the level object. The editor starts on the saved map and sets up the units automatically (`levels\_autoload.txt`).
- **Key 3:** create a scenario package (ZIP) from a level (only if levels exist): level selection as with key 2, then `scenario\scenario_builder.ps1 -Level name -Auto -AskName` runs (at the end of the questions, so after the values: a list "Scenario info stored in the level" (title, author, summary, briefing, roles, tech, AI, win condition, resources, grace period, ID, Tower Defense), then the title is asked with `AskLine`, Enter keeps it; a changed title proposes the ID `Get-Slug <title>`, otherwise the saved ID stays; then `Confirm-ScenarioId`: shows the target `scenarios\<id>`, Enter takes the name or another one is typed (`Get-Slug`, written into the level block as `sid`), if the folder or zip exists: y = overwrite, n = another name, c = cancel) (PowerShell, no Python needed; see 14) without further questions, the info comes from the level (edited in the editor with button I, defaults apply if it is missing); then back to the menu. The info is changed in the editor.
- **Key 4:** start a built scenario (only if `scenario\scenarios` holds folders with a `scenario.txt`): list of the scenarios with ID, title (first line of the `README.txt`), map, a note "Tower Defense" if the folder has `td_waves.lua`, and date (`Get-Scenarios`, `-TestScenarios` lists them), search while typing; Enter opens a second list (Single player / Host a game for others in the same network / Join a game hosted by another player / Split screen; Esc goes back to the scenarios) and then runs the **current** `scenario\template\start_scenario.ps1 -BarPath <BAR folder> -ScenarioDir <folder of the scenario> -EditorDir <LevelEditor folder>` (not the copy in the package, see section 14), with `-HostGame -Lobby` for Host, `-Join -Lobby` for Join (the same as `Host Game.bat` / `Join Game.bat`) and with the games of the split screen started from the menu itself (section 14.1) (finds the engine and game, builds the extra game of a Tower Defense scenario, downloads a missing map after a question, starts the game); when the game ends the menu comes back (the next scenario can be tried at once; the other keys still end the menu with exit code 0 to start the editor).
- **Key 5:** upgrade a built scenario package (only if there are built scenarios): the same list of scenarios as key 4; Enter finds the level the scenario came from (`Find-ScenarioLevel`: the level whose saved scenario info has `"sid"` = the ID of the scenario, otherwise the level whose name gives that ID: lowercase letters and digits) and runs `scenario\scenario_builder.ps1 -Level <level> -Auto` (the saved info, no questions, the folder and the ZIP of that ID are replaced), then "Continue with any key" and back to the menu; without a matching level a message says to build it again with key 3. Checked on a copy of the folders (no real package touched): `level002` -> `level_002`, `level8` -> `Level8`, the rebuilt package has the current starter, lobby, stub and gadgets.
- The map list must stay smooth: the filtered list is cached, only changed lines are redrawn, a backlog of key presses is discarded, resizing the window is handled (no slowdown, not even at the end of the list).
- Writes `editor_script_installed.txt` (start script for the engine, player "Player", game "Level Editor 1", game options including `maxunits=32000`).

### 2.3 At the start of the game
- Shortly after the start (frame 6) `widget:Update` sends `cheat 1` and `godmode 3` once, so units of every team can be selected and commanded (3.1).
- At the start only the commander stands there. All mobile **builders of every faction** are created by the user when needed with Ctrl+D at the mouse pointer (markers ARMADA, CORTEX, LEGION), grouped by kind, on **reachable spots** (check by grid and `TestMoveOrder`; no water, no cut-off mountains). Do not use: `Spring.RequestPath` (leads to a crash).
- The menu is visible at the start, with the Units tab first.

## 3. Controls in the game

### 3.1 Keys (let the mouse point at the map)

| Key | Effect |
|---|---|
| `[` and `]` (BAR keys "build rotation", `buildfacing inc/dec`) | rotates the unit or blueprint stamp by 90 degrees (south, east, north, west) while one is armed; BAR gets the key as well |
| Del | delete the selection, without a selection the unit, wreck or feature at the mouse pointer (radius 64–80; unit has priority; not over the menu); on the Tower Defense page first the waypoint under the mouse pointer (64 Elmo) |
| Ctrl+B | blow up (normal death with explosion, wreck stays), selection or unit at the mouse pointer |
| Ctrl+C / Ctrl+V | copy / paste (selection, otherwise the unit at the mouse pointer; pasting centered at the mouse pointer with team, rotation, height; any number of times; the clipboard lasts until quitting) |
| Ctrl+X | cut (copy + delete) |
| Ctrl+Z / Ctrl+Y | undo / redo the last action (place, blueprint, paste, groups, delete, blow up, move, rotate, mirror, team change, features) |
| Ctrl+S | save the level (`saveCurrentLevel`: under the current name, otherwise as a new `level_NNN`; the same function as "Save" in the settings page) |
| Ctrl+D | create the builders of all factions again at the mouse pointer for the current team (the team chosen on the left) |
| D | delete rectangle on/off (see below; the same as the DR button) |
| M | cycle the maze mode: off → dragon teeth (`<faction>drag`) → walls (`armfort`/`corfort`/`legforti`) → off (faction as chosen on the Generate page; also the Maze sub-tab of the Generate tab). Then drag a rectangle with the left mouse button held down: on release a random, fully connected maze appears (depth-first search, `Shared.mazeWalls`; no cycle). Tile 16 Elmo (footprint of the units), corridors 2, 4, 8, 10 or 12 tiles = 32, 64, 128, 160 or 192 Elmo wide, the same widths as the corridors of Tower Defense (default 4 = 64 Elmo; `gen.mazePath`, buttons "Corridor width" on the Maze sub-tab; checked in the real game: 32 Elmo gave 16 x 16 cells and 863 pieces, 128 Elmo 5 x 5 cells and 308 pieces in an area of 800 Elmo), walls 1 tile; entrance top left, exit bottom right. The rectangle is cut to whole cells (preview frame green, red = too small, at least 11 × 11 tiles) and capped at about 12000 wall units (area up to about 190 × 190 tiles). Team and neutral switch as when placing; one step for Ctrl+Z; right click ends, and so does arming anything else (unit, blueprint or feature; `widget:Update` checks that). Checked in the real game: 927 dragon teeth placed, Ctrl+Z removes all; mock test: all corridors reachable from the entrance, exit reachable, exactly cells−1 passages |
| Alt+Z / Alt+X (also with Shift) | build spacing when dragging larger / smaller (BAR default, only with an armed unit stamp) |
| Right click | ends every mode (stamp of a unit, feature or blueprint, delete, maze, generate, area attack, Tower Defense drawing and picking) and every drag in progress (row, selection frame, Alt + drag move) and returns to the default mode; with no mode active it is left to the game: the order for the selected units (a left click on the ground clears the selection); starting a Tower Defense or Capture the Flag test calls `gen.disarmAll()` (ends stamp, delete, maze, generate, area attack, picking and every drag); works anywhere on the screen, also over the menu and the buttons (`gen.cancelModes`) |
| Left click and hold, move (armed unit or feature) | paint: one is placed after every footprint of movement (section 7); W decides about occupied spots |
| Shift + left click drag / Shift+Alt + drag | drag a row / rectangle of units, features or blueprints (section 7) |
| Alt + left click and hold over a waypoint, the spawn point or the goal (Tower Defense), or over a collection or flag point (Capture the Flag), also with the page closed | move it, like Alt + drag moves units and features (`td.dragAt`, `td.wpDrag`, `ctf.grab`; section 11a) |
| Left click or drag a rectangle | select units of every team (god mode, see below) |
| Arrow keys (up/down/left/right) | move the selected units by one grid step (`grid`, default 16); up = north (−z); a held key repeats; without a selection, with Shift/Ctrl/Alt or with the help open the key stays free for the camera (`ARROW_STEP`, key codes 273–276, sends `led|move|dx|dz|ids`). Checked in the real game: two units +16 / −16 |
| Alt + drag (on a selected unit) | move the selection |

**Selecting units of every team:** BAR only lets you select your own units, unless the god mode is on. `widget:Update` sends `cheat 1` and `godmode 3` once (frame 6 or later, only with the game option `leveleditor`); checked: then `Spring.SelectUnitArray` takes units of other teams (21 commands in the menu; `godmode 1` = allied teams only, `2` = enemies only, `3` = all, other values switch it off). The engine sends no orders for units of other teams (checked: the order of the command menu and `Spring.GiveOrder` have no effect), so `widget:CommandNotify` forwards every order for selected units of other teams as `led|order|cmdID|options|params|ids` and the gadget gives it with `Spring.GiveOrderToUnit` (checked with the message: units of team 0 and team 2 drove; that the engine calls `CommandNotify` for orders of the command menu is not checked here). Delete, blow up, `assign`, copy and saving a blueprint use the selection of the game; without a selection delete/blow up still act on the unit at the mouse pointer (any team). There is no selection of its own and no Ctrl selection any more.

Notes:
- **Ctrl shortcuts:** `ctrlEdit(key, shift, isRepeat)` is called by the action handler `gridmenu_key` (in front of the build menu) and by `widget:KeyPress` when Ctrl is held without Alt; search fields and chat take precedence. Checked in the game with a chosen commander (builder, build menu active): Ctrl+C reports "units copied", Ctrl+V starts the blueprint stamp, Ctrl+X copies and deletes, Ctrl+Z works and Ctrl+Y redoes (also Ctrl+Shift+Z); Ctrl+B blows up (wrecks stay; Ctrl+B is neither used in the editor nor in the BAR default keys, Ctrl+D creates the builders). The keys were sent to the game window with real key presses (German layout: Z and Y swapped). The BAR default keybind `Ctrl+v = pastetext` (chat) stays untouched because the editor consumes the key first.
- **Key conflict with the BAR build menu:** BAR uses Z X C V / A S D F (with "Any+") for the build menu and eats Ctrl letters as soon as a builder or factory is selected (`actionHandler:KeyAction` runs before `widget:KeyPress`). Solution: widget layer −1, own handler for `gridmenu_key` that passes Ctrl (without Alt) + C/V/X/Z/Y/B/S on to `ctrlEdit` (a held key does not repeat).
- There are still no Alt-letter bindings that override BAR default keys.

### 3.2 Chat commands (prefix `/led_`)
- `help [topic]`: short version or the topics `start`, `keys`, `place`, `units`, `blueprint`, `save`, `team`, `edit`, `features`, `search`, `scenario`, `build`.
- The grid is no longer a chat command: it is a setting (button O, see 4.4). Unit and team are only chosen through the menu and the team buttons (0 = you/Armada, 1 = enemy/Cortex).
- **Team assignment** (click on a team button with selected units; the chat command `assign` no longer exists). **Technique:** the handover runs as a takeover (`Spring.TransferUnit(id, team, false)`, "capture"), because several BAR rules block gifts to enemies/teams without a player when no cheat is on. The message "N units changed team" comes from the game and only counts units that really changed; the message when sending says "… sent".
- `clear`: clears the map (units; undoable).
- `ghost [gl|wg|auto]`: state and mode of the 3D preview.
- Removed (the functions run through keys, buttons and the menu; the Generate tab replaces the group commands, Create and the tiles the blueprint commands, Ctrl+S and the settings page save/load, Ctrl+D builders): `units`, `buildings`, `turrets`, `air`, `ships`, `blueprint`, `save`, `load`, `builders`, `place`, `delete`, `boom`, `undo`, `redo`, `copy`, `paste`, `rotl`, `rotr`, `mirror`, `rotate`, `assign`, `unit`, `team`, `bp_quick`, `bp_next`, `bp_prev`, `bp_place`, `bp_menu`, `spacing` (and the sub-command `blueprint menu`).

## 4. Menu (at the right screen edge)

### 4.1 Structure
- Position: right edge, top edge at 94 % of the screen height (below the menu bar of the game at the top), bottom edge at most at 12 % (for settings, scenario, Generate and Tower Defense 5 %); the collapsed menu sits at the same height. Minimum width 560·S, at most half the screen width.
- **Movable:** the title row is the handle (`panelPress`: left button starts, right click resets; `MouseMove` / `MouseRelease` end it). `basePanelRect()` is the place at the right edge, `panelRect()` = `basePanelRect()` moved by the offset of `panelMover` (`Shared.newPanelMover`) and kept on the screen (room `2·HB + 12` for the team strip on the left and `HB + 2·PAD` for the button column on the right, at least 40·S above the bottom edge). Everything (strip, button column, content, 3D preview) is built from `panelRect()` and moves along. The offset is stored as a fraction of the screen size in the config data (`widget:GetConfigData` / `SetConfigData`).
- Header: above everything a **title row** with the text "Level Editor" at the top left (like "BluePrinter" in the other widget; `titleH()`, 44·S high, not shown when collapsed). The two main menus **Place** and **Generate** are the buttons P and G of the button column (`kind = "top"`, `side = true`), not a row of the menu any more (`headerRowCount` has one row less). **Place:** row 2 is **one search field** for all four lists (the `search` table in the widget: `searchSet(q)` copies the query into `uGrid`, `fGrid`, `bpGrid` and `fav`; Recent filters both its blueprint rows and its unit symbols, `fav:matchCount()`; the sub-tab labels show the number of matches while a query is active; the field and its X button turn reddish while it contains a text), row 3 the sub-tabs **Recent | Units | Features | Blueprints** (`kind = "mode"`, font 22·S), below them the rows of the chosen tab (faction, group and tech for Units; the feature kinds for Features; the button **Create** for Blueprints, which saves the selection as a new blueprint). A click on a faction, group, tech or feature-kind button ends the search. **Generate:** the page has its own sub-tabs Units | Maze (see 7). The buttons V, O, I, ?, P, G, TD, XL, XR, XC, FX, FD stand in the button column at the far right (see 7), the buttons W, DL, DR, DC, L, R, S, N, the teams and G in the strip at the left (see 5).
- The menu scales with the screen height: factor = `ui_scale` (BAR setting, fine control) times height / 2160 (the dimensions are designed for 4K; Full HD is half as big, 1900x1000 about 0.46), limited to 0.3 to 3. Checked in the game at 1900x1000.
- The faction buttons (Units tab and both Generate sub-tabs) carry the faction symbol on the left (see `shared`). The faction, group and tech buttons of the Units tab have no tooltips; all other buttons have (see 7).
- Above the blueprint grid there is a hint text in font 24·S: "Click a tile, drag = sort", in stamp mode "Left click places, right click ends".

### 4.2 Blueprint view
- **Search and scrollbar (Units, Features and Blueprints, also in BluePrinter):** the search matches every word of the query against code, name and description (`M.matches`, `M.unitSearchText`, `M.featureSearchText`, `M.blueprintSearchText` = blueprint name plus code, name and description of its units). A scrollbar (`M.scrollbarDraw/Press/Move/Release`, 24·S wide at the right edge of the list area, needs `grid.scroll` and `grid:maxScroll(rect)`) is drawn when the list is longer than the area; drag the thumb or click the track.
- **Filtered view:** the blueprint grid shows a filtered view of `lib.list`; indices handed to the host (`onSelect`, `selected`) are always library indices. Dragging to sort is disabled while a search is active. In the Level Editor the query comes from the global search; the grid's own search row (`g:filterRects`) is only used by the BluePrinter.
See `..\shared\SPECIFICATION.md` section 8 (tiles with unit pictures as thumbnails, the grid grows from top to bottom up to the set size, dragging to sort, x to delete with trash, double click to rename, mouse wheel 234·S per notch, that is three times the speed plus 30 %). Specific to the editor:
- The label shows "N units" and below it the total cost of the blueprint (`M` metal in light blue, `E` energy in yellow; from the shared grid).
- Left click on the map places the chosen blueprint (with a frame preview in team colors and 3D models), right click ends stamp mode.
- Blueprints are placed with **the team chosen on the left**. Air units keep their height, landed air units stay landed. The layout is not checked for passability.
- The order is in `blueprints\_order.txt` (and `_index.txt`), the trash in `blueprints\_trash`.
- The list reads the folder `LevelEditorBlueprints/` (junction to `blueprints`).

### 4.3 Units view
See `..\shared\SPECIFICATION.md` section 9 (faction, group, tech, pictures, sorting, info lines with name, code, seconds per shot and damage, description, metal and energy cost). Specific to the editor:
- Click a unit → stamp mode for this unit; left click on the map places it (gadget message `led|place|<name>|<team>|<x>|<z>|<facing>`), right click ends. The team is the one chosen on the left, the grid comes from the settings (`cfg.v.grid`).
- Preview: blue outline (footprint, swapped for odd rotations) and the 3D model at the mouse pointer.
- All groups are available (buildings, bots, vehicles, hover, air, ships).
- **Restriction marks:** the grid is created with the option `restrict` (the functions of `rst`, section 11c): a small X on every symbol and on the faction, group and tech buttons forbids units for the player in the game; `shared` section 9.4b describes the drawing and the derived state of the buttons. A click on such an X does not arm a unit.
- The hint text is **above the menu** (24·S): "Click a unit, then place it on the map" or in stamp mode "Left click places, right click ends, [ and ] rotate", above it in smaller font (20·S) "Shift = row, Shift+Alt = rectangle, Shift+Mouse wheel = spacing (N)".
- Info lines below the menu (see `shared`, section 9.4): name (code) with `(<s> s/shot - <n> damage)` (for anti-air with the suffix "air"), description, metal and energy, for buildings additionally the explosion with damage and radius.

### 4.4 Settings (button **O**)
- Columns and rows for the blueprint view (`bpCols`, `bpRows`) and the units view (`uCols`, `uRows`), default 3 and 4, limits 1–6 and 1–8, stored in `LuaUI\Config\LevelEditorUI.lua` (game folder), immediately on every change.
- **Placing block:** the **grid** (1 = free, 4, 8, 16, 32, 64 Elmo; default 16; replaces the removed chat command `/led_grid`; used for placing, moving, arrow keys and snapping) and the **unit limit** (500 to 32000 in steps; default 32000). The values move along fixed lists (`cfg.steps`, `M.newConfig` supports `steps[key]`). The unit limit is written into the level file as `unitlimit = N,` (next to `mapsize`) and read again when a level is loaded; the scenario builder uses it as the game option `maxunits` of the package. The editor game itself always starts with `maxunits=32000` (it cannot be changed while the game runs).

## 5. Strip at the left of the menu (`teamRects`)
- Top to bottom, with a free slot (one button high) between the groups: **W**, a free slot, **DL, DR, DC**, a free slot, **L, R, S** (only while units are selected; then a free slot), **N**, one button per team, **G**. With a collapsed menu the strip is gone.
- **W** (Write, `writeOn`, default on, green when on, grey when off): decides what happens when something is placed where something already stands: on = it is overwritten (what is in the way is deleted), off = nothing is placed on an occupied spot (see 7, Painting). It is not stored in the level.
- **DL, DR, DC** (red, `del` = "line" | "rect" | "circle"): the delete modes (see 7); the active one is marked with a white frame.
- **L, R, S** (blue): rotate the selection left or right, mirror it (see 6).
- Team buttons: number = team number, team color, without Gaia (the **G** button at the bottom is the Gaia team; its tooltip names the unit limit of 500 that the engine fixes for Gaia, read with `Spring.GetTeamMaxUnits`). ## 6. Editing the selection, moving, redo
- **Edit buttons** (only visible while units are selected) stand in the strip at the left (see 5), above N and the teams: `L` rotates the selection 90° to the left, `R` to the right, `S` mirrors left-right, each around the center of the selection. The gadget sets the units up again (team, neutral flag, height stay), replaces their IDs in the undo stack and reports the new IDs through the game rules parameters `led_newids` / `led_newids_n`; the widget selects them again. At most 2000 units per operation (rotating, mirroring, moving).
- **Moving:** hold Alt, click a selected unit (radius 48 Elmo), drag, release; the offset is rounded to the grid (`led|move|dx|dz|ids`). Preview: green frames at the target. A click outside a selected unit drags the selection rectangle as before.
- **Undo / redo (history in the gadget):** `Ctrl+Z`, `Ctrl+Y` (the chat commands `led_undo` / `led_redo` no longer exist). The gadget keeps a history of steps (at most 300); a step is an action of the user (a row, a blueprint, a delete of the selection …). Before every action the widget sends `led|step`; everything up to the next `led|step` belongs to this step. All messages run in order through the queue (`led()`) so nothing overtakes a not yet sent part of a row. Operations of a step: `add` (unit placed), `del` (deleted or blown up; when blowing up the wrecks that appear are noted through `gadget:FeatureCreated` and removed on undo), `swap` (moved, rotated, mirrored: state before/after), `team` (team change), `fadd` / `fdel` (feature placed / deleted). Units are created anew on undo and redo and get new IDs; `replaceId` then swaps the ID in all steps, and before every access it is checked whether the ID still belongs to a unit of this type. A new action empties redo. Not in the history: loading a level (`led|load` without suffix, `led|loadfeature`), `led|clear` (empties the history), creating builders (Ctrl+D). Blueprints and paste send `led|load|…|1` (suffix 1 = remember in the history). Checked in the real game: placing, blowing up (wreck gone and back), deleting, team change; in the mock additionally moving, rotating, features, a row as one step and long chains with changing IDs.
- **Selection info:** at the top center the number of selected units, up to four types with count and the sum of metal and energy are shown.

## 9. Blueprints

- Saving: Create writes the selected units (all kinds, with team, neutral flag and the indestructible flag of the Tower Defense walls) as a layout, positions relative to the center of the selection, `rot` = heading, `h` = height above ground. After saving: re-read the list, choose the blueprint, add it to the index.
- Loading/placing: through the menu. Placing runs through a load queue (50 units per update) and the gadget.
- Managing: sorting (`_order.txt`), deleting into the trash (never for good), renaming (copy under the new name, original into the trash).

## 10. Levels

- Ctrl+S writes `levels\<name>.lua`: all units (position, height, team, neutral, rotation, `indestructible = true` where set) **and all features** (wrecks, trees, rocks). The file states which game options (e.g. extra pack) must be on in the main game.
- Loading a level (level list in the settings) clears the map (except the builder rows) and sets the level up again (features are replaced if the file contains any). `/led_clear` only clears units.
- Autosave: every 120 seconds and when leaving as `_last`, only when editing is allowed, the load queue is empty and from game frame 100. It saves to `_last`, not to the named level: the named level only changes with Ctrl+S or "Save" in the settings page. `_last` is the state at that moment: units destroyed in a fight in the meantime are gone (wrecks and heaps remain as features). Save under a name of your own before experimenting.
- **Save as new:** a new level made from another one (the level loaded last) takes over the scenario info of that level, but not its title and ID: they are made from the new name (`level_002` → title "Level 002", ID `level002`), so the scenario package of the new level is not built into the folder of the other one (found when a Tower Defense level made from Level8 was built into `scenarios\level8`). Autosaves (`_last`, `_beforeplay`) keep the block unchanged. Checked in the real game.
- The sections `towerdefense = { ... }` (settings of the tower defense page, 11a), `capture = { ... }` (Capture the Flag, 11b) and `restrictions = { banned = { ... } }` (11c) are written when the page has been used or the list is not empty; they follow the scenario block in the file. When loading only the known fields of each section are taken over (`knownFields`: the keys of the defaults, plus `spawn` / `goal`); a missing field gets its default, everything else is dropped and not saved again.
- Air units in the air are loaded in the air (with the saved height, otherwise cruise height) and stay in flight mode, air units saved on the ground are loaded landed.
- The gadget places factories anywhere (checked on a test map, steep slopes, water, overlaps).

## 11. Gadget (`unit_level_editor.lua`)

- **No gravestone when a unit is taken away:** moving, rotating, mirroring, deleting and undoing set the unit rules parameter `remove_decorations = 1` before `Spring.DestroyUnit` (`destroyUnit`); the game's gadget `unit_tombstones.lua` leaves a tombstone feature (e.g. `armstone`) next to every destroyed commander unless that parameter is 1. A real explosion (`boom`) keeps wreck and tombstone. Checked in the sandbox: the move of a commander left one `armstone` before, none after.

- Messages through `Spring.SendLuaRulesMsg` with the prefix `led|`: `step`, `place`, `delete`, `deleteids`, `boomids`, `boom`, `undo`, `redo`, `clear`, `clearrect`, `clearcircle`, `clearline`, `clearids` (units `u<id>` and features `f<id>` that are in the way), `fix` (indestructible on / off for buildings in a rectangle), `tdroute` (undo step for the Tower Defense route), `ctfpts` (undo step for the Capture the Flag points), `order` (an order of the player for units of other teams: `led|order|cmdID|options|params|ids`, `Spring.GiveOrderToUnit` in the gadget, see 3.1), `load`, `generate`, `generaterect`, `builders`, `assign`, `feature`, `loadfeature`, `clearfeatures`, `move`, `xform`.
- Only works with cheat or in editor mode; otherwise the message "Cheat mode is off: please type /cheat".
- `GG.LevelEditor` offers the same functions for tests; `GG.LevelEditorSpawnBuilders(x, z, team)` creates the builders (manually without markers, in the team of the call).
- Handovers (`assign`) by takeover, message with the actual count.
- **Loaded stockpile:** units that can stockpile (nuclear silos, anti-nuke ...) get `max(10, queued)` missiles through `Spring.SetUnitStockpile` when the editor places them (`place`, `generate`; also after undo/redo and when a level is loaded). The call only works in a later frame than `CreateUnit`, so the IDs wait in `pendingStockpile` and `gadget:GameFrame` fills them (checked in the game: armsilo and corsilo have 10 missiles at once, other units are not touched). The stockpile is not part of the level file; a scenario starts with empty silos.
- **Resurrected units: Hold Position.** When a unit is resurrected (the builder is executing the `RESURRECT` command at that moment), it gets the movement mode "hold position" (`CMD.MOVE_STATE` 0) so it does not run off. In the editor the gadget does this (`gadget:UnitCreated` with `builderID`, only in editor mode). Checked in the real game: a Rector resurrects a wreck, the new unit has `movestate = 0`, a normally placed one `movestate = 1`.
- **Unit limit in the editor:** the start script (`choose_map.ps1`) sets the game option `maxunits=32000` (engine upper limit, divided over the teams; checked in the game: 15750 per team with two teams plus Gaia).

## 11a. Tower Defense (button **TD**, gadget `td_waves.lua`)

Waves of enemy land units walk from a spawn point through waypoints to a goal; the player builds towers next to the route. The level author builds corridors, sets the route and the waves and says what the player may build. The page can start a test in the editor (**Start test**); the scenario builder packs it for the official game (section 14).

- **Widget:** the page is the table `td` (everything is a field of it, the file is at the limit of 200 locals): `td.layout` builds buttons and labels (also used by `td.press`, `td.height`, `DebugLayout`), `td.draw` / `td.drawTiles` draw, `td.press`, `td.key`, `td.text`, `td.wheel` handle input, `td.drawWorld` (also with the page closed, as `ctf.drawWorld`, as soon as something is set; only the highlight of the point under the mouse needs the open page) draws spawn point (green circle), goal (red circle of 120 Elmo), the waypoints and the line spawn → waypoints → goal (only to look at), `td.hud` the status at the top. The page is wider (780·S) than the others and excludes the other pages like Generate does. The title row reads "Level Editor - Tower Defense" while Tower Defense is on or the page is open.
- **Data:** own section `towerdefense` of the level file (a Lua table next to `unitloadout`; written by `saveLevel` through `td.lua`, read by `load_level` into `td.data`; the scenario block is not touched; the scenario builder reads it, `Read-TowerDefense`): `enabled`, `width` (tiles of 16 Elmo: 2, 4, 8 (default), 10, 12), `leaks`, `spawn` and `goal` (`{x, z}`), `waypoints` (ordered list of `{x, z}`), `economy` and `fog` (booleans, default on; missing counts as on), `waves` (list of `{fac, kind, tech, count, gap, hp}`; `fac` a string of the chosen factions e.g. `armcor`, `tech` e.g. `12`, `kind` e.g. `vb` = vehicles and bots, `h` = hovercraft; older values (`arm`, 1, `any`/`bot`/`vehicle`) are read as well; `td.chosen`, `td.toggleChoice`: one choice per group always stays on; `gap` seconds after the previous wave, default 0 for wave 1; `hp` percent). Without the section the page shows the defaults and nothing is written. An older drawn `path` is not supported any more.
- **Page, top to bottom:** checkbox `tdon` (green when on); **Walls**: material `tdmat` (Teeth / Walls, only a choice) and below it the button `tddraw` Single; **Corridor (walls on both sides)**: `tddraw` Line | Free in one row; **Corridor width**: `tdwidth`; **Route**: `Spawn X | Waypoint X | Goal X`; **Enemies allowed through** (- / number / +); green line; **Waves** (- / number / +) and the table (wave number, three faction toggles with symbols, T1–T3, V B H, count, gap, HP %; 8 rows, mouse wheel scrolls); green line; **Restrictions**: toggles `tdeconomy` and `tdfog`, faction buttons `tdfac`, category buttons `tdcat`, tech buttons `tdtech` (each with a red X `tdtechx`), the tiles; red message (`td.notice`, 6 s); at the very bottom the button `tdplay`. All buttons have tooltips (the earlier hint texts at the bottom are gone).
- **Corridor:** `td.pick` = "corridor" | "waypoint" | "spawn" | "goal", `td.mode` = "single" | "line" | "free"; right click ends the mode (`td.cancel`; a drawn line with at least two points is built first). The mode stays on after every corridor. *Single* (`td.startSingle`, `td.sdrag`, `td.sample`): a press places one wall piece on the 16 Elmo grid, while the button is held a piece in every cell the pointer passes (cells in between included, no cell twice per stroke), one undo step per stroke. *Line*: clicks collect points (`td.pts`), right click or Enter builds. *Free*: press starts `td.stroke`, `td.sample` adds a point whenever the mouse moved 48 Elmo, release builds. `td.finishDraw` simplifies the line (`td.simplify`, Douglas-Peucker, 24 Elmo) and calls `td.buildWalls`: `td.wallSpots` every 8 Elmo along both offset lines (offset = half corridor + 8, snapped to the grid, no piece inside the corridor of another section) plus an arc of pieces (radius = offset, every 8 Elmo) around every bend on the outer side, so corners are closed (simulated with 400 random two-segment paths: open corners 349 → 9, only hairpins tighter than the corridor is wide are left). The pieces go through `placeQueue` as one undo step with `led|place|...|1`; what is in the way is handled by W (see 7). A corridor does not touch spawn point, goal and waypoints.
- **Route:** *Spawn* / *Goal* (click, then click the map; X deletes it). *Waypoint* (`td.pick` = "waypoint"): every click adds a point via `td.addWaypoint` (onto a drawn line between two points of the route — spawn point, waypoints, goal; within 48 Elmo, projection inside the segment — it is inserted there, otherwise behind the nearest point of the route), the mode stays on, right click ends; the X next to it deletes all waypoints (its tooltip names Del for single ones). Ctrl + left mouse button over a waypoint (`td.waypointAt`, 64 Elmo) sets `td.wpDrag`: `td.sample` moves the point to the mouse position while the button is held, `widget:MouseRelease` ends it (`td.endWpDrag`, one undo step). Del (`key == 127`, `td.deleteWaypoint`) removes the waypoint under the mouse pointer. `td.route()` is the waypoint list in its order; the payload field `path` carries it, the gadget walks spawn → path → goal.
- **Undo of the route:** `td.routeState()` writes spawn point, goal and waypoints as text ("sx,sz;gx,gz;x,z/x,z"); every change (`td.commit(before)`) sends `led|step` and `led|tdroute|before|after`; the gadget records the op `tdroute` in its history (with the unit steps, so Ctrl+Z / Ctrl+Y keep the order) and on undo / redo publishes the state through the game rules parameters `led_tdroute` and `led_tdroute_n`, `td.pollRoute` (every `widget:Update`) applies it. Checked in the real game: four changes, three undos and three redos went back and forth in the right order.
- **Start test / Stop / Reset:** button `tdplay` (`td.toggle`; green "Start test", red "Stop" while running, green "Reset" when won or lost): with no state (`tdState` empty) it needs spawn point and goal (else the red message and a chat message, nothing starts), saves the level as `_beforeplay` (shown in the level list like `_last`) and sends `tdw|start|<payload>`; with a state it sends `tdw|stop` and loads `_beforeplay` again through `load_level` (`currentLevel` stays as it was), so destroyed towers, wave units and the removed commander are back / gone. The gadget marks the wave units with the public unit rules parameter `tdwave`; `saveLevel` skips them (also the autosave). At the start the gadget destroys the commanders of the player team (the builders are placed by the level). The payload fields 14 `metal` and 15 `energy` (start resources of the level, `scenario.metal` / `.energy`, default 1000) are applied three frames later (the removed commander takes its storage with it only then) by `GameFrame` in the editor (`EDITOR_MODE`): resources and storage of the player (storage at least 1000). The editor gadget does not refill that team while `tdState` is not empty (rules parameters `tdState`, `tdPlayer`); after Stop the refill (1e9 / 1e10) starts again within half a second. Checked in the real game: 1000 / 1000 during the test, 1e9 / 1e10 after Stop. In a finished scenario the resources come from its game options. Checked in the real game: a tower deleted during the test is back after Stop; 1 commander before, 0 during, 1 after Stop.
- **Restrictions:** towers can always be built. `economy` on: also economy structures (unitgroup energy / metal or `extractsMetal`: extractors, solar, wind, geothermal, fusion, storage, converters); `fog` on: also radars (`radarDistance > 0`); both also decide which categories the list offers (`td.cats()`: Towers, Economy, Radars). `td.class(ud)` / the gadget's `buildClass` sort structures (factories: none; tower = armed and not unitgroup explo). The tiles (`td.turrets(fac, tech, cat)`, from `Shared.buildUnitCache`, land only, built once in `td.tcache`; 8 per row, at most 4 rows, mouse wheel scrolls, `td.tscroll`): picture `#unitDefID`, hover shows the 3D model (`Shared.drawUnitPreview`) and name / cost below the panel; a click arms placing like the unit list of the Place tab (`td.armUnit`; painting, Ctrl, Alt, Shift work); the corner button `tdban` (red X, `rst.toggle`) forbids the tower (dimmed, big red X), `tdtechx` forbids all units of a tech level like the Place menu (`rst.setBanned(uGrid:namesOf("tech", t), ...)`, button tinted red while all are forbidden); both write the restrictions of the level (section 11c). The editor itself can always place everything.
- **Enforcement (gadget):** payload `enemyTeam;playerTeam;spawnX;spawnZ;goalX;goalZ;leaks;path;waves;restrict;fog;metal;energy` (see the head of `td_waves.lua`; `restrict` = "economy" when the Economy toggle is on, else "towers"), by message `tdw|start|…` or the game option `tdconfig`. While a game runs `gadget:AllowCommand` refuses build orders of the player team (cmdID < 0) for structures outside the allowed classes (radars only with fog); the forbidden units and tech levels are refused by the gadget `unit_restrictions.lua` (section 11c); units from factories are not restricted; the message reads "Not allowed in this level: name (reason)". In a finished scenario (`not EDITOR_MODE`) the gadget calls `Spring.SetGlobalLos(allyTeam, not fog)` at the start; the editor keeps its global view (it needs it to save). Checked in the real game: banned towers are marked, a build order for `armllt` banned / `armsolar` with towers only / `armpb` with tech 2 banned was refused with the message, `armllt` T1 was not refused when only T2 was banned. Not tested: that an allowed tower is queued (a scripted order was not queued in the control run either).
- **Gadget (waves):** `tdw|stop`; waves start `gap` seconds after the previous one (the first after the start); the units of a wave appear one after the other (every 12 frames) at the spawn point, get `MOVE` orders along the path to the goal, health scaled by `hp`. Unit choice: random land unit (mobile, armed, no builder, ship or aircraft; bots and vehicles by the movement class `ud.moveDef.name`: bot*, otherwise not hover) among all that fit one of the chosen factions, tech levels and types; units without any weapon that can hit the ground (`WeaponDefs[..].canAttackGround`, pure anti-air such as `armjeth`, `coraak`) are left out. A kill pays the metal and energy cost of the unit to the player team (player = first team with role Player, enemy = first with role Enemy, otherwise team 1). An enemy within 120 Elmo of the goal is removed and counts as through; more than `leaks` = lost, all waves gone and no enemy alive = won (outside the editor the gadget ends the game with `Spring.GameOver`). Status in the game rules parameters `tdState`, `tdWave`, `tdWaves`, `tdLeaks`, `tdMaxLeaks`, `tdKilled`, `tdAlive`.
- **Tech levels:** BAR files some Epic units under T1/T2 (Epic Grunt, Epic Goblin, Epic Mosquito, Epic Skater); `techLevel(ud)` (in `editor_common.lua`, both gadgets and the scenario briefing) counts every unit with the name "Epic ..." or an epic movement class as T3 (checked in the real game: none of them is left in T1 or T2).
- **Indestructible pieces:** `led|place` has a ninth field (1) and `led|load` an eleventh; the gadget (`setIndestructible`) puts the unit into the table `GG.Indestructible` (shared with `td_waves.lua`) and sets the public unit rules parameter `indestructible`; `td_waves.lua` protects the units in it: `gadget:UnitPreDamaged` returns 0 (also crushing and any weapon), `UnitDestroyed` removes the entry. The corridor pieces get it; the buttons FX / FD set and remove it for the buildings in a rectangle (see 7). They can also not be taken apart by units: `AllowCommand` (registered for reclaim, capture and self destruction) refuses a reclaim or capture order on one such unit and a self destruction order of it, `AllowUnitBuildStep` refuses every reclaiming step (area reclaim included); all in `td_waves.lua` (the table `GG.Indestructible`, filled by the editor gadget when it sets the flag and by the scenario start from `tdfixed`; the editor loads `td_waves.lua` too). Checked in the real game, editor and scenario: a builder reclaimed an unflagged wall, but a single order and an area order on flagged walls changed nothing. Deleting or blowing them up with the editor still works (it is not damage). The flag is part of the snapshot (undo, redo, rotate, mirror keep it), of blueprints and of the clipboard (`indestructible = true` in the file; placing sends the eleventh field); `saveLevel` writes `indestructible = true` into the unit line and `load_level` sends it again. In a Tower Defense scenario the gadget `td_waves.lua` protects the flagged units again (game option `tdfixed`, see 14). Checked in the real game: a flagged wall piece survived the fire of two turrets while an unflagged unit next to it died; the flag came back after saving and loading; FX marked 3 buildings, FD took it from one, rotating kept it, a pasted copy and a saved blueprint carried it.
- **Checked in the real game (overview):** waves on a route with waypoints, kills, won, Start test without spawn point / goal shows the message, X buttons, the settings come back after saving and loading the level.
- **Scenario:** a level with Tower Defense on becomes a Tower Defense scenario (section 14): everything on this page is packed.
- **Open:** the loss condition (more through than allowed) is only read, not tested in the game; balance of the pay and the strength.

## 11b. Capture the Flag (button **CF**, gadget `ctf_game.lua`, page `led_ctf.lua`)

Flags lie at flag points; units pick them up, carry them to the collection point of their team and are paid (metal per second for every flag that lies at the collection point, nothing else: no one-time reward, no experience); the delivered flag stays at the collection point (`f.parked`, `unpark`), where units of other teams take it (`check`); in mode "own" the owner of the flag only brings it back to its flag point; the pod is not blocking (`SetUnitBlocking`: a blocking pod pushed the carrier into a zigzag); a team that holds enough flags at the same time wins (`g.score` = flags held): `finish` then blows up the units of every team that is not on the winner's side (`blowUp`, flags and collection points stay; checked in the game: 8 units of the other team, 1 left = its own collection point), the same as when the last team standing wins. A destroyed carrier drops the flag where it died (it goes back only after `returnTime` seconds if that is above 0). Humans only: nothing in the code makes a computer opponent play it. Idea and open questions: issue 1 of the repository.

- **Widget part:** `led_ctf.lua` is a Lua file that returns a function; the widget loads it (`VFS.Include("luaui/Include/led_ctf.lua")`, packed by `install_editor.ps1`) and calls it with a `host` table (the services of the widget: `Shared`, `S()`, `say`, `canEdit`, `team()`, `serialize` (= `td.lua`), `disarm` (ends the other modes), `beforePlay` / `afterPlay` (save and restore `_beforeplay`)). It returns the page `ctf` (the widget keeps only one local variable for it; the file is at the limit of 200 locals): `ctf.layout(rect)` (buttons, labels, height, also `DebugLayout`'s eighth value), `ctf.draw`, `ctf.press`, `ctf.key`, `ctf.text`, `ctf.click(x, z)` (left click on the map in the pick mode `ctf.pick` = "home" | "flag"), `ctf.cancel`, `ctf.deleteAt` (Del), `ctf.grab` / `ctf.sample` / `ctf.endDrag` (Alt + drag moves a point (like units and features; also with the page closed)), `ctf.state` / `ctf.applyState` / `ctf.commit` / `ctf.poll` (undo, see below), `ctf.pointAt`, `ctf.drawWorld` (rings), `ctf.toggle` (test), `ctf.payload`. The widget hooks are the same places as for `td`: header button (`kind = "ctf"`, `sideTop(9)`, the area attacks and FX / FD moved down one slot), size of the panel, title ("Level Editor - Capture the Flag"), drawing, press, map click and right click, text and key input, Del, mouse wheel, world drawing, pick mode ended when another mode starts, save and load of the level.
- **Exclusive with Tower Defense:** ticking `ctfon` calls `host.excludeTd()`, ticking `tdon` sets `ctf.data.enabled = false` (with a message); both can be off.
- **Data:** own section `capture` of the level file (written by `saveLevel` through `td.lua`, read by `load_level` into `ctf.data`): `enabled`, `amount` (metal, 0 to 99999), `score` (flags to win, 0 to 99, 0 = never), `radius` (Elmo, 10 to 2000), `returnTime` (seconds, 0 to 3600, default 0 = the dropped flag stays), `speed` (top speed of a flag carrier in Elmo per second, 0 to 2000, default 50, 0 = no limit), `visible` (boolean, default true), `homes` (`{ team, x, z }`, as many as you like per team), `flags` (`{ team, x, z }`, team -1 = neutral = Gaia chosen in the strip, otherwise the team chosen in the strip); neutral flags are units of the Gaia team, which has its own unit limit (checked in the editor game: `Spring.GetTeamMaxUnits` is 500 for Gaia, 15750 for the other teams with `maxunits` 32000), so with very many Gaia units in the level a neutral flag could not be created.
- **Page, top to bottom:** checkbox `ctfon` (at the very top, the switch of the mode); Places: `ctfhome` + X, `ctfflag` + X and two lines of what is placed; the box `ctfvisible`; Income: the field `amount`; fields `score`, `radius`, `speed`, `returnTime` (`ctfedit`: click, type digits, Enter accepts, Esc cancels, limits as above); at the bottom `ctfplay`.
- **Gadget:** payload `amount;radius;score;returnTime;speed;homes;flags;visible` (homes and flags as `team,x,z/team,x,z`; visible "1" or "0"), by message `ctf|start|...` (`ctf|stop`; only with cheats or in editor mode) or the game option `ctfconfig` (base64url, decoded by `decode64` of `bar_rules.lua`; the game starts at frame 30). Flags are real units (`lootboxsilver`, the silver pod of the scavengers), collection points are `lootboxnano_t1_var1`, both created neutral, with no selection, always visible (`Spring.SetUnitAlwaysVisible`, flags only when the option `visible` is on: checked with the global line of sight off, four flags in the corners, two in sight of the player's units: with the option off only those two are seen, with it on all four), indestructible (the gadget has its own protection: no damage, no reclaim, capture or self destruction) and with the unit rules parameter `tdwave` (so the editor does not save them) and frozen with `Spring.MoveCtrl.Enable` (the pod is a drifting unit with the speed 0.03, which would be its only movement); in mode "own" a flag belongs to a team (created for that team: its color), otherwise it is created for the Gaia team. Every 5 frames: a flag that nobody carries is taken by the first mobile unit (not a building, not a Gaia unit, not a unit being destroyed) within the radius; in mode "own" only by a unit of another ally team, a unit of the owner's ally team brings a dropped flag home. A carried flag follows its carrier every frame (`SetUnitPosition` to the position plus one frame of the carrier's speed: measured with the view positions in the game, one frame halves the lag, more makes it worse; the rest is the interpolation of the drawing; air units and units in a transporter work, the position of a loaded unit is the one of its transporter). A carrier within the radius of the collection point of its own team delivers: *once* = `AddTeamResource(team, "metal", amount)` and the flag goes back to its flag point; *income* = the flag stays at the collection point and every second every team gets `amount` times the number of flags it holds. **Carrier:** while a unit carries a flag its weapons have the range 0 (`disarm` saves the ranges in the flag record, `rearm` puts them back on delivery or when the game stops). A destroyed carrier (`UnitDestroyed`) leaves the flag where the carrier died (`f.dropped`); it goes back to its flag point after `returnTime` seconds only when that is above 0. **Lost team:** with mode "own", when all flags of a team are parked (`f.parked`) at collection points, `eliminate(team)` blows up all its units (`Spring.DestroyUnit(id, true)`, not the flags and collection points) and every 30 frames what the team built since; when only one team of the collection points is left it wins ("last one standing"). With reward "once" the flags always return, so no team is lost that way. A team with `score` delivered flags wins (`Spring.GameOver` of its ally team in a finished scenario, only a message in the editor).
- **Undo of the points:** like the route of Tower Defense: `ctf.state()` writes collection points and flag points as text ("t,x,z/t,x,z;t,x,z/..."; "-" for none), every change (`ctf.commit(before)`: click, Del, X buttons, end of a drag) sends `led|step` and `led|ctfpts|before|after`; the editor gadget records the op `ctfpts` (with the unit steps, so Ctrl+Z / Ctrl+Y keep the order) and hands the state of an undo or redo back through the game rules parameters `led_ctfpts` / `led_ctfpts_n`, which `ctf.poll()` reads every frame. The settings (buttons, fields) are not part of the undo.
- **Carrier speed:** `disarm` (a unit takes a flag) saves `ud.speed` in the flag record and calls `Spring.SetUnitCOBValue(unitID, COB.MAX_SPEED, speed * 65536 / 30)` when the unit is faster than `cfg.speed`; `rearm` (delivery, lost flag, stop) sets `ud.speed * 65536 / 30` again. Checked in the game (an `armflash`, `ud.speed` 101): 50.7 Elmo/s while carrying with the cap 50, 101.0 after the delivery; the value is Elmo per second * 65536 / 30 (a first test with `MoveCtrl.SetGroundMoveTypeData("maxSpeed")` had no effect on the speed, `SetUnitCOBValue` has). Not checked: air units and hovercraft.
- **Minimap:** the pods get `Spring.SetUnitNoMinimap` (no engine icon); the unsynced part draws a square per flag in the color of its owner (light grey: neutral) and a ring of the capture radius around every collection point over the minimap (`drawMiniMap`, from `DrawScreenPost` with `Spring.GetMiniMapGeometry`: BAR's minimap does not call `DrawInMiniMap` of gadgets, and `DrawScreen` comes before the minimap). The flag ids come in `ctfFlagIds` ("id:owner,..."); with the option `visible` off a flag is only drawn when `GetUnitLosState` says los or radar (spectators see all). Checked in the game with fog: four flags in the corners, with the option on all four, off only the two next to the player's units.
- **Display:** game rules parameters `ctfState` ("", "running", "won by team N"), `ctfScore<team>`, `ctfTarget`, `ctfTeams`, `ctfOut` (lost teams), `ctfRadius`, `ctfHomes`, `ctfSpots`; the unsynced part of the gadget draws the rings (`DrawWorldPreUnit`) and the score line (`DrawScreen`), so a finished scenario needs no widget.
- **Scenario:** a level with Capture the Flag on becomes a scenario with the settings in the game option `ctfconfig` (teams renumbered like the units, a team with a collection point but without units is added); `ctf_game.lua` and `bar_rules.lua` are in the package and the starter builds them into the small extra game (section 14). The computer opponents get no AI (NullAI), the win condition is "no end" (the gadget decides). A level with both modes on is refused by the script (they exclude each other in the editor).
- **No capture of the pods and towers (found 2026-10-23):** BAR's gadget `pve_supply_drops.lua` treats every unit with "lootbox" in its name (the flags `lootboxsilver` and the collection points `lootboxnano_t1_var1`) as a lootbox: every 30 frames `NearbyCapture` adds capture progress for the units of other teams within 1024 Elmo (commander about 0.027 per tick) and at 1 hands the unit to the nearest enemy (`Spring.TransferUnit`); a commander next to a collection point took it within about 40 s (checked in the sandbox with the old code: the bar rose from 0.10 to 0.88, then team 0's tower belonged to team 1 and the other way round). **Main fix (2026-10-23): the extra game replaces that gadget.** The files of an extra game come before those of the game it builds on, so `luarules/gadgets/pve_supply_drops.lua` in the extra game (the text of `scripts\pve_supply_drops_stub.lua`: only `return false`) keeps the gadget of the game from being loaded: nothing is captured, no bar appears, no flicker (checked in the sandbox with the code from before the fix: the capture progress stayed 0.00 for 1200 frames with a commander next to a collection point, and the log has no "supply drops" line). The stub is packed by `install_editor.ps1` into `LevelEditorMod.sdz` (it is in `$EditorFiles` of `editor_stamp.ps1`, so the extra game is rebuilt by itself) and by `start_scenario.ps1` into `TowerDefenseScenario.sdz` of a scenario with Capture the Flag (the builder copies the stub into the package, the editor's menu takes the current one from `scripts\`). What is lost: the dropping of lootboxes by the game option `lootboxes` (off by default), only in these extra games; the official game is not changed. **Second line of defense in `ctf_game.lua`** (the first version of the fix, kept; without the stub the reset made the bar flash for a moment every second): `AllowUnitTransfer` refuses every change of the team of a protected unit, and every 5 frames the capture progress of protected units is set back to 0 (`SetUnitHealth(id, { capture = 0 })`, so the bar stays empty; the flags kept rising slowly too). Checked: with the fix the towers kept their owner (progress at most 0.03) while a commander stood next to one for 3000 frames. Learned on the way: `AllowUnitTransfer` is also asked when another gadget calls `Spring.TransferUnit` (the capture of the lootbox gadget was refused by it); the game's capture needs no command, so `AllowCommand` (refusing CAPTURE and RECLAIM) is not enough; which of the game's gadgets act on a unit can be found by reading the game files: `data\packages\*.sdp` lists the files (name, md5) and `data\pool\<md5[0..1]>\<rest>.gz` holds the gzipped content (how `unit_tombstones.lua`, `pve_supply_drops.lua` and `nearby_capture.lua` were found).
- **Checked in the game:** pick up, carry (flag follows), delivery (income), win, dropped flag after the death of the carrier (it lies there), the delivered flag stays at the collection point and another team takes it from there, own, other-team and neutral (Gaia) flags, saving and loading the section, undo / redo and dragging of the points, carriers in the air and in a transporter, weapons off while carrying and back after the delivery, a team that loses its flags (its units blow up, the other team wins). ## 11c. Restrictions of the level (what the player may not build)

- **One list for the whole level** (`rst`, `led_restrictions.lua`, a file of its own because the widget is close to the limit of 200 locals): `rst.data = { banned = { "armllt", ... } }` (names only: every X of the Place menu and of the Tower Defense page puts single units into this list), saved in the section `restrictions` of the level file (only when not empty; `rst.load(data.restrictions)` when loading, no backward compatibility). `rst.set` is the set of the names. Functions: `isBanned`, `setBanned(names, on)`, `toggle`, `allBanned(names)`, `payload()` ("name,name", "-" for none), `start()` / `stop()` (messages `rst|start|payload`, `rst|stop`). The Tower Defense page (`td.isBanned`, `td.techBanned`, the corner buttons) and the Place menu use the same object: what is forbidden in one is forbidden in the other.
- **Place menu (Units tab):** `Shared.newUnits({ restrict = { isBanned, setBanned, allBanned } })` (only the Level Editor passes it; the BluePrinter does not): every symbol has an X box in the upper right corner (`u:xBox`, `u:xAt`; click = `rst.toggle`), a forbidden unit is dimmed with a big red X and "- forbidden" in the title line. `u:filterRects` adds an X box (kind `factionx` / `groupx` / `techx`, `label = "X"`, red when set) to every faction, group and tech button (the button keeps room for it: `reserve`); `u:applyFilter` handles them: faction = all units of it (`u:namesOf`: all groups and tech levels), group = all tech levels of that group of the chosen faction, both ban all or allow all (`rst.allBanned`); the tech X works the same way with all units of that level in all factions and groups (`u:namesOf("tech", t)`; the level as the Place menu counts it: `clamp(floor(techLevel(ud)), 1, 3)`, Epic = 3, half levels count down; there is no rule of its own for a tech level any more). The state of every X button (and the red tint of its button) is computed with `rst.allBanned(names)` at every drawing: forbidding the last unit of a group turns its X on, allowing one unit turns it off. Header clicks and tooltips take the last rectangle under the mouse (the X lies over its button). The favorites view has no X.
- **Gadget `unit_restrictions.lua`** (synced; in the extra game `LevelEditorMod.sdz` and in every scenario package with restrictions): message `rst|start|name,name,...` (only with cheats or in the editor game) or at frame 5 the game option `restrictions` (base64url of the same payload; `GamePreload` reads it). It turns the names into a set of unitDefIDs, tells `GG.BuildBlocking.AddBlockedUnit(unitDefID, team, "level_restrictions")` of BAR for every team except Gaia (BAR then greys the units out in the build menu and refuses the build order itself: checked, the team rules parameter `unitdef_blocked_<id>` = `level_restrictions`; `rst|stop` removes it again) and refuses build orders itself in `AllowCommand` (cmdID < 0; builders and factories; "Not allowed in this level: name"). Without `GG.BuildBlocking` only the second part works. The editor sends `rst|start` when a Tower Defense or Capture the Flag test starts and `rst|stop` when it stops; in the editor itself nothing is blocked.
- **Scenario:** `Read-Restrictions` in `scenario_builder.ps1` reads the section; with a non-empty list the package gets the game option `restrictions`, the gadget file and `bar_rules.lua`, and `start_scenario.ps1` builds the small extra game "Tower Defense Scenario" for any package that holds one of the three gadgets (a plain level with restrictions therefore needs it too).
- **Checked in the real game:** every X (tech, group, faction, tile) sets and clears the list through simulated clicks; after `rst|start|armllt,armack` both units are blocked in the rules parameters and `armwin` is not, a second `armllt` was refused while the first one built before the block exists, an allowed unit was built; `rst|stop` released the block (the parameters are gone); the tech X of T2 put 319 units into the list, allowing one turned the X off, forbidding it again turned it on, the second click allowed all. Not checked: a real mouse click on an X, the build menu greyed out in a real game.

## 14. Scenario builder (`scenario\`, start menu key 3)

- **Button I in the game** (button column at the far right, below O; page of its own like O): edits the scenario info in the widget (`scenario` table, fields as in the block below). Rows: title, author, summary, briefing (Shift+Enter = new line), per team (teams with units, without Gaia and editor builders) a role (a click switches player → allied AI → enemy), tech T1/T2/T3 per team (green = allowed, red = off), AI behavior, win condition, start metal, start energy (digits only), grace period (m:ss), ID (a–z, 0–9). Text fields take the input through `OwnText`; Enter accepts, Esc discards. Changed info (`scenarioDirty`) is written by `saveLevel` as a block (`Json.encode`) instead of the block from the file; loading resets it. There is no save button on this page any more: the info is written with Ctrl+S (or "Save" / "Save as new" in the settings page O). Line endings `\r` in the level file are tolerated when reading the block (editor and script). Checked with mocks and in the real game (button, typing, saving; the block was in the level afterwards).

- `choose_map.ps1` (key 3) starts `scenario\scenario_builder.ps1` (PowerShell 5.1, without Python; the target computer needs only PowerShell as well) for the chosen level (also directly: `powershell -File scenario\scenario_builder.ps1`, without `-Level` with a level selection): asks title, author, summary, briefing, role of every team (player / allied AI / enemy), AI (BARb or NullAI), win condition, start metal and energy, ID. `-Level name -Auto` asks nothing.
- The answers are in a block `scenario = [==[ <json> ]==],` directly after `return {` in the level file (keys `title`, `author`, `summary`, `briefing`, `roles` per team number, `ai`, `win`, `metal`, `energy`, `sid`) and are the defaults on the next run. The editor copies the block unchanged and does not know the fields. The editor (`saveLevel`) reads the block of the target file before overwriting and writes it back unchanged; if it is missing there it takes the block of the level loaded last (`keptScenario`). Autosave `_last` included.
- `-Edit` (by hand): shows the info saved in the level numbered (title, author, summary, briefing, role per team, tech per team, AI, win condition, metal, energy, grace period, ID); choose a number and change the value, every change is saved in the block at once (only with exactly one player team); Enter ends, then the question whether the package should be rebuilt. Without a block: note, create a scenario first (key 3). Checked with test data.
- **Grace period** (field `grace`, minutes as a number, also fractional, input `m:ss`, `2,5` or `3`): with `grace > 0` the script writes per alliance `StartRectLeft/Top/Right/Bottom` (frame around the units of the alliance plus 300 Elmo margin, with 30 or more units without the outer 3 % of each edge; overlapping frames or ones closer than 500 Elmo are separated, the one of the alliance with the smaller number (player) stays, divided by the map size; double values, because `[math]::Max` rounds with integers), the game option `norushtimer = grace` (dot as decimal separator) and `startpostype=2`. The game (`game_startbox_config.lua`) widens the start boxes to the whole map for every other start mode, that is why `startpostype=2` is needed; then `game_no_rush_mode.lua` (commands and damage outside the start area) and the start position choice take effect. The editor writes `mapsize = { x, z }` (Elmo) into the level file; if it is missing the script stops with a message (save the level again in the editor). `scenario_briefing.lua` does the start position choice itself (`Spring.RequestStartPosition` in the middle of the own start area, then `SendLuaRulesMsg("ready_to_start_game")`; only if `grace > 0` is in `scenariooptions`). Checked in the game (level 8, 2:30): the game starts without input, the start boxes match the fractions, `norushtimer=2.5`; a move command into the enemy area and an attack command on an enemy unit are discarded, a command in the own area is accepted.
- **Resurrected units: Hold Position.** In the scenario the briefing widget (`widget:UnitCreated`) does this for the units of the player (see 11); for AI teams it is not possible in the official game, because widgets only control own units.
- **Tech restriction** (field `tiers`, per team number a string of allowed tiers, e.g. `"12"`; if a team is missing or it is `"123"`, there is no restriction): switches T1/T2/T3 per team in button I (green = allowed, red = off) and a question in the script. The script writes `tiers` with the new team numbers into `scenariooptions` (only teams with a restriction). At the start of the game the briefing widget locks per team all units with `customParams.techlevel` outside the allowed tiers through `/luarules buildblock <team> scenario_tech <names>` (gadget `api_build_blocking`, also applies to factory orders). The command needs cheats: the widget switches them on from frame 2 and off again from frame 16 (only if it switched them on itself). Tier 1.5 counts as T2; all units without the field count as T1; Epic units count as T3 (`techLevel`). Existing units stay. Checked in the real game (player T1+T2: only T3 locked; enemy T1: T2 and T3 locked; cheats off afterwards).
- **Tower Defense scenario** (the level has the section `towerdefense` with `enabled = true`, spawn point, goal and waves; `Read-TowerDefense`, `Find-CloseBrace` in `scenario_builder.ps1`): the waves run in the gadget `td_waves.lua`, which the official game cannot load. The builder writes two more game options into `scenario.txt`: `tdconfig` = base64url (no `;` inside) of the payload `enemyTeam;0;spawnX;spawnZ;goalX;goalZ;leaks;path;waves;restrict;fog` (team numbers as renumbered for the scenario: the player is 0, the enemy team the first one with the role Enemy, otherwise the first other team) and, if there are such units, `tdfixed` = base64url of `name:x,z,x,z|name:...` (units with `indestructible = true`: the corridor walls, buildings marked with FX). The scenario script `UNIT_RX` reads the flag from the unit lines (without it the flagged units would be skipped). Further settings for a Tower Defense scenario: the AI of the enemy team is NullAI (BARb would take the wave units over), `deathmode` is `neverend` (the gadget ends the game: all waves beaten = won, too many through = lost; a destroyed start commander must not eliminate the player), a level with only one team gets an extra enemy team without units (the waves belong to it), and the grace period is switched off (`$grace = 0` after saving the info; with `norushtimer` the no-rush gadget of the game blocks orders to targets outside the start area, so the wave units stood still at the spawn point: checked in the real game with the same level, 3 of 8 wave units moved with the grace period of 2:30, 8 of 8 without; the start areas of the sides were also wrong for the extra enemy team). The info page (button I) stays the same; the saved `ai` and `win` answers are not changed.
- **Capture the Flag and restrictions in the scenario:** a level with Capture the Flag on gets `ctfconfig` and `ctf_game.lua` (11b), a level with a non-empty list of restrictions gets `restrictions` and `unit_restrictions.lua` (11c); both need the small extra game of the starter. Tower Defense and Capture the Flag on in the same level file are refused by the script (`throw`, they exclude each other in the editor). The block `scenario` has no version and `Update-Block` does not exist any more; a missing `mapsize` stops the script with a message (no question for old levels).
- **Gadget in the scenario** (`not EDITOR_MODE`): `GamePreload` reads `tdconfig` / `tdfixed` (own base64 decoder), `GameFrame` starts the waves at frame 30 (`START_FRAME`; then the commanders of the player are removed, the visibility is set with `Spring.SetGlobalLos(allyTeam, not fog)`) and marks the units of `tdfixed` at frames 5, 30 and 90 (unit at that position with that name within 10 Elmo: `fixedIds`, public rules parameter `indestructible`; `UnitPreDamaged` returns 0). Build orders are restricted by `AllowCommand` (registered for all commands) as in the editor. Checked in the real game with a test level (2 waves, one waypoint, 2 flagged walls, armllt and tech 2 banned, Economy on, fog off): the extra game loads, "Started: 2 waves", wave 1 spawns 4 units, no own commander, 2 units protected, orders for armllt ("forbidden"), armpb ("tech level 2 is forbidden") and a nano turret ("only towers and economy structures may be built") are refused. Not played to the end (won / lost) in the scenario.
- **Which scripts run (start menu key 4 or the unpacked package):** the package is self-contained, so that it can be passed on to people without the editor: it holds the starter, `lobby.ps1`, `player_mapping.ps1`, the briefing widget, the gadgets the level needs and `bar_rules.lua`. When the scenario is started from the editor's menu nothing but `scenario.txt` (which gadgets it needs = which `*.lua` files its package holds, and `bar_path.txt`) is taken from the package: `start_scenario.ps1 -ScenarioDir <package folder> -EditorDir <LevelEditor folder>` runs from `scenario\template` (so the starter, the lobby and the briefing are the current ones) and builds the extra game from the current gadgets in `scripts\` and `..\shared\bar_rules.lua`. Checked (2026-10-23, sandbox, no game started): with a package whose `ctf_game.lua` had a marker appended the extra game contained the current gadget with `-EditorDir` and the packaged one without it.

Checked in the game.
### 14.1 Several players: lobby, split screen, direct host and join (tested only on one computer)

- **Entries:** start menu key 4 → scenario → **Single player** (`start_scenario.ps1` without options), **Host** (`-HostGame -Lobby`), **Join** (`-Join -Lobby`) or **Split screen** (below). Every package also has `Host Game.bat` and `Join Game.bat` with the same options (written by the builder next to `Start Scenario.bat`, together with `player_mapping.ps1` and `lobby.ps1`, which the starter dot-sources at its start). All players need the same BAR version and the same scenario folder; every computer builds the extra game itself.
- **Options of `start_scenario.ps1`:** `-HostGame`, `-Join` (asks for the address and the name), `-JoinIp <address>`, `-Name <name>`, `-Lobby` (the lobby below), `-LobbyPort` (TCP, 8453), `-LobbyAutoStart n` (the host starts by itself when n players are in: tests), `-Port` (UDP game port, 8452, fixed for the user), `-Wait` (seconds the game waits after the host has loaded before it starts: 90 without a lobby, 15 with a lobby, 10 is given by the split screen), `-Mapping "Ralf=0,Anna=2"` (who plays which team, first = host), `-Players n` (without a lobby and without `-Mapping`: number of humans for the dialog), `-HostIp` (0.0.0.0; the split screen gives 127.0.0.1), `-WindowRect x,y,w,h`, `-NoBuild`, `-WaitForHost`, `-ScriptOnly`.
- **Join:** the address comes from a list of the last 10 addresses (`%LOCALAPPDATA%\BAR-Scenario\Last Joined Addresses.txt`, one per line, newest first, shared by all scenarios): a number picks one, Enter = the newest, anything else is a new address; the used one moves to the top. The name is asked next (default: the Windows user name cleaned to letters, digits and `_-[]`, afterwards the last one used, `Last Player Name.txt`).
- **Lobby (`lobby.ps1`):** runs right after the scenario is read, before the extra game is built and the map is fetched. The host listens on TCP `-LobbyPort` (all network cards) and shows the screen of `Get-LobbyLines`: a title line (host, addresses, port, number of players), one box per team (`Get-TeamInfo` reads `Side` and `AllyTeam` of `scenario.txt`: "Team n: Side, ally team m"; players below, "(host)" behind the host; two free lines between the boxes, one or none if the window is not high enough) and the last box "[ Start game ]" ("ready" or the reason); **the focus starts on "Start game"**, so Enter or F5 starts at once once two players are in. Everybody who joins is put into a team box at once: the team of the last mapping (by name, `%LOCALAPPDATA%\BAR-Scenario\Last Player Mapping.txt`) if nobody is there, otherwise the first team without a player, otherwise team 0; a team may hold several players; a joiner whose connection breaks (also without `BYE`) is removed. **Keys of the host:** `Tab` / `Shift+Tab` or `Left` / `Right` = next / previous box (the last stop is "Start game"), `Up` / `Down` = player in the box, `Enter` = pick the player up (yellow, "<- moving"), then `Up` / `Left` / `Down` / `Right` move him into the neighbouring team box, `Enter` drops him, `Esc` puts him back; `Enter` on "Start game" or `F5` = start (two players are needed, otherwise the reason is shown), `Esc` twice = cancel. **Protocol** (TCP, one UTF-8 line each): joiner `HELLO <name>`, `BYE`, later `READY`; host `OK <name as the host knows it>` or `ERR <reason>` (name used already or empty after cleaning: the connection is closed), then `TEAM <n> <text>` and `ROSTER name=team;...` whenever something changes, at the end `START` or `CANCEL`, and `GO`. The joiner (`Join-Lobby`) shows address, status, his team and the players; `Esc` leaves.
- **Start from the lobby:** the host sends `START` and keeps the connections; the roster (entries name, team; host first) is saved as the last mapping and becomes `-Mapping`. Everybody prepares: the host builds the extra game, checks the map and writes his start script, every joiner does the same (extra game unless `-NoBuild`, map; a missing map is only fetched after a question) and sends `READY` (`Wait-JoinerGo`). The host waits for all of them (`Wait-LobbyReady`, up to 300 s; if somebody went away or does not come, nothing is started and the others get `CANCEL`), starts `spring.exe`, waits 5 s (the engine listens after about 3 s) and sends `GO`; the joiners then start `spring://<name>@<address>:<port>` and the game begins `-Wait` (15) seconds after the host has loaded.
- **Version of the files (`Get-PlayVersion` in `lobby.ps1`, 2026-10-23):** everybody who plays together needs the same starter, lobby and gadgets. The version is made of the files `bar_rules.lua`, `ctf_game.lua`, `lobby.ps1`, `player_mapping.ps1`, `pve_supply_drops_stub.lua`, `scenario_briefing.lua`, `start_scenario.ps1`, `td_waves.lua`, `unit_restrictions.lua`, looked for by name in the editor (`scripts\`, `scenario\template\`, `..\shared\`) or in the folder of an unpacked package (files a package does not hold are left out). **Hash:** SHA-256 over file name and text (without carriage returns, so the line endings of git do not matter) of all of them in a fixed order; **date:** the newest change time (UTC, `yyyyMMddHHmmss`) of these files. The hash alone says whether two computers are the same; the date only says who is probably newer (after a `git pull` it is the time of the pull, so it is a hint, not proof). The start menu shows both in its first line. In the lobby the joiner sends `VERSION <hash> <date>` before `HELLO`, the host answers after `OK` with its own `VERSION <hash> <date>`. A joiner with another hash stays in the lobby, marked in his box ("files older than yours: needs an update", "newer than yours" or "differ from yours"), and the start is refused with the reason ("Bob has older files than yours.") until the versions are the same; the joiner sees the same in his lobby (yellow: "OLDER than on the host - you need an update", "NEWER than on the host - the host has to update", "different from the host"; green: "the same as on the host"). Checked with the real files, a copy with one changed file (older: marked, start refused) and a copy with other line endings (same hash).
- **Play a level at once, bundle, transfer through the lobby (start menu key 6, 2026-10-23):** `scenario_builder.ps1 -Level <name> -BundleDir <folder>` (implies `-Auto`) writes only `scenario.txt` and the gadgets the scenario uses (`td_waves.lua`, `ctf_game.lua`, `pve_supply_drops_stub.lua`, `unit_restrictions.lua`, `bar_rules.lua`) into the folder (no starters, bats, readme, zip, **nothing is written into the level**; checked: the level file is unchanged). `Install-Bundle` (`lobby.ps1`) puts those files into the cache `%LOCALAPPDATA%\BAR-Scenario\Cache\<hash>\` (finished when `complete.txt` is there); the **hash** (SHA-256 over file names and bytes of the allowed files in a fixed order, `Get-BundleHash`) is the id, so the same level gives the same folder on every computer. `start_scenario.ps1 -Bundle` (needs `-EditorDir`; the BAR path is remembered in `%LOCALAPPDATA%\BAR-Scenario\bar_path.txt`): the host gives `-ScenarioDir <cache folder>` and offers the bundle in the lobby; a joiner gives no `-ScenarioDir`, takes the bundle from the lobby and then reads `scenario.txt` from the cache. **Protocol (additional lines):** host after `OK` and `VERSION` (only to a joiner with the same version): `OFFER <hash> <size of the zip>`; joiner with the hash in his cache: `HAVE <hash>`; otherwise he opens a **second connection** to the lobby port (so the text lines of the first one never see binary data), sends `FETCH <hash>` and gets `SIZE <n>` and the n bytes of a zip (`New-HostBundle` makes it from the cache folder; the host sends 256 KB per round with `WriteAsync`, so a slow joiner never blocks the lobby), shows the progress (`PROGRESS <percent>` to the host every 5 %: "(loading the scenario: 45 %)" in his box), unpacks, **checks the hash** and says `HAVE <hash>`. The host cannot start until everybody has said `HAVE` ("Anna has not loaded the scenario yet."). **Safety:** no program code comes from another computer. `Expand-BundleZip` accepts only the six names above (no paths, no `..`, no subfolders, nothing else) and at most 64 MB in total, the hash of the unpacked files must be the offered one, otherwise everything is thrown away, and an id from the network is only used as a folder name if it is 64 capital hex digits. Checked: lobby with a 6 MB bundle: a joiner with an empty cache fetched it (hash equal), one with the bundle in his cache took it without a transfer; zips with `evil.ps1`, `..\scenario.txt` and `sub/scenario.txt` are refused; the whole way with games: split screen of two players where the joiner has an empty cache of his own, the bundle went through the lobby, both games loaded and were in the game (Level8). **The map (2026-10-23):** after the bundle the joiner reads `mapname` from `scenario.txt` and looks whether the map is installed (name in the archive cache of his data folder, or a map from a host in the extra data folder, `Test-MapInstalled`); he says `MAPOK`; otherwise **nothing is asked** (2026-10-23): if he is in the **same network as the host** (`Test-SameLan`: the host's address is on this computer or in the subnet of one of his network cards, address and prefix length from `Get-NetIPAddress`; link-local addresses are ignored) and the host offers the map, he gets it from the host over the network (**H**); in every other case he downloads it from the internet (**D**, `pr-downloader --download-map`, the official map service; `MAPOK` when it ends with exit code 0). Only if that fails the lobby shows him the choice D (again) or H. The host offers his archive only if he finds it (`Get-HostMap`: the file of the map in the archive cache of his data folder, a name of letters, digits and `._()- ` ending in `.sd7` or `.sdz`, at most 1 GB; the SHA-256 is made once when the lobby opens): `MAP <size> <sha256> <file>` after `OFFER`. **Official hash (2026-10-23):** the maps of the game have no hash that is stored in the game (`checksum` in `ArchiveCache22.lua` is mostly zeros: the engine fills it only when it needs it), but the file server of BAR, which `pr-downloader` uses, knows MD5 and size of every official map: `GET https://files-cdn.beyondallreason.dev/find?category=map&springname=<name>` gives `[{"filename","springname","md5","size",...}]` (the `<map>.sd7.md5.gz` files next to the maps in `data\maps` hold the same MD5; all 25 of the maps checked match the file). With **H** `Get-OfficialMap` asks that service (timeout 6 s) **before** `MAPREQ`: `official` (md5, size), `unknown` (empty answer: a map of your own) or `offline`. For `official` a host file of another size is refused at once, and `Complete-MapFetch` compares the MD5 of the received file as well (besides the host's SHA-256); a difference throws the file away and the lobby shows "NOT the official map ..." with the choice D. For `unknown` and `offline` only the host's SHA-256 counts and the lobby says so ("not an official map: only the hash of the host is checked" / "official hash not reachable ..."). Checked with a local fake service: matching md5 (accepted, "checked against the official hash"), wrong md5 (thrown away, nothing in the cache), wrong size (refused before the transfer), empty answer and no service (accepted with the note); the real service answered for "Angel Crossing 1.5.1" with the md5 of the local file. **Exact size of every transfer (2026-10-23):** `Start-BundleFetch` gets the size that was offered (`OFFER`, `UPDATE`, `MAP`) as `$expect`; `Step-BundleFetch` refuses a `SIZE` line with another number ("the host sends another size than he offered") before any byte is read, and reads at most `SIZE` bytes, so a host can never make the joiner take more than he offered (beyond that the old upper limits stay: 1 GB map, 64 MB scenario, 16 MB update). Checked with a fake host: size 5000 and 10 against 1000 offered refused with 0 bytes read, 1000 accepted, header 1000 followed by 3000 bytes: only 1000 read. With **H** the joiner sends `MAPREQ`; the host does not ask anybody: if the address of the joiner's connection is in his own network (`Test-SameLan`) he answers `MAPYES` at once, otherwise `MAPNO` (the map of a joiner from outside comes from the internet); after `MAPYES` the joiner fetches the file on a second connection (`FETCHMAP <sha256> <his name>`, only for a joiner the host has agreed to, and only that file), shows the progress (`MAPPROGRESS <percent>` to the host: "(loading the map: 45 %)" in his box), checks the hash and puts the file with a small `.mapinfo` file (name of the map, hash) into `%LOCALAPPDATA%\BAR-Scenario\Cache\Maps\maps\`. **The engine finds it there** because `start_scenario.ps1` adds that folder to `SPRING_DATADIR` (the data folder of the player stays untouched). The host cannot start until everybody has said `MAPOK` ("Bob has no map yet."). Option for tests: `-LobbyMapKey D|H` (the joiner takes this answer at once instead of the automatic one). Checked: `Test-SameLan` (127.0.0.1, localhost and an address of the own /24 network: yes; 8.8.8.8 and 10.99.99.99: no); lobby with a 12 MB fake map: Anna (no key, same network) got it from the host without any question (hash equal), Carl "downloaded" it (fake downloader called with the right arguments), Dora had it installed, the game could start; a joiner from outside the network could not be tried on one computer; **with games**: split screen of two players, the joiner's data folder has no map and an empty cache, the map (20 MB `hooked_1.1.sd7`) came through the lobby into his cache, the engine scanned `Cache\Maps\maps`, loaded "Hooked 1.1" from there and both games started (the test ran in two sandbox data folders that see the real engine, game and maps only through links, nothing of the real data folder was written). **Update of the editor files through the lobby (2026-10-23):** if a joiner's version is **older** than the host's (or another one with the same date, never when the joiner's is newer: nobody is turned back) and the host runs from an editor folder (`-EditorDir`), the host adds `UPDATE <size> <sha256 of the zip> <number of files>` after `VERSION` (`New-HostUpdate` makes the zip when the first joiner needs it: all `*.ps1` and `*.lua` of `LevelEditor\scripts`, `LevelEditor\scenario`, `LevelEditor\scenario\template` and `shared` and `install_editor.bat` / `uninstall_editor.bat`, 26 files, about 190 KB; **never** levels, scenarios, `start_level_editor.bat` or other files; the zip is deleted when the lobby closes). The joiner sees "Your files are older than the host's (26 files, 194 KB). U = get the update from the host: it is only looked at first, nothing is replaced before you say Y". With **U** he fetches the zip on a second connection (`FETCHUPDATE <sha256>`); it is checked (the SHA-256 of the zip, `Expand-UpdateZip`: only names matching `$script:UpdateNameRx`, no `..`, no other folders, at most 16 MB) and unpacked into `%LOCALAPPDATA%\BAR-Scenario\Update\<16 digits of the hash>` (a short path on purpose), and **the unpacked files must give exactly the version hash the host announced** (`Get-StagedVersion`). Then the screen lists which files would change ("... would change: choose_map.ps1 (changed), help_texts.lua (new)"), says that these are programs and that the old ones are saved first; **Y** installs, **N** throws the unpacked update away. `Install-EditorUpdate`: the old files that change are copied to `%LOCALAPPDATA%\BAR-Scenario\Backup\<time>\` first (same folder structure), then the new ones are copied over; if any copy fails everything that was done is **put back** from the backup and the error is shown; it **refuses a folder with a `.git`** (a working copy is updated with git). Files that are not in the update (own files) stay. After the installation the joiner says `BYE`, `start_scenario.ps1` ends with **exit code 10** and the start menu (`choose_map.ps1`) shows "The Level Editor was updated from the host. Please start the Level Editor again" and ends (it still runs the old files in memory); the player starts the editor and joins again. A package (no `-EditorDir`) only shows that the update is not possible from there. **Trust:** there is no signature; the joiner trusts the host after his explicit Y, and the safety is only that nothing else than editor files can arrive and that the transfer is complete and unchanged. Option for tests: `-LobbyAutoUpdate` (the joiner says U and Y at once). Checked in copies of the editor tree: the client with 3 files older or missing got exactly those 3 (2 changed, 1 new), they equal the host's afterwards, the version hashes are equal, the backup holds the 2 old ones, an own file stayed; a failure in the second file (opened without sharing) put the first one back (state before = state after); a folder with `.git` is refused; zips with `x.exe`, `scripts/../../x.ps1`, `Windows/x.ps1` and `start_level_editor.bat` are refused; the whole way with the real `start_scenario.ps1 -Bundle -Join -Lobby -LobbyAutoUpdate` of the older copy: it updated itself and ended with exit code 10. **The cache and faults (2026-10-23):** what hosts gave lives in `%LOCALAPPDATA%\BAR-Scenario`: `Cache\<hash>` (scenarios), `Cache\Maps\maps` (maps with `.mapinfo`), `Update\<16 digits>` (unpacked updates), `Backup\<time>` (files an update replaced). **Looking after it** (`lobby.ps1`): `Use-CacheItem` marks a scenario or map as used (its time is set when the cache is hit); `Remove-OldCache` runs when the start menu starts (`choose_map.ps1`) and deletes scenarios not used for 30 days, maps not used for 60 days and, oldest first, more maps while the maps are beyond 3 GB, `.part` / `.tmp` leftovers and unpacked updates older than a day and zips of hosts (`bar_bundle_*.zip`, `bar_update_*.zip`) older than a day in TEMP; **`Backup` is never deleted**. Start menu **key 7** shows the size ("Clean the cache (scenarios and maps from hosts: 214 MB, 3 maps)") and, after y, `Clear-BundleCache` empties `Cache` and `Update` (what is needed again is fetched again from the host). The zips a host made for the joiners are deleted when his lobby closes (start, cancel or error). **Faults:** a transfer that breaks off (`Step-BundleFetch` sees the closed connection, a wrong answer, a size beyond the limit) ends with the reason shown (scenario: the joiner leaves the lobby with "refused: scenario - error: the host closed the connection"; map or update: back to the question with the reason) and `Close-Fetch` removes the half-finished file; a failing hash, name or unpacking throws everything away. A joiner who breaks off in the middle of a transfer is removed by the host (the failed write ends the transfer) and the lobby goes on. Checked: pruning with fake ages (an old scenario, an old map with its `.mapinfo`, an old `.part`, an old unpacked update and an old zip in TEMP went; a fresh scenario, a fresh map, an old scenario that had just been used and the backup stayed); a fake host that closes after 1 of 5 MB (clear reason, no file left); a real host with a 30 MB bundle and a joiner who read 1 MB and left (the host removed him, a second joiner got the scenario and the game could start, the zip was removed afterwards). **Not checked:** a full disk, a transfer over a real network (only loopback), two computers.
- **Who plays which team (start script):** every human gets `[playerk]` with the name and the team of his entry (the host `player0`, `Name` and `Team` replaced); a team with a human loses its `[ai]` block, a team without human keeps its AI or gets one (copy of the first AI block: `ShortName`, `Version`, `Name=<ShortName>_<team>`, a new index); `numplayers` = humans, `numusers` = humans + AIs, `hostip`, `hostport`, `GameStartDelay` = `-Wait`. The start script is written to `%TEMP%\bar_scenario_start_<name>.txt` (one file per player: games of one computer must not overwrite each other's script). Without `-Lobby` the mapping comes from `-Mapping` or from the dialog `Get-PlayerMapping` (`player_mapping.ps1`: the lines "name -> team (side)" start from the last mapping, a line number edits that line, a team of another player is swapped, Enter starts; `Get-TeamInfo`, `ConvertTo-PlayerName` and the file of the last mapping are used by the lobby as well); the joiners must then type the names of the mapping.
- **Split screen (start menu key 4, fourth entry):** asks "How many players" (2 to 8, at most the number of `[team]` blocks of `scenario.txt`; typed digits, `Read-PlayerCount`: **Enter without digits = the maximum, Esc = back**) and starts all games from `choose_map.ps1`: the n-1 joiners first, each a minimized `start_scenario.ps1 -Join -JoinIp 127.0.0.1 -Lobby -Name <TopRight, BottomLeft, ... (`Get-SplitNames`; with three or four columns Top1, Top2, ...)> -NoBuild -WaitForHost -WindowRect <cell>`, which wait up to 2 minutes until the host listens on the lobby port (`GetActiveTcpListeners`; without a lobby until a UDP listener exists on the game port), then the host in the foreground: `-HostGame -Lobby -Name TopLeft -HostIp 127.0.0.1 -WindowRect <cell>`. The players are in the same lobby (the local ones joined by themselves, the host distributes the teams) and start together after "Start game". Everything stays on this computer (`hostip=127.0.0.1`, no firewall question). **Window layout** (`Get-SplitRects`): work area of the main screen without the task bar in real pixels (`SetProcessDPIAware`, otherwise a 150 % screen reports scaled values), up to 4 players 2 x 2 cells, up to 6 players 3 x 2, up to 8 players 4 x 2, row by row from the top left, the host first. `-WindowRect x,y,w,h` (outer size): the starter writes an own copy of the settings of the user into `%TEMP%\BAR-Scenario\window_<name>.cfg` (the original `springsettings.cfg` is only read) with `Fullscreen = 0`, `WindowBorderless = 0`, size and position (window values minus an estimated frame) and `InitialNetworkTimeout = 600`, `NetworkTimeout = 600`, starts `spring.exe --config <copy>` and, as long as the window is not exactly on the rectangle (first 90 s), sets the outer rectangle with `SetWindowPos` (no activation). `-NoBuild` keeps the extra game the host has built.
- **Findings about the engine (2026-10-22):** (1) without `hostip` or with 127.0.0.1 in a start script the engine listens on the loopback address only ("other users will not be able to connect"; a client of the same computer did not get through either), `0.0.0.0` works for the LAN; an explicit `127.0.0.1` works for the split screen. (2) The server does not wait for a player who has not connected: with `GameStartDelay=3` the game started when the host had loaded and a player who connected 20 s later was refused with "Game has already started"; with 60 s a player who connected after 52 s was waited for until he had loaded. That is why the lobby gets everybody together first. (3) Several games loading on one computer are slow (three games: one needed 77 s) and the server dropped a game that was still loading with "timeout": `InitialNetworkTimeout` and `NetworkTimeout` 600 in the copy of the settings. (4) Several games can share one data folder (`--write-dir`). (5) `TowerDefenseScenario.sdz` is locked while a game runs, so only the host builds it in the split screen. (6) A game that connects before the host's engine listens fails after 10 s; hence `READY` / `GO`. (7) The 8 GB of video memory of the test computer were almost full with three games (four still ran).
- **Checked (2026-10-22, sandbox, Capture the Flag / Tower Defense gadgets):** two games over the network layer on one computer (client connects, both load, the game starts); split screen with 3 and 4 players (cells exact, 1920 x 1044 on a 3840 x 2160 screen); the lobby with test scripts (key feed and dump file instead of the console) and in a real console window (screenshot): joiners land in free teams, moving between boxes (also into a team with another player), start with two or more players, a leaving joiner is removed, a repeated name is refused, the joiner sees his team and the players; the whole path with a game: split screen with 2 players through the lobby (`-LobbyAutoStart 2`): TopLeft and TopRight joined, both prepared, the host's game started, the joiner connected after `GO`, both games ran in their cells and the game started. **Not checked:** two computers (firewall: TCP 8453 and UDP 8452), 5 to 8 players, three or more players with the lobby start, a joiner who has to download the map, the keys of the lobby on the real keyboard, the flags and the income with two humans.
- `scenario.txt` is a start script for the official game: teams numbered 0..n-1 (player = 0), allies in alliance 0, enemies in alliance 1, `startpostype=0`, game options `deathmode`, `maxunits`, `startmetal`, `startenergy`, the `requiredmodoptions` of the level and `scenariooptions` = `base64url(zlib(json))` with `scenarioid`, `title`, `briefing`, `disablefactionpicker`, `unitloadout`, `featureloadout`. The placeholders `__GAMETYPE__` and `__PLAYERNAME__` are filled by the starter.
- `start_scenario.ps1`: finds BAR (remembers the path in `bar_path.txt`), the newest engine and the installed game version (like `install_editor.ps1`), if the map is missing it points out that it has to be downloaded from the internet and asks (y/n); only with "y" it downloads it with `pr-downloader`, with "n" it aborts; then it starts `spring.exe`. `-ScriptOnly` only writes the start script.
- Gaia units are in the level with `gaia = true` (`team` is the Gaia number of the editor); when loading in the editor they get the current Gaia team, in the scenario the number after the last real team. Checked in the game: scenario with two teams and one Gaia unit, Gaia team 2, the unit belongs to team 2.
- Wrecks: features `<unit>_dead` get the field `resurrectas` in the scenario (the game calls `Spring.SetFeatureResurrect` with it); the editor gadget (`placeFeature`) sets the resurrection when creating as well. In the level file resurrectable wrecks additionally carry `resurrectas = 'unit'` (the editor writes it when saving from `Spring.GetFeatureResurrect`; the scenario builder takes it, otherwise derives it from the name). Input in the scenario builder: the console input stays on the default encoding (if it is switched to UTF-8, `Console.ReadLine` returns the character NUL for umlauts). Checked in the game: `armpw_dead` has `GetFeatureResurrect = armpw`, `armpw_heap` none.
- The unit limit of the scenario is the `unitlimit` stored in the level (set in the editor settings, default 32000) and written as the game option `maxunits`.
- Builders created with Ctrl+D (tools) are not saved in the level by the editor.

## 15. Known limitations and open points

- The look of the menu was mostly only checked with mocks; acceptance happens in the game.
- The fallback `gl.UnitShape` of the 3D preview is not finally confirmed in the real game (`/led_ghost` helps with the diagnosis).
- Damage per shot uses the default armor class and ignores special effects (area damage, slowing).
