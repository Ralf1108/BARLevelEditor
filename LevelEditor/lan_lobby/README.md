# LAN Play (prototype)

A widget for the official lobby (Chobby) of Beyond All Reason: the main menu entry **LAN Play** (right after Multiplayer) to host or join a game in the local network **with the official multiplayer battle room** (map, options, AIs, colours, teams, chat), without the lobby server in the cloud.

## How it works

The host's lobby runs a very small lobby server inside the widget (the "TASServer" text protocol the official lobby speaks, plus the part of an autohost the room needs). The lobby of every player then behaves as on a normal server:

- **Host a LAN game:** the widget listens on TCP port 8453, the lobby of the host connects to it (the server address of the lobby is changed for the time of the LAN game and put back when you leave), logs in and joins the battle. The battle room opens.
- **Player name:** the name in the LAN game is the one the lobby logs in with (`Configuration.userName`, saved in the lobby settings, so the player does not have to be logged in; else the Steam name, else "Player"). The LAN Play page has a field "Your name" with it; a changed name is remembered in `data\lan_name.txt` (deleted again when it equals the account name). Two players with the same name cannot be in one game: the host refuses the second ("name taken"); change the name in the field.
- **Find LAN games:** while the LAN Play page is open (and this computer neither hosts nor plays a LAN game) the widget looks for games by itself every few seconds: it asks `WHO` on port 8453 at the addresses `x.y.z.1 .. 254` of the own network (a /24 network is assumed; the lobby cannot ask for the netmask). A computer that hosts does not scan, so it never finds itself. A found game is a button; a click joins it (or type the address and press Join). The joiner's lobby connects to the host's server and joins the battle.
- **The menu button:** the tab "LAN Play" is added to the finished main menu, right below Multiplayer (the menu is one column; there is no place beside it). It is checked every second, because the lobby builds its menu again at times.
- **Normal Multiplayer is untouched:** the widget never changes the server address of the lobby (the lobby saves its configuration when it ends; an earlier version changed it and the official games were gone). It connects its own LAN connection with the LAN address only. "Leave LAN play" and leaving the battle room log the lobby in to the normal server again and bring the player back to the LAN Play page; after a game the lobby starts again and the widget opens the LAN Play page (marker file `lan_return.txt`).
- **Server side (what the widget answers):** `LOGIN`, `PING`, `JOINBATTLE`, `LEAVEBATTLE`, `MYBATTLESTATUS` (relayed as `CLIENTBATTLESTATUS`), `SAYBATTLE` / `SAYBATTLEEX` (chat, relayed), `ADDBOT` / `REMOVEBOT` / `UPDATEBOT` (AIs), and the autohost commands the room sends as chat: `!map`, `!bSet` (game options, relayed as `SETSCRIPTTAGS`), `!cv start` / `!start`. Only the host may use the `!` commands. Everything else (score, ratings, friends, channels, queues) is not answered.
- **Start:** `!cv start` makes the autohost set its status to "in game"; every lobby in the battle then connects to the game as for any game on a server (`ConnectToBattle`, with the script password the player sent when joining). The lobby of the **host** is the one that runs the game server: its `ConnectToBattle` is replaced by a `Spring.Reload` with a start script built from the state of the room (game, map, options, players with password, teams, ally teams, colours, sides, AIs, `HostIP=0.0.0.0`, port 8452).

## Install

The Level Editor setup (`install_editor.bat`) does it: it runs `install_lan_play.ps1` (copies `lan_lobby.lua` to `data\LuaMenu\Widgets\` and sets `["Chili lobby"].loadLocalWidgets = true` in `data\LuaMenu\Config\IGL_data.lua`, with a backup of that file; the game and launcher must be closed) and makes the junction `data\LevelEditorScenarios` -> `scenario\scenarios`. `uninstall_editor.bat` removes both. By hand: `powershell -File install_lan_play.ps1` (`-Uninstall` removes it again).

## What the sandbox test showed (2026-10-24)

Two sandbox instances of the real lobby on one computer (test file `lanlobby_cfg.txt` in the write dir: `auto=host|join`, `name`, `map`, `players`, `ip`): the joiner found the host by the scan, both logged in to the small server, both joined the battle, the host's lobby chose the map (`!map`) and pressed Start (`lobby:StartBattle()`, the call of the room's Start button, which sends `!cv start`); the autohost set "in game", the host built the start script (2 players with the passwords the lobbies had sent, Hooked 1.1, the game of the lobby, `HostIP=0.0.0.0`), both engines loaded the game, and the host log says "Connection attempt from ..." for both and "Player Hanna finished loading and is now ingame".

Sockets of the lobby: TCP listen and connect to any address are allowed, UDP receive too, **UDP send is refused** (`UDPAllowConnect` is empty). So TCP only.

## Copilot: several humans play one player (2026-10-25)

- **Idea:** inside an ally team every human has a number 1 .. n (n = the humans of that ally team). By default everybody has a number of his own (his place in the team). The host can give a human the number of another one: **humans with the same number are Copilots and play one player together**: one team of the start script, all of them give orders to its units, one pool of resources.
- **Where:** the button **Copilot** (host only; in the middle column of the room, under the lines "Update Ready" / "Map Ready", below the button Custom Scenario). Its list opens under the buttons and lists the humans (spectators do not count) by team; the button of a human shows "player k"; a click gives him the next number (1 .. n, then 1 again); "+ Copilot with ..." marks the humans with the same number. The state is kept in the server of the widget (`c.slot` of the connection, only a number the host chose; the others keep their place in the team, so a human who takes the number of another one joins him and the other one stays), not in the battle status (the lobby of Chobby would fight it). Every click puts a line into the chat of the room ("Ben is player 1 of his team now and is Copilot with Ralf."); the start says "Copilot (one player, several humans): Ralf + Ben". In a scenario everybody plays the team of the scenario together anyway (the window says so).
- **Start script (`buildScript`):** one `[TEAMn]` for every "ally:number" group of humans (leader = the first one), every `[PLAYERn]` of the group gets that `Team=`; the host is player 0 (the little widget acts only in the game of player 0). With a shared team `StartPosType=0` (the positions of the map) instead of 2 (chosen in the game).
- **Why a widget starts the game (`shared_start.lua`, in `scenario\template`, installed to `data\LuaUI\Widgets` by `install_lan_play.ps1` and by the scenario starter):** found with two instances of the game on one computer: two humans in **different** teams start by themselves after the delay of the start script (control test), two humans in the **same** team stay in the pregame for ever. The widget of the host (player 0) sends the engine command `forcestart` three seconds after every human player is `active` (a player becomes active when he has finished loading: the host after 3 s, the second player after 13 s in the test). Only if some team has two or more humans.
- **Checked (sandbox):** pure functions of the numbers (defaults, same number = together, a number above the count of the team, two ally teams, the third keeps his number, cycling), the whole file in a stub environment with fake players (script: the same team for Ralf and Ben after one click, 2 teams + AI instead of 3 + AI, host = player 0, spectator without team, chat line, `StartPosType` 0 or 2); the script of that fake room played with two real instances (a shared team: both humans see the same commander, the host orders it east, the guest orders it back west, both instances show the same positions, the game started by itself through the widget). **Not checked:** the window (screenshots of this lobby come out black here), a click on it, two computers, the balance warning of the official room when the teams start (I do not know how it counts humans who share a player; the problem with the start found here was the engine's pregame, not a balance check).

- **Where the buttons live (2026-10-26, seen in a screenshot of the real room):** as floating buttons at the top left (children of `screen0`) they were hidden behind the lobby's own windows, so both buttons are children of the middle column of the room (the parent of the labels "Update Ready" / "Map Ready"), under those lines; the lists open as windows over the team list (see the next point). The lobby builds the room again at times, so the column is looked for once a second and a field set on it (`lanButton272`, the controls are proxies, no `==`) tells whether the buttons are already in it; the windows are made new at every click. The room is repainted only when the mouse moves (a test needs real mouse moves and a first click to focus the window; screenshots with `CopyFromScreen` of the sandbox window, DPI aware).
- **Layout follows the room (HD and 4K, 2026-10-26):** the column of the room is about 380 wide in a 4K window and about 160 in a HD window (the heights of the lobby's buttons stay about the same). Width of the buttons = width of the column - 10, their place = under the lowest of the labels "Update Ready" / "Map Ready", and the small font in a narrow column. Below the buttons there is room in a 4K window only, so the lists open as a window **over the team list** (left of the column, in the panel that holds the column) with a button Close; a window in the main window of the room was not drawn. The help text is a tooltip (of the button Copilot and of the player buttons), not text in the window.
- **Joiners see the list, read only:** the button **Copilot** is also there for a joiner (the button Custom Scenario only for the host). The host's server answers the command `COPILOT` (before the login, like `WHO`) with one line `COPILOT name~ally~number|...`; the joiner asks every two seconds on a short connection (`updateCopilotPoll`) and shows the list without buttons ("player 1" as text). A game option would have been shown by the room as a text line, and the lobby does not keep other script tags; the joiner's list was checked in the log (`Ralf:0:1|Ben:0:1`), a screenshot of the joiner's window stayed at the loading screen of the game.
- **Fixed with it:** the Copilot list sorted the humans by name before it worked out the default numbers, so it showed other numbers than the chat line and the start script (Ben "player 1", Ralf "player 2" although the chat said they play together).

## Scenarios (2026-10-24)

- **Where they come from:** the junction `data\LevelEditorScenarios` -> `scenario\scenarios` (made by the Level Editor setup; the lobby cannot read folders outside the game folder). The host sees the button **Custom Scenario** (in the middle column of the room under "Map Ready", only for the host while the LAN battle room is open) with the list of the built scenarios and the entry "Official map (no scenario)".
- **What a choice does:** the server sets the map of the scenario (the room shows the map and its picture as usual), tells the room the scenario by the game option `lanscenario`, and keeps the teams of the scenario: every player's ally team is forced to the one of the scenario's first player (the corrected status goes to everybody, also to the sender; spectators stay spectators). The room still shows its team controls; a change is undone by the server. Choosing an official map (the room's map selection or the list entry) lifts this again.
- **Start:** the script is the scenario's own (`scenario.txt`: teams, units, options, start positions, AIs) with `__GAMETYPE__` = "Level Editor Scenarios 1", the host as player 0 and **every other human as a further player in the team of player 0** (password from the lobby, spectators stay spectators), `hostip=0.0.0.0`, port 8452.
- **The extra game "Level Editor Scenarios"** (`data\games\LevelEditorScenarios.sdz`, built by `install_editor.ps1` and by the quick setup together with the Level Editor game, same stamp): the gadgets of the scenarios (waves, flags, restrictions, the lootbox stub) and `bar_rules.lua`. Each gadget switches on only by the game options of the scenario, so it is one game for all scenarios. The zip entries have a fixed time so that two computers build equal archives. A joiner who does not have it (or has another one) gets it from the host before the start, see below.
- **Same extra game on every computer (checked 2026-10-24):** with the scenario the host announces the hash and size of his `games\LevelEditorScenarios.sdz` (game option `lansync`, hash by `VFS.CalculateHash`). A joiner whose file is missing or different is asked (a confirmation popup: the file holds gadgets of the scenarios, only from a host you trust); on yes he opens a second connection to the host's lobby port and sends `FETCHGAME <hash>`; the host answers (after the usual greeting line) `SIZE <n>` and the bytes, 64 KB per frame. The joiner takes at most the announced size (at most 4 MB), checks size and hash, writes `games\LevelEditorScenarios.sdz.part`, replaces the file, calls `VFS.ScanAllDirs()` and the game is there. The start of the game waits for it (`ConnectToBattle` is postponed until the file is loaded); declined or failed means: no start for him, with a message. Checked in the sandbox: the joiner had no extra game, got 17647 bytes, the file equals the host's byte for byte, both engines loaded "Level Editor Scenarios 1" with the Capture the Flag gadget. Not exercised: declining, a failing transfer, the postponed start (the transfer was faster than the start).
- **Checked** in the sandbox (two lobbies): the host chose `level8`, the server set Hooked 1.1 and the ally team 0, a second player joined, the start script has both humans in team 0 (`numplayers=2`, `numusers=3` with the AI), game "Level Editor Scenarios 1"; both engines loaded it and both logs say "Loaded synced gadget: Capture the Flag".
- **Not checked:** the look and place of the button and the list, clicking the entries, how the room shows the forced teams, a second computer, the scenarios' own widgets (briefing) in a LAN game, declining the transfer of the extra game, a failing transfer, the postponed start.
