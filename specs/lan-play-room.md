# LAN Play: bosses, teams and start boxes

Part of the specification of [LAN Play](lan-play.md) (the lobby widget `lan_lobby.lua`: server, page, start of the game, menu, Copilot, Custom Scenario, versions, map, tests).

What the host's room does with the chat commands of the official server: who may change the room and start the game, and how the players get into teams and start boxes.

## 1. Bosses (`!boss`, `!unboss`)

- "Make Boss" / "Disable Boss" in the menu of a player send `!boss <name>` / `!unboss <name>` as chat.
- `autohostCommand` keeps the names in `S.battle.bosses` and tells the room with the BarManager line `{"BattleStateChanged":{"boss":"PlayerB,PlayerC"}}` (empty = no boss; the room sets `isBoss` from it, only if it comes from the founder); a joiner gets the line right after `JOINBATTLE`.
- The host is boss from the start (added when it logs in, `!unboss` on the host is refused): the lobby's Option Presets load (modoptions, bots with bonus) applies them only when `battle.bossed` is true, i.e. when the room reports at least one boss, otherwise it says "tried to apply a preset containing modoptions, but was prevented due to not being boss" and loads nothing (saving worked, loading did not).
- A preset also sends `!preset <x>`, `!lock`/`!unlock`, `!autobalance <x>`, `!balanceMode <x>` with the values it saved from `battle.preset` etc.: the load builds these strings by concatenation, so a value that the room never reported (nil) raised an error and loaded nothing (the real reason that loading failed while saving worked).
- The emulated autohost therefore reports `preset=team`, `autoBalance=off`, `balanceMode=skill` as BarManager fields at every join (`spadsState`), keeps what `!preset`, `!autobalance`, `!balanceMode` set and reports it again; `!lock`/`!unlock` are ignored (logged); `!bSet`, `!nbTeams`, `!set teamSize` and `!force <bot> bonus` it answers.
- A boss may use the same room commands as the host (`isBoss(c.name)`); a player who leaves is dropped from the list (`dropBoss`).
- Test: `lan_test.ps1 -Mode boss` (log lines `test: ... isBoss`). **Option Presets, checked in the real panel without a game** (`lan_test.ps1 -Mode preset`, version 12): the test writes a preset file, opens the lobby's panel (`WG.OptionpresetsPanel.ShowPresetPanel`), chooses the preset in its list and presses its Load button, then logs the room's values (`test: preset before / after`).
- Result: preset, autoBalance, balanceMode, teamSize, nbTeams, the map, the start boxes, a computer with its bonus (`!force <name> bonus`), the modoptions (`startenergy`, `startmetal`) and the lock are taken over.
- `!lock` / `!unlock` were ignored by the room until version 12: they set `S.battle.spads.locked`, reported to the lobby as field `locked` of `UPDATEBATTLEINFO` (the lobby reads `battle.locked` only from there, not from BarManager); the room itself stays open for joiners.
- A preset file written by hand needs the start boxes as `{left, top, right, bottom}` (scale 0-200), otherwise the load stops in `AddStartRect` with an error after the first settings (that was an error of the test file, not of the lobby).
- A preset without start boxes while it has multiplayer settings is not handled by the lobby (`#presetRectangles` of nil, an error of the panel's own code, `multiplayer and presetMPBattleSettings == nil` only).
- Presets saved before version 9 have a "Multiplayer Battle Settings" block without `preset` / `autoBalance` / `balanceMode` (the room did not report them then): the lobby's load raised `attempt to concatenate field 'preset' (a nil value)` (`gui_optionpresets_panel.lua`, line 147) and loaded nothing (reproduced with the preset file of a user: `lan_test.ps1 -Mode preset -PresetFile <optionsPresets.json> -PresetName <name>`).
- Version 13: `repairPresetFile` (before hosting) puts the missing values (`team`, `off`, `skill`) into `optionsPresets.json` by a text edit, the rest of the file stays.
- Checked with two presets of a user (map, team size, teams, computers with bonus, modoptions, start boxes loaded).
- **Start by a boss (version 28):** the Start button of the lobby sends `!cv start`; the host starts with it when it wants, a boss only when every player (not a spectator) has pressed Ready: `notReadyPlayers` lists who has not (`ParseBattleStatus(...).isReady`), the room says "The game cannot start yet: everybody has to press Ready first.
- Not ready: ..." and nothing starts; every autohost command is logged with its sender and role (`autohost: command ... (host|boss|no boss)`, a refused start too).

## 2. Teams and start boxes (`!nbTeams`, `!set teamSize`, `!balance`)

- The room's buttons "N teams" and "N per team" only send chat commands to the autohost and change nothing by themselves: they wait for the autohost to report the new value, as SPADS does.
- The widget therefore answers (host only, not while a scenario is selected):

- `!nbTeams N` / `!set teamSize N` (1 to 16): stored in `S.battle.nbTeams` / `teamSize` (start 2 and 2), reported to everybody as the BarManager line `SAIDBATTLEEX LANHost * BarManager|{"BattleStateChanged":{"nbTeams":"3","teamSize":"2"}}` (the room takes it only from the founder) and as the chat line `Global setting changed by <host> (nbTeams=3)`, which makes the room refresh its boxes and ask `!balance`.
  - A joiner gets the BarManager line right after `JOINBATTLE`.
- `!balance` (`balanceTeams`): non-spectator humans (host first, then in joining order) and computers get the ally teams 0 .. nbTeams-1 one after the other; the new status goes out as `CLIENTBATTLESTATUS` / `UPDATEBOT`.
- `!force <name> team <N>` (menu entry "Change Team" of another player; N counts from 1) and `!force <name> bonus <N>` ("Add Bonus", the handicap): `forceCommand` changes the ally team / handicap of that human or computer (host or boss only, like all commands) and sends `CLIENTBATTLESTATUS` / `UPDATEBOT`; with a scenario the ally team stays the scenario's (`forcedStatus`).
  - A player can change their own team without it (the lobby sets their own status).
- **Network limits of the host:** the game server runs inside the host's game, so the host's own limits apply to every player (`LinkOutgoingBandwidth` 192 KB/s by default, `LinkIncomingSustainedBandwidth` / `PeakBandwidth`, `LinkIncomingMaxPacketRate`); a server in the cloud has much higher ones.
  - Before `Spring.Reload` the host writes higher values into `springsettings.cfg` (`Spring.SetConfigInt(name, value)`, only when the stored value is lower; 4 MB/s out, 4 / 8 MB/s in, 4096 packets).
  - The first try with the config overlay (this run only) may not have counted, because the engine may read these values only at its start: the saved values count from the next start of the game.
  - Meant against the many messages "Player is lagging behind" / "caught up" in LAN games.
  - Not verified in a game: whether the bandwidth was the cause (other causes: a slow computer of a player, a VPN with delay, the host's computer busy with its own game).
- **Scavengers / Raptors AI in the room:** the computer is written to the start script as chosen (`ScavengersAI` / `RaptorsAI`; the game's Scavenger / Raptor mode needs a team with such a Lua AI, `teamfunctions.lua`, and a `NullAI` there spawns nothing: tried, reverted).
  - The AI is only the spawner; the humans of its ally team command its units.
  - The order stop works only for an AI that has a human player (not a spectator) in its ally team (`hasHuman` in `lan_pve_hold.lua`, read at the start of the game);
    - the room tells everybody about it (version 11, `pveHumanNotice` in `lan_lobby.lua`, checked once a second in `updateServer`: a chat line from the host when the first human comes into the ally team of such a computer or the computer is added to a team with a human, and another when the last human leaves it or the computer is removed; log: `pve notice`);
    - an AI alone in its ally team stays as the game has it (the gadget removes itself, checked: no order dropped, no `[LAN] the orders ... are dropped` line).
  - To stop the AI's own orders the gadget `lan_pve_hold.lua` (in the extra game of the scenarios, switched on by the game option `lanpvehold=1`) drops, in `AllowCommand`, every order that Lua code gives to a unit of a team with a Lua AI containing `Scavengers` / `Raptors` without a player behind it (`playerID` -1, `fromSynced`/`fromLua`: the orders of the Scavenger and Raptor gadgets).
  - Orders of players pass, also those that other gadgets pass on for a player (they keep the player number; seen in the log: order 34571 with player 0 and `fromSynced`); state switches (fire state, move state, repeat ...) pass.
  - Tried and dropped: `fromSynced` alone (also dropped the orders other gadgets derive from a player's order, nobody could command the units) and the call stack (`debug` is an empty table in synchronized code).
  - The first 30 orders to such units are written to the log (`[LAN] order ... player, fromSynced, fromLua -> dropped / allowed`).
  - Checked with `test-data\tools\pve_test.ps1` (a sandbox game with a human, the AI in the human's ally team and an enemy team): Raptors and Scavengers without the option: all units of the AI have an order of the AI (8 of 8) and a player's move order may be overwritten; with the option: none (0 of 10 / 0 of 11) and the player's move orders stay (3 of 3).
  - The engine lets a player command the units of an AI team of their own ally team.
  - Because the official game has no such gadget, a room with such a computer plays with the extra game: `syncPveGame` (after `ADDBOT`, `REMOVEBOT`, a leaving owner) announces it like a scenario's (`S.gameFile`, game option `lansync`, joiners fetch it from the host after a question; the checks in `updateSync` and `hookConnect` need `lansync`, not `lanscenario`), `buildScript` writes `GameType=<extra game>` and `lanpvehold=1`;
    - without such a computer, or with a scenario, nothing changes.
  - The spawners work under the game name of the extra game (units spawn).
  - Not checked: a real LAN room with two computers, and ways other than orders by which the spawners could move units.
  - Checked in the real LAN lobby too (`lan_test.ps1 -Mode pve`: host and joiner as two instances, the host adds the Raptors computer in the room, both place a start position and press ready, speed 20 until the Raptors have mobile units after their grace period): both instances load the gadget, the Raptor gadgets' orders (`player -1`) are dropped, 0 of 9-13 mobile units of the AI had an order of the AI, and the 3 move orders of the human stayed.
  - Not checked: the Scavengers in the LAN lobby, a joiner that fetches the extra game.
  - Version 21: the host serves `FETCHGAME` by hash from `S.servedGames` (every extra game it announced in this session, also one it has replaced since because the room changed) and logs `FETCHGAME refused: ... (current: ...)` when it has none; the question of the joiner names the game mode (Evolution, scenario, or an extra game) instead of always a Scavengers / Raptors AI.
- **Raptor Brood Chamber:** with a Raptors computer in the room the host adds the game option `tweakdefs<N>` to the start script (`broodOption` in `buildScript`: the highest slot from 29 down that the room does not use, the text of `LuaMenu/Config/lan_raptor_brood.txt` in base64url without padding, encoded by the widget).
  - That file is `lan_lobby\raptor_brood_defs.lua`, copied by `install_lan_play.ps1` (part of the stamp of the setup); without it the room plays without the chamber.
  - BAR's `gamedata/unitdefs_post.lua` runs the text on `UnitDefs`: it adds `raptor_brood_chamber` ("Raptor Brood Chamber"), a copy of `raptor_hive` (model, script, build picture) that grows nine raptors (swarmer, healer, kamikaze, brawler, spiker, artillery, scout, fighter, bomber; each with its own price and build time), metal 300, energy 3000, build time 6000, health 6000, +3 metal / +60 energy, the middle of the footprint open (`y`), `customparams.scriptlessbuilder` (the hive script knows no building: BAR's `unit_missing_build_scripts.lua` sets `INBUILDSTANCE`), the name through `customparams.i18n_en_humanname` / `i18n_de_humanname` (BAR's widget "Tweakdefs Custom Unit Names"), and puts it first in the build lists of the healers (T1 to T4 and the healer matriarch).
  - The option goes to every computer with the start script, so all have the same units.
  - The Raptors still lose when their queens are killed (`raptor_spawner_defense.lua`); hives and chambers do not count for the end.
  - Checked with `pve_test.ps1 -Brood -Widget zz_brood.lua`: the healer of the Raptors team builds it on the human's order, the chamber grows raptors in its middle and they walk out.
- **Start boxes** (`applyStartboxes`, `startboxOptions`): for the map and the number of teams the widget sets two game options, which the room draws (order: override, set, SPADS rectangles) and the game reads (`startbox_utilities.lua`; they are copied into the start script like every game option): `mapmetadata_startboxes_set` when the lobby's `loadStartboxesSet` knows the map, only for one or two teams (encoded by `encodeStartboxesSetModoption`), else (more teams: one box per team, evenly spread by `generatedBoxes`, the size following the distance of neighbours) `mapmetadata_startbox_override` with rectangles from the lobby's `savedBoxes` (SPADS list) or `generatedBoxes` (2: left/right 20 %, 4: corners, else boxes round the middle).
  - They are made again when the map or the number of teams changes (`S.battle.boxKey`; the number is `boxTeams()`: the teams of the room, or more when a human or a computer sits in a higher ally team; `updateServer` looks about once a second while no scenario is chosen and the game has not started) and when a scenario is removed.
  - Boxes the host draws in the room (`!bSet mapmetadata_startbox_override`) stay until the next change of map or teams.
- `buildScript` numbers the ally teams of the start script in the order of the room (not of joining), so box `i` of the room is ally team `i` of the game.
