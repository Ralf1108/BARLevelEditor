# LAN Play

Playing with computers in the same network with the multiplayer battle room of the game, without a server in the cloud and without changing the official game. Widget `LevelEditor\lan_lobby\lan_lobby.lua` for the lobby of the game (Chobby), installer `install_lan_play.ps1`. User view: [LAN Play](../docs/lan-play.md). The console lobby of the scenario packages is a different thing: [Scenarios with several players](scenario-multiplayer.md).

## 1. Parts and way in

- The lobby of the game (Chobby, a Lua program in the game) loads widgets from `data\LuaMenu\Widgets` when the lobby setting `["Chili lobby"].loadLocalWidgets` is true (`data\LuaMenu\Config\IGL_data.lua`; `VFS.RAW_FIRST`).
- `install_lan_play.ps1` copies `lan_lobby.lua` to `data\LuaMenu\Widgets\` (only when it differs) and the game widget `shared_start.lua` to `data\LuaUI\Widgets\`, sets that setting (backup of the file first, only when not set; refuses while the game or launcher runs because the lobby writes the file when it ends), and makes the junction `data\LevelEditorScenarios` → `scenario\scenarios` (the lobby cannot read folders outside the game folder). `-Uninstall` removes it. No file of the game is changed. `install_editor.bat` runs it; a failure there only prints a warning.
- **Menu entry:** `WG.Chobby.interfaceRoot.GetSingleplayerSubmenu().AddTab("LAN Play", "LAN Play", panel, nil, 1.5)` (rank 1.5: right below Multiplayer; the menu is one column). The config list of the menu is read only once when the lobby is built, so the tab is added to the finished menu and checked every second (the lobby builds its menu again at times). `WG.Chobby.GetInterfaceRoot()` is the constructor (builds a new interface); the existing one is `WG.Chobby.interfaceRoot`.
- **Login:** the lobby does not log in by itself: the widget adds an `OnConnect` listener that sends `Login`.
- **The server address of the lobby is never changed:** the lobby saves its configuration when it ends. Only the LAN connection (`lobby:Connect(ip, 8453, ...)`) goes to the LAN server; leaving a LAN game disconnects it and does what the settings window does after a server change (`lobby.host = <configured address>`, and `WG.LoginWindowHandler.TryLogin()` only if the lobby was logged in on the normal server when the LAN game began: `lanWasLoggedIn`, taken from `GetMyUserName()` in `lanConnect`; otherwise Leave Lobby would open the login window of the cloud server for nothing).
- **Player name:** `lan_name.txt` (typed on the page, only when it differs) > `Configuration.userName` (the last login) > `suggestedNameFromSteam` > "Player"; cleaned to letters, digits and `_-[]`, 20 characters; the server refuses a name that is already in the game or is "LANHost".
- **Sockets of the lobby:** TCP listen and TCP connect to any address are allowed (`TCPAllowListen` / `TCPAllowConnect` = `*`), UDP receive is allowed, UDP send is refused (`Spring.SetConfigString` at run time does not help), so everything uses TCP. The lobby has no HTTP client (LuaSocket without TLS; the file servers redirect HTTP to HTTPS): what needs the internet is done by the setup (PowerShell) or by `WG.DownloadHandler`.

## 2. The server in the host's widget

TCP 8453, the text protocol of the official lobby. The host's lobby connects to it and joins the battle; the lobby of every joiner connects to the host's address, so the official multiplayer room works unchanged.

- **Accepted addresses** (`localAddress`): 127.x, 10.x, 172.16-31.x, 192.168.x, 169.254.x, 100.64-127.x (Tailscale) and 25.x (Hamachi); every other connection is closed at once. The lobby cannot list the network cards, so these ranges stand for "the LAN". Windows asks once for the firewall (private networks); both ports 8453 (lobby) and 8452 (game, `HostPort` of the start script, `HostIP=0.0.0.0`) must be reachable.
- **Answered:** `LOGIN` (+ `ACCEPTED`, `ADDUSER`, `CLIENTSTATUS`, `BATTLEOPENED`, `JOINEDBATTLE`, `LOGININFOEND`), `PING`, `JOINBATTLE` (+ `REQUESTBATTLESTATUS`, `SETSCRIPTTAGS`, bots), `LEAVEBATTLE`, `MYBATTLESTATUS` (relayed as `CLIENTBATTLESTATUS`), `SAYBATTLE` / `SAYBATTLEEX`, `ADDBOT` / `REMOVEBOT` / `UPDATEBOT`, `WHO`, and the autohost commands the room sends as chat from the host only: `!map`, `!bSet` (game options), `!cv start` / `!start`, `!boss <name>` / `!unboss <name>` (Make Boss / Disable Boss). The founder of the battle is the pseudo user "LANHost". Scores, ratings, friends, channels and queues are not answered.
- **Short connections before login** (each answered with one line or a file, then closed): `WHO` (search for games), `COPILOT` (the numbers of the humans), `LANVER` (versions), `MAPINFO <name>`, `FETCHGAME <hash>`, `FETCHMAP <first> <count> <name>`. A game option set by the widget would be shown by the room as a text line and push its buttons away, so checks and transfers never use game options.

## 3. LAN Play page

A field "Your name", Host a LAN game, Find LAN games, an address field + Join, the list of found games (a click joins), a busy indicator under Find LAN games while a search runs (`ui.spin`: the text "Searching for LAN games" with a turning bar, set by `widget:Update`; when no search runs and none found: "No LAN game found"; with games found the list stands in that place), Leave LAN play (`ui.leave`, only visible while this computer hosts or plays a LAN game; Close then sits right of it, otherwise at the left edge), Close (class `negative_button`: the red close button of the lobby's lists; it was called Back). While the page is open and the computer neither hosts nor plays, it looks for games every few seconds: `WHO` on port 8453 at the addresses x.y.z.1..254 of the own /24 network (the lobby cannot ask for the netmask; 24 connections per frame, 8 s at most). A host does not scan, so it never finds itself.

## 4. Start of the game

`!cv start` makes the autohost "in game" (`CLIENTSTATUS LANHost 65`); every lobby in the battle then connects as for a game on a server (`ConnectToBattle`, script password from the `JOINBATTLE`). The host's lobby runs the game server: its `ConnectToBattle` is wrapped and starts `Spring.Reload` with a script built from the room (game, map, options, players with password, teams, ally teams, colours, sides, AIs, `HostIP=0.0.0.0`, port 8452). After leaving the room the player is on the LAN Play page again; the lobby is rebuilt after a game, so a marker file `lan_return.txt` (written when the widget ends during a LAN game) makes the widget open the LAN Play page then.

### Bosses (`!boss`, `!unboss`)

"Make Boss" / "Disable Boss" in the menu of a player send `!boss <name>` / `!unboss <name>` as chat. `autohostCommand` keeps the names in `S.battle.bosses` and tells the room with the BarManager line `{"BattleStateChanged":{"boss":"PlayerB,PlayerC"}}` (empty = no boss; the room sets `isBoss` from it, only if it comes from the founder); a joiner gets the line right after `JOINBATTLE`. The host is boss from the start (added when it logs in, `!unboss` on the host is refused): the lobby's Option Presets load (modoptions, bots with bonus) applies them only when `battle.bossed` is true, i.e. when the room reports at least one boss, otherwise it says "tried to apply a preset containing modoptions, but was prevented due to not being boss" and loads nothing (saving worked, loading did not). A preset also sends `!preset <x>`, `!lock`/`!unlock`, `!autobalance <x>`, `!balanceMode <x>` with the values it saved from `battle.preset` etc.: the load builds these strings by concatenation, so a value that the room never reported (nil) raised an error and loaded nothing (the real reason that loading failed while saving worked). The emulated autohost therefore reports `preset=team`, `autoBalance=off`, `balanceMode=skill` as BarManager fields at every join (`spadsState`), keeps what `!preset`, `!autobalance`, `!balanceMode` set and reports it again; `!lock`/`!unlock` are ignored (logged); `!bSet`, `!nbTeams`, `!set teamSize` and `!force <bot> bonus` it answers. A boss may use the same room commands as the host (`isBoss(c.name)`); a player who leaves is dropped from the list (`dropBoss`). Test: `lan_test.ps1 -Mode boss` (log lines `test: ... isBoss`). **Option Presets, checked in the real panel without a game** (`lan_test.ps1 -Mode preset`, version 12): the test writes a preset file, opens the lobby's panel (`WG.OptionpresetsPanel.ShowPresetPanel`), chooses the preset in its list and presses its Load button, then logs the room's values (`test: preset before / after`). Result: preset, autoBalance, balanceMode, teamSize, nbTeams, the map, the start boxes, a computer with its bonus (`!force <name> bonus`), the modoptions (`startenergy`, `startmetal`) and the lock are taken over. `!lock` / `!unlock` were ignored by the room until version 12: they set `S.battle.spads.locked`, reported to the lobby as field `locked` of `UPDATEBATTLEINFO` (the lobby reads `battle.locked` only from there, not from BarManager); the room itself stays open for joiners. A preset file written by hand needs the start boxes as `{left, top, right, bottom}` (scale 0-200), otherwise the load stops in `AddStartRect` with an error after the first settings (that was an error of the test file, not of the lobby). A preset without start boxes while it has multiplayer settings is not handled by the lobby (`#presetRectangles` of nil, an error of the panel's own code, `multiplayer and presetMPBattleSettings == nil` only). Presets saved before version 9 have a "Multiplayer Battle Settings" block without `preset` / `autoBalance` / `balanceMode` (the room did not report them then): the lobby's load raised `attempt to concatenate field 'preset' (a nil value)` (`gui_optionpresets_panel.lua`, line 147) and loaded nothing (reproduced with the preset file of a user: `lan_test.ps1 -Mode preset -PresetFile <optionsPresets.json> -PresetName <name>`). Version 13: `repairPresetFile` (before hosting) puts the missing values (`team`, `off`, `skill`) into `optionsPresets.json` by a text edit, the rest of the file stays. Checked with two presets of a user (map, team size, teams, computers with bonus, modoptions, start boxes loaded).

### Teams and start boxes (`!nbTeams`, `!set teamSize`, `!balance`)

The room's buttons "N teams" and "N per team" only send chat commands to the autohost and change nothing by themselves: they wait for the autohost to report the new value, as SPADS does. The widget therefore answers (host only, not while a scenario is selected):

- `!nbTeams N` / `!set teamSize N` (1 to 16): stored in `S.battle.nbTeams` / `teamSize` (start 2 and 2), reported to everybody as the BarManager line `SAIDBATTLEEX LANHost * BarManager|{"BattleStateChanged":{"nbTeams":"3","teamSize":"2"}}` (the room takes it only from the founder) and as the chat line `Global setting changed by <host> (nbTeams=3)`, which makes the room refresh its boxes and ask `!balance`. A joiner gets the BarManager line right after `JOINBATTLE`.
- `!balance` (`balanceTeams`): non-spectator humans (host first, then in joining order) and computers get the ally teams 0 .. nbTeams-1 one after the other; the new status goes out as `CLIENTBATTLESTATUS` / `UPDATEBOT`.
- `!force <name> team <N>` (menu entry "Change Team" of another player; N counts from 1) and `!force <name> bonus <N>` ("Add Bonus", the handicap): `forceCommand` changes the ally team / handicap of that human or computer (host or boss only, like all commands) and sends `CLIENTBATTLESTATUS` / `UPDATEBOT`; with a scenario the ally team stays the scenario's (`forcedStatus`). A player can change their own team without it (the lobby sets their own status).
- **Network limits of the host:** the game server runs inside the host's game, so the host's own limits apply to every player (`LinkOutgoingBandwidth` 192 KB/s by default, `LinkIncomingSustainedBandwidth` / `PeakBandwidth`, `LinkIncomingMaxPacketRate`); a server in the cloud has much higher ones. Before `Spring.Reload` the host writes higher values into `springsettings.cfg` (`Spring.SetConfigInt(name, value)`, only when the stored value is lower; 4 MB/s out, 4 / 8 MB/s in, 4096 packets). The first try with the config overlay (this run only) may not have counted, because the engine may read these values only at its start: the saved values count from the next start of the game. Meant against the many messages "Player is lagging behind" / "caught up" in LAN games. Not verified in a game: whether the bandwidth was the cause (other causes: a slow computer of a player, a VPN with delay, the host's computer busy with its own game).
- **Scavengers / Raptors AI in the room:** the computer is written to the start script as chosen (`ScavengersAI` / `RaptorsAI`; the game's Scavenger / Raptor mode needs a team with such a Lua AI, `teamfunctions.lua`, and a `NullAI` there spawns nothing: tried, reverted). The AI is only the spawner; the humans of its ally team command its units. The order stop works only for an AI that has a human player (not a spectator) in its ally team (`hasHuman` in `lan_pve_hold.lua`, read at the start of the game); the room tells everybody about it (version 11, `pveHumanNotice` in `lan_lobby.lua`, checked once a second in `updateServer`: a chat line from the host when the first human comes into the ally team of such a computer or the computer is added to a team with a human, and another when the last human leaves it or the computer is removed; log: `pve notice`); an AI alone in its ally team stays as the game has it (the gadget removes itself, checked: no order dropped, no `[LAN] the orders ... are dropped` line). To stop the AI's own orders the gadget `lan_pve_hold.lua` (in the extra game of the scenarios, switched on by the game option `lanpvehold=1`) drops, in `AllowCommand`, every order that Lua code gives to a unit of a team with a Lua AI containing `Scavengers` / `Raptors` without a player behind it (`playerID` -1, `fromSynced`/`fromLua`: the orders of the Scavenger and Raptor gadgets). Orders of players pass, also those that other gadgets pass on for a player (they keep the player number; seen in the log: order 34571 with player 0 and `fromSynced`); state switches (fire state, move state, repeat ...) pass. Tried and dropped: `fromSynced` alone (also dropped the orders other gadgets derive from a player's order, nobody could command the units) and the call stack (`debug` is an empty table in synchronized code). The first 30 orders to such units are written to the log (`[LAN] order ... player, fromSynced, fromLua -> dropped / allowed`). Checked with `test-data\tools\pve_test.ps1` (a sandbox game with a human, the AI in the human's ally team and an enemy team): Raptors and Scavengers without the option: all units of the AI have an order of the AI (8 of 8) and a player's move order may be overwritten; with the option: none (0 of 10 / 0 of 11) and the player's move orders stay (3 of 3). The engine lets a player command the units of an AI team of their own ally team. Because the official game has no such gadget, a room with such a computer plays with the extra game: `syncPveGame` (after `ADDBOT`, `REMOVEBOT`, a leaving owner) announces it like a scenario's (`S.gameFile`, game option `lansync`, joiners fetch it from the host after a question; the checks in `updateSync` and `hookConnect` need `lansync`, not `lanscenario`), `buildScript` writes `GameType=<extra game>` and `lanpvehold=1`; without such a computer, or with a scenario, nothing changes. The spawners work under the game name of the extra game (units spawn). Not checked: a real LAN room with two computers, and ways other than orders by which the spawners could move units. Checked in the real LAN lobby too (`lan_test.ps1 -Mode pve`: host and joiner as two instances, the host adds the Raptors computer in the room, both place a start position and press ready, speed 20 until the Raptors have mobile units after their grace period): both instances load the gadget, the Raptor gadgets' orders (`player -1`) are dropped, 0 of 9-13 mobile units of the AI had an order of the AI, and the 3 move orders of the human stayed. Not checked: the Scavengers in the LAN lobby, a joiner that fetches the extra game.
- **Start boxes** (`applyStartboxes`, `startboxOptions`): for the map and the number of teams the widget sets two game options, which the room draws (order: override, set, SPADS rectangles) and the game reads (`startbox_utilities.lua`; they are copied into the start script like every game option): `mapmetadata_startboxes_set` when the lobby's `loadStartboxesSet` knows the map (encoded by `encodeStartboxesSetModoption`), else `mapmetadata_startbox_override` with rectangles from the lobby's `savedBoxes` (SPADS list) or `generatedBoxes` (2: left/right 20 %, 4: corners, else boxes round the middle). They are made again when the map or the number of teams changes (`S.battle.boxKey`) and when a scenario is removed. Boxes the host draws in the room (`!bSet mapmetadata_startbox_override`) stay until the next change of map or teams.
- `buildScript` numbers the ally teams of the start script in the order of the room (not of joining), so box `i` of the room is ally team `i` of the game.

## 5. Floating buttons in the room

Copilot and Custom Scenario are children of the middle column of the room (the parent of the labels "Update Ready" / "Map Ready"), at the bottom end of the column, anchored with `x`, `right`, `bottom` (made so in `ensureScenarioUi` / `ensureSlotUi`, moved into the column once by `roomPlace`), so they follow every size of the column and the advanced options above do not cover them; as floating buttons at the top left they were hidden behind the lobby's windows. The lobby builds the room again at times, so the column is looked for once a second and a field set on it (`lanButton272`; the controls are proxies, no `==`) tells whether the buttons are already in it. The lists are windows over the team list (a window in the main window was not drawn), made new at every click. The column is about 380 wide in a 4K window and about 160 in an HD window: button width = column - 10, small font in a narrow column, help text as tooltip. The room is repainted only when the mouse moves.

## 6. Copilot

A button for the host (below Custom Scenario): numbers per human inside an ally team, the same number = one player together.

- Kept as `c.slot` of the connection on the server of the widget (not in the battle status: the lobby would fight it). `effectiveSlots` (default = place in the team, a chosen number overrides it, so the one who takes the number of another joins them and the other keeps their), `nextSlot`, `sharedGroups` (pure functions between `-- SHARE-BEGIN` and `-- SHARE-END`, loaded by the test of the Level Editor), `cycleSlot` (chat line to the room). The list sorts the humans like the default numbers, the chat line and the start script.
- `buildScript` makes one team of the start script for every "ally:number" group of humans, puts the host first (player 0) and uses `StartPosType=0` when a shared team exists, 2 otherwise (a game widget starts such a game: `shared_start.lua`, [Scenarios with several players](scenario-multiplayer.md), "Player numbers and Copilot").
- Joiners see the Copilot list read only: they ask `COPILOT` every two seconds and get `name~ally~number|...`.
- Test hook: `widget.DebugShare` lets the Level Editor test load the file in a stub environment.

## 7. Custom Scenario

A floating button for the host at the top left of the room (only while the LAN room is open). Scenarios come from `data\LevelEditorScenarios` (`VFS.SubDirs`, `scenario.txt`).

- A choice sets the map (`UPDATEBATTLEINFO`), tells the clients through the game option `lanscenario`, and forces the ally team of every player to the one of the scenario's first player (status codes decoded and encoded as the lobby does: ready bit 1, team bits 2-5 and msb 2-5, ally bits 6-9 and msb 12-15, player bit 10, handicap bits 11-15 and msb 0-1, sync msb 6-7, side msb 8-11; the corrected `CLIENTBATTLESTATUS` goes to everybody, also the sender; spectators stay). The room still shows its team controls, the server undoes a change. `!map` (an official map) drops the scenario.
- The start script is the scenario's own with `__GAMETYPE__` = "Level Editor Scenarios <version>" ([Scenario builder](scenario-builder.md)), `__PLAYERNAME__` = the host, every other human as a further player in the team of player 0 (`Password` from the lobby, spectators as spectators), `hostip=0.0.0.0`, `hostport=8452`, `numplayers` / `numusers` corrected.
- **Human against human:** a scenario with `ctfconfig` or `rtfconfig` (and an AI team as the opponent) keeps the ally teams of the room. `selectScenario` marks it `versus` and remembers the opponent team (the team of its `[ai]`); `forcedStatus` then only corrects the first status of a joiner (they get the other ally number once, afterwards they may choose); `buildScenarioScript` puts every human with another ally number than the host into the opponent team, removes the AI of that team and makes the first human its `TeamLeader`. Tower Defense and the other scenarios put all humans into the team of the first player (cooperative against the AI).

## 8. Same versions everywhere

**Lobby and game widget.** At every join (scenario or official map) the host answers `LANVER` (before the login, like `COPILOT`) with `<lobby>|<shared>|<number>|<date time>`: the first two are the first 8 characters of `VFS.CalculateHash` of `LuaMenu/Widgets/lan_lobby.lua` and `LuaUI/Widgets/shared_start.lua` (carriage returns removed, `-` when missing), the last two are `LAN_VERSION` at the top of `lan_lobby.lua` (a number raised when the network protocol or the logic of the two files changes, with date and time; a change of the looks alone does not raise it; the message says who is newer). The joiner compares once per join and logs `version check: same ...` or `DIFFERENT, host ..., own ...`. Only the version number decides: with equal numbers the joiner logs "same version number" even if the file hashes differ (a change of the looks), and no window opens. On a different number exactly one message window (`bigPopup`, 640x360, with OK) names the file that differs and asks to update the Level Editor on all computers. A host that sends no `lanver` (an older lobby) gives the same warning after 4 s. It is a warning, not a lock. Nothing is replaced: the lobby widget is never fetched from the network.

**The extra game of a scenario.** The host announces version, hash and size of its own extra game (the one named in `games\LevelEditorScenarios.txt`; game option `lansync` = `<version>|<hash>|<size>`, hash by `VFS.CalculateHash`). A joiner who has that version (`VFS.HasArchive("Level Editor Scenarios <version>")`) uses it; one who has not is asked (a confirmation popup: the file holds gadgets of the scenarios, only from a host you trust). On yes they open a second connection and send `FETCHGAME <hash>`; the host answers (after the usual greeting line) `SIZE <n>` and the bytes, 64 KB per frame. The joiner takes at most the announced size (at most 4 MB), checks size and hash, writes `games\LevelEditorScenarios_<version>.sdz.part` and renames it (a version that is not 8 hex digits is refused; their own version is never replaced), calls `VFS.ScanAllDirs()`. The start of the game waits for it (`ConnectToBattle` is postponed); declined or failed: no start for them, with a message. A host without a version in `lansync` (an older editor) gets "please update the Level Editor manually". It logs `scenario game check: same version as the host ...` or `... different`.

## 9. The map of the room

A joiner who has not got the map of the room (`VFS.HasArchive`, the name from `battles[1].mapName`) asks the host at once. The lobby would start its own online download as soon as it knows the map: the widget holds that call of `WG.DownloadHandler.QueueDownload` back until it is known where the map comes from, drops it when the map comes from the host and lets it through when it does not (after 30 s at the latest).

- `MAPINFO <name>` is answered with `<size>|<md5 base64>|<file>` or `none`. The host serves only the map of its room, only a `.sd7` / `.sdz` file of `maps\`, at most 300 MB (size and md5 are worked out once, reading in 64 KB chunks). Maps that are folders (`.sdd`) are not served.
- **The list of official maps:** the setup (full run of `install_editor.ps1`, `Update-MapHashes` in `shared\bar_common.ps1`) fetches `https://maps-metadata.beyondallreason.dev/latest/live_maps.validated.json` (about 60 KB, `springName` / `fileName` / `md5`) and saves it as `data\games\LevelEditorMapHashes.txt` (`# etag=`, `# fetched=`, then `<spring name>|<md5>`). The next setup asks with `If-None-Match` and gets a 304 when nothing changed; offline or on any error the old list stays.
- **Decision:** the md5 of the host equals the official one → fetched from the host at once, no question, no online traffic (the received file is hashed anyway and must give that md5). Different → a window warns (host or list out of date, or a changed map) and asks. Not in the list or no list (own maps, offline setup) → a window asks and says the md5 is only the host's word. The window offers **From the host** (over the LAN) or **Online** (the lobby's own download, which `pr-downloader` checks against the official checksum).
- **Transfer:** the file is cut into blocks of 64 KB and fetched on 8 connections at once (`MAP_STREAMS`, all to port 8453): every connection sends `FETCHMAP <first block> <count> <name>`, the host answers `BLOCKS <first> <count>`, the blocks (up to 4 MB a frame) and closes; the joiner writes every run at its place in `maps\<file>.part`. Size and md5 are checked, then it is renamed and `VFS.ScanAllDirs()` makes the game know it. A failed check deletes the part file and lets the lobby download the map online. The start of the game waits for the map.
- **Why blocks:** a Lua widget moves about one buffer (64 KB) per connection and frame: one connection gave 1.7 MB/s (69 MB in 41 s), 8 give about 10 MB/s (69 MB in 7 s). The lobby's Lua counts a file 3 bytes longer than it is (`#`, `seek`, `read("*a")`: 69333408 against 69333405; content and md5 are right), so the transfer is in blocks, not in bytes.
- Test keys: `noOnline=1` in `lanlobby_cfg.txt` (the lobby cannot download), `lan_test.ps1 -NoMap`.

## 10. What goes over the network

- **Two kinds of files, never more:** the extra game of the scenarios (`LevelEditorScenarios_<version>.sdz`: only Lua files, at most 4 MB) and the map of the room (`.sd7` / `.sdz` from `maps`, at most 300 MB). No PowerShell, no batch file, never the lobby widget itself or any other program: updates of the Level Editor are done by the players (git pull, or copy the folder and run `install_editor.bat`). The host serves only the map of its room and its own scenario game.
- **Trust:** the checks (size, hash, md5) prove that a file is the one the host announced, not that the host is honest. A map that is not in the official list and the extra game of a scenario are taken on the word of the host after a question. The Lua gadgets of a scenario run in the game of every player, so use LAN Play with hosts you trust.

## 11. Tests and findings

Two real lobbies in sandbox instances on one computer (pictures of the room: `lan_test.ps1 -Shots`, with `PrintWindow` flag 2; a copy of the screen or `gl.SaveImage` come out black); the mode `teams` presses the buttons "N teams" / "N per team" of the room (`teams=`, `teamSize=` in `lanlobby_cfg.txt`) and logs what the lobby knows (`nbTeams`, game options, ally teams, the middle column with `dump=`); `lanlobby_cfg.txt` in the write dir drives them (`auto`, `name`, `map`, `players`, `ip`, `openTab`, `clickFirst`, `leaveAfter`, `scenario`, `startDelay`, `noOnline`); tools `test-data\tools\lan_test.ps1` (the widget) and `console_test.ps1` (the console lobby); details and pitfalls: `test-data\TESTING.md`. Each game instance needs 8-10 GB of RAM: tests run with the host plus one joiner. Checked: join and scan, room, chat, map and start through the room's own Start call, two players loaded the game, leaving returns to the LAN page, the normal lobby is unchanged without the widget, scenario choice and transfer of the extra game, map transfer with all list cases, version warning, Capture the Flag (2:0 on both computers), Reclaim the Fame (1564 : 1638 on both), Tower Defense (both humans in one team, won), Copilot through the real lobby into the game.

Findings behind the design: the menu button positions (Multiplayer y 171, LAN Play y 245, Skirmish y 319 in the test window); `read("*a")` and `seek` of a file in the lobby return 3 bytes too many (the widget reads in 64 KB chunks); messages longer than a line need their own window (`bigPopup`; the lobby's `InformationPopup` is too small); changing the server address of the lobby once made the official games disappear from the normal Multiplayer.

**Rejoin (version 14).** A player whose game ended or crashed while the room's game runs comes back with LAN Play (same name) and finds the room in the state "game running": the room reports the host as in game (`CLIENTSTATUS <host> 65` at the login once `S.battle.running`), so Chobby shows the **Rejoin** button instead of Start. The room keeps team, color and script password of a leaver while the game runs (`S.rejoin[name]`) and gives them back at the new join (`JOINEDBATTLE` announces the old password; the game server knows only the one of the start script: with a new one the engine says "Connection rejected: Incorrect password"); no new team is chosen (`placeNewPlayer` is skipped). The engine of the host takes the player back by the name in the start script; the game is caught up by re-simulation. Checked with `lan_test.ps1 -Mode rejoin` (two instances, the joiner's game killed after 40 s, started again, Rejoin clicked: "PlayerB has finished resuming" at the host, frame 4500 reached by both). A player who is not in the start script cannot join a running game (open: joining as a new player).

**Late join as a new player (version 15).** The host switches it on in the room before the start with the chat command `!latejoin on` (`off` takes it back; host or boss; `S.battle.lateJoin`). The room then plays with the extra game of the scenarios (like with a Scavengers / Raptors computer: `needsExtraGame()`, `syncPveGame`, game option `lansync`) and the start script gets `AllowAdditionalPlayers=1;` and the game option `lanlatejoin=1`. A name that is not in the start script then connects to the running game server: the engine adds it as a spectator with a `~` in front of the name (`added new player ~PlayerB with number 1 to team 0`). The gadget `lan_latejoin.lua` (in the extra game) makes it a player: its unsynchronized part sends the game message `lanlatejoin` once for a spectator whose name starts with `~` (`SendLuaRulesMsg`); the synchronized part (`RecvLuaMsg`) assigns it with `Spring.AssignPlayerToTeam` to a team: the ally team with the fewest human players, there the team with the fewest players (the newcomer plays it together with them, as in Copilot; no new commander is created). The choice uses only state of the game (spectator flags, team lists), no network state, and the message is executed at the same frame on every computer: **a first version decided in `PlayerAdded` / `GameFrame` from the player list; the late joiner, which has the whole list from the start, did not make the call in its own simulation and stayed a spectator there (`SPEC` in the log) while the host had that player as a player.** Without late join the room says in the chat that the new name is not taken (`!latejoin on` before the start). Checked with `lan_test.ps1 -Mode latejoin` (host alone, the joiner comes 40 s after the placement, presses Rejoin): both computers show `~PlayerB(p1 team0 ally0)` as a player from the same frame, the commander of team 0 is seen by the newcomer, frame 4500 reached, no desync message. Not checked: that the newcomer's orders move the units (the test gives none), more than one newcomer, a newcomer in a game with computers only, a long game (catching up), a new commander for a team of its own (not built: the teams of a game are fixed by the start script).

**Raptors against Scavengers (extra game).** The game switches both spawners off when a Raptors and a Scavengers AI are in the same game (`raptor_spawner_defense.lua`: `IsRaptors() and not IsScavengers()`, `scav_spawner_defense.lua` the other way round; `snd_notifications.lua` says "leave the match"). `Write-ScenarioGame` therefore puts changed copies of these three files into the extra game (`$ScenarioGameDerived` in `shared/bar_common.ps1`: the text is read from the installed game by `Get-GameFileText` (package list .sdp, pool file), the lines are replaced, a changed text of the game skips the file with a note; the copies are part of the version hash of the extra game). A second change is needed: the Scavenger waves only start when `GG.PowerLib.TotalPlayerTeamsPower()` is above 0 (otherwise `Wave()` returns at once, `dynamicDifficultyClamped` stays nil, the log says `dynamicDifficultyClamped:  nil`); in the room the humans play the teams of the computers, the Raptors team is not counted as a player team, so the sum is 0 and no Scavenger unit spawns (only beacons and the boss). The copy of the Scavenger spawner adds the power of the Raptors team. Checked in a LAN room (`lan_test.ps1 -Mode mix`: PlayerA with Raptors, PlayerB with Scavengers, both humans in the team of their computer): both computers spawn (after 30000 frames Raptors 180, Scavengers 141 units), `dead:RaptorsAI by ScavengersAI` is logged, difficulty 1.05. The area healer gadget (`pve_areahealers.lua`) heals the units of one computer team only (the Raptors'): its copy in the extra game heals the Scavengers' team too (it loads without an error in the room; whether the Scavenger healers heal was not measured). The builder and nuke gadgets (`pve_builder_controller.lua`, `pve_nuke_controller.lua`) take the Scavenger team id and work in a mixed game, but with a human in the team `lan_pve_hold.lua` drops their orders (the human builds and fires itself). Not checked: the end of such a game, the Scavenger boss, a human in a team of its own next to the two computers. `lan_test.ps1 -Mode mix -Play` starts the two instances for a game to play (no test widgets, no speed-up; the two start positions are clicked by the script).

Not checked: the look of the menu entry, the page, the Custom Scenario button and list, and the room with forced teams; real clicks (the tests call the same functions); two computers; three or more players; declining a transfer or a failing transfer; the answer "Online" of the map window; the briefing widget and units of a scenario in a LAN game; the scenario's AI in the room (open: it is not shown there).
