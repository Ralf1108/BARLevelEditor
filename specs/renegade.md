# Renegade

A game mode in the making (first test, one human against computer units; not yet in the LAN Play room): every human steers **one original BAR unit in the first person** (mouse look, W A S D, crosshair, three mouse buttons for the weapons), like the units of a real-time strategy game played as a shooter (named after C&C Renegade). Models, speed, weapons, range, armor and damage stay those of the game; the engine does movement, collision, weapons, projectiles and damage, Lua only sends the intent. User view: [Renegade manual](../LevelEditor/game-modes/renegade.md), the weapon table: [renegade-weapons.md](../LevelEditor/game-modes/renegade-weapons.md). Related: [Evolution](evolution.md) (one unit per player, same gadget pattern), [LAN Play](lan-play.md).

Rules of thumb: local things stay local (camera, mouse, crosshair, HUD: a game widget); everything that changes the game goes through the synchronized gadget (`Spring.SendLuaRulesMsg` -> `gadget:RecvLuaMsg`), so every computer simulates the same game. Scaling target (long term, not promised): 1 -> 2 -> 4-8 -> 20-40 players, measure network load, latency, sim rate and desyncs before going further; hundreds of players are not a goal of the first steps.

## 1. Parts

| Part | File | Job |
|---|---|---|
| Game widget | `LevelEditor/scripts/renegade.lua` (`luaui/widgets`) | camera on the eye of the unit, mouse and keys, crosshair, ray, HUD, anti-air circle, debug menu, sends the input |
| Gadget | `LevelEditor/scripts/renegade_game.lua` (`luarules/gadgets`) | unit of every human, moving, shooting (the buttons), respawn, energy, bots, debug messages |
| Weapon table | `LevelEditor/game-modes/renegade_weapons.csv` (source), `renegade-weapons.md` (made from it) | which weapon of which unit is fired with which button |
| Table tools | `test-data/tools/renegade_weapons.py`, `zz_weapondump.lua`, `game-modes/update_renegade_weapons.bat` | table <-> `renegade_game.lua` |
| Start | `LevelEditor/start_renegade.bat`, `scripts/start_renegade.ps1` | a game at once (see 2) |
| Lobby | `lan_lobby.lua` | not done: button and game option like `lanevolution` (needs a `LAN_VERSION` bump) |

Widget and gadget are in `$ScenarioGameFiles` (`shared/bar_common.ps1`) together with `editor_common.lua` and `area_attack.lua` (the unit menu of the debug mode; `Get-EditorGameEntries` in `editor_manifest.ps1` skips what the extra game "Level Editor" has already). Tests: sandbox `test-data/tools/pve_test.ps1 -Ren [-RenTest] [-RenBots n] -Widget zz_ren*.lua` (section 7).

## 2. Game options and start

- `lanrenegade=1`: the mode (gadget and widget load only with it). `lanrenebots=<n>` (0 to 30): computer Peewees that hunt the players. `lanrenedebug=1`: the debug menu (turn into a unit, spawn an enemy). `lanrenotest=1`: test hooks (section 7).
- **Quick start:** `LevelEditor\start_renegade.bat [map] [AI] [bots]` (default `Hooked 1.1`, `NullAI`, 3 bots) runs `ensure_installed.ps1` and `scripts\start_renegade.ps1`, which writes `LevelEditor\renegade_script_installed.txt` (ignored by git) and starts the engine on it: you in team 0 (Armada), the computer player in team 1 (Cortex), options `lanrenegade=1; lanplay=1; deathmode=neverend; lanrenebots=<n>; lanrenedebug=1` (`-DebugMode 0` without the debug menu). Do not change the bat file while the game runs (cmd reads it by position).

## 3. Messages and parameters

Widget -> gadget (`SendLuaRulesMsg`; the sender's team must own a unit):

- `ren|<yaw>|<pitch>|<keys>|<fire>|<x>|<y>|<z>|<unit>`: the view in whole degrees (yaw 0 looks along +z, 90 along +x), keys W 1, A 2, S 4, D 8, `fire` bits left 1, right 2, middle 4; while firing the point under the crosshair and the unit there (an aircraft in the anti-air circle: the lock) or -1. Sent at once when keys or buttons change, otherwise at most every 3 frames and only when the text changed.
- `ren|unit|<name>`: debug, turn into that unit. `ren|spawn|<name>`: debug, an enemy of that kind. `ren|test|1`, `ren|test|2`, `ren|test|3`: `lanrenotest` only.

Parameters (gadget -> widget): team rules `renUnit` (the unit, 0 = none), `renRespawn` (frame of the return after a loss, 0 = alive); unit rules `renSlots` ("left;right;middle", each a comma list of weapon numbers), `renAA` and `renHY` (comma lists, section 5.3).

## 4. The widget (`renegade.lua`)

- **Camera:** the engine camera `fps`, set every frame (`Update`) by `Spring.SetCameraState({name = "fps", mode = 0, oldHeight = 0, px, py, pz, rx, ry, rz}, 0)`. **The direction comes from `rx` and `ry`, not from `dx, dy, dz` (ignored):** `rx = pi/2 - pitch`, `ry = pi - yaw`. Without `mode` and `oldHeight` the engine fell back to the `spring` camera; `free`, `ta` and `spring` did not take over by name. Eye = `GetUnitViewPosition` + 0.85 x `GetUnitHeight`. The own unit is hidden (`SetUnitNoDraw`) and unselectable (`SetUnitNoSelect`; otherwise the screen ray answered with the own unit in many directions and a click selected it); the selection is cleared (`SelectUnitArray({})`) so the game draws no range rings.
- **Mouse and keys:** each frame the cursor is read (`GetMouseState`) and warped to the middle (`WarpMouse`); the way it moved is the turn (`SENS` 0.15 degrees per pixel, mouse up = look up, right = yaw down), the cursor is "none". `MousePress`, `MouseRelease` and `MouseWheel` return true while the view is on (the RTS does nothing), W A S D too. The buttons are read every frame as well (a lost release must not keep the unit firing). **Tab** (debug menu: free mouse, no look, no steering, no fire) is polled with `GetKeyState(9)`: as a commander the press never reached `KeyPress` (the game's own use came first). **Insert** or `/renegade` switches the view off and on; `/renegade log` writes the camera state, `/renegade flip` turns the yaw offset by 180 degrees.
- **Ray (`aim`):** `TraceScreenRay(middle, false, false, true)` gives `"unit", id` or `"ground", {x, y, z}` (the table also with `onlyCoords`). The engine answered "sky" for slopes of the heightmap (ground 337 to 560 Elmo away at pitch 3 degrees), so `march` follows the view ray over `GetGroundHeight` in steps of 24 Elmo (bisected at the hit, inside the map only); mountains outside the map have no heightmap and stay "sky". `R.hit` = unit or ground point, distance from the eye and from the unit (`udist`); `R.shot` = `R.hit`, or a point 3000 Elmo along the ray in the sky.
- **Crosshair:** four lines; green when `R.hit` is within the range of the left button group (`udist`), red when not, white for the sky; text under it: "Pawn 100%  151 m  IN RANGE" / "ground  84 m  OUT OF RANGE (180)" / "sky".
- **Anti-air circle (`aaPick`):** shown when the unit has weapons in `renAA` or `renHY`: an orange circle of 15 % of the screen height (`AA_RADIUS`) round the crosshair. Of the visible enemy units (`GetVisibleUnits(ENEMY_UNITS)`) that fly (`canFly`), are in front of the camera and within the longest range of those weapons, the one whose picture (`WorldToScreenCoords`) is nearest to the middle inside the circle is the lock `R.aaTarget` (an orange square and "AA LOCK <name>"); with a lock the circle **glows** (bright yellow, 3.5 pixels, three wider translucent rings that pulse). The lock is the `unit` of the message.
- **Panel (`panel`):** right of the middle at the bottom (the game's buttons are left of it): the health bar (red to green, "HEALTH 370 / 370"), then one row per button group: description of its weapon ("x3" for several), tag LMB red / RMB yellow / MMB green, range (the longest of the group), reload time, READY / reloading and a bar in the color of the button (from `reloadFrame` and `reloadTime` of the first weapon); "(anti-air: aircraft in the circle)" or "(aircraft in the circle: lock; ground: aim)" for those groups. The groups come from `renSlots` (cached by the three parameter texts: a Pawn and an anti-air turret both have "1;;").
- **Rings and barrel lines (`DrawWorld`, depth test off, thickest first):** for each group a ring (`gl.DrawGroundCircle`) of its range and a line on the ground from the unit in the direction its barrel points now (`GetUnitWeaponVectors` of the first weapon: straight up while it is not aiming, then the aim direction; a nearly vertical direction is replaced by the unit's facing; at most 260 Elmo): you look round faster than the turret turns, fire when the line points where you look. Left red 3 pixels, right yellow 5, middle green 7, so all show when they lie on each other. The lines were not seen on a picture yet.
- **Loss:** while `renRespawn` is in the future "YOU DIED" and "respawn in 5" ... "1" in big letters (`countdown`, also without the view); the view comes back by itself when the unit appears.
- **Debug menu (`lanrenedebug`):** above the panel two buttons: "Spawn enemy v" and "Debug unit: <name> v". A click (with the mouse free, Tab) opens the unit menu of the Level Editor (`Shared.newUnits` of `editor_common.lua`, loaded by `VFS.Include("luaui/Include/editor_common.lua")`): search field (`ownText`, `widget:TextInput`; Enter = done, Esc = clear, Tab leaves), rows faction (Armada, Cortex, Legion), group (Turrets, Bots, Vehicles, Hover, Air, Ships), tech level, the pictures of the units that have a weapon, the mouse wheel scrolls, no 3D preview. In the mode of "Debug unit" a click on a picture sends `ren|unit|<name>` and leaves the menu; in the mode of "Spawn enemy" (`R.pickMode = "enemy"`) it sends `ren|spawn|<name>` and the menu stays open.
- Test hooks: `WG.renegade` is the state table (`fake` = the test widget steers: yaw, pitch, keys, fire; `menu`, `list`, `pickMode`, `hit`, `shot`, `aaTarget`, `aaCircle`, `unit`).

## 5. The gadget (`renegade_game.lua`)

### 5.1 Units, moving, respawn, energy
- **Units:** from frame 30 to 300 every team with a human and a commander gets an `armpw` at the commander's place instead (`take`, `giveUnit`; fire state hold fire: the unit shoots only what the player aims at). `units[team]`, `kind[team]`, `input[team]`.
- **Moving:** `steer` gives `CMD.MOVE` to a point 200 Elmo ahead in the wished direction (forward `(sin yaw, cos yaw)`, right `(-cos yaw, sin yaw)`; again after 10 frames or when the direction turns by more than 6 degrees), `CMD.STOP` when no key is down. No `MoveCtrl`. W, A, S, D move the unit the right way (measured: 211 and 327 Elmo in about 4 s game time); pathfinding decides at cliffs, aircraft and ships are not steered specially.
- **Respawn:** a lost unit of a player comes back after 150 frames (`RESPAWN`) as the same kind, at a place far from the enemy units (`place`: of 24 random places where the unit can stand, the farthest; a second pass without the movement test for ships on land and turrets; none: the place where it was lost; creating fails: again after a second). No score, no teams yet.
- **Energy:** every second each player team gets 500 energy (`ENERGY`, `AddTeamResource`) and a storage of 20000 (`SetTeamResource "es"`): the lasers need much (test setting).
- **Bots (`lanrenebots`):** at frame 120 `n` Peewees of the first team without a human (`botTeam`) appear on the land at about 800 Elmo from the nearest player unit (`place`); every 120 frames each bot gets `CMD.FIGHT` to a point within 150 Elmo of the nearest player unit; a lost one comes back after 150 frames. On Hooked they need about 40 s of game time to arrive (the way round the rim is long).

### 5.2 Shooting and the three buttons (`shoot`)
Like in a shooter, never a "target". While a button is down every weapon of its group gets the point the player aims at (`Spring.SetUnitTarget(unit, x, y, z, false, true, weaponNumber)`, a user target), shortened along the line from the unit to the point to the reach of that weapon (`shortened`), so it fires toward the crosshair where nothing is in reach, into the sky, at far mountains. An enemy unit under the crosshair is not chosen as a target (the earlier unit target made the weapon wait; the point does not); only the anti-air lock is (5.3). The target is set at once when the message arrives (`RecvLuaMsg` calls `shoot` with force) and renewed every 3 frames. **One click is one shot:** a weapon keeps its target while its button is down (continuous fire, as fast as it reloads); when the button goes up before the weapon has fired (the turret was still turning, the weapon was reloading) the target stays until the weapon has fired (its `reloadFrame` changed) or its time is up (45 frames plus the reload time, at most 8 s; `inp.hold` per weapon in `shoot`), then it is cleared; a weapon that has fired is let go at once. A target set for one weapon number stays after `SetUnitTarget(unit, nil)`, so clearing is a stop order (`clearTargets`; the steering gives its move order again), after which the weapons still held get their targets again. Measured with `zz_ren14.lua` (a click of 3 frames, the aim far behind the facing): Pawn: the target was still set 10 frames later, the weapon had fired by 90 frames and the target was cleared; Titan laser: fired, cleared; held buttons: the reload frame advances several times (continuous fire). Before this a short click cleared the target before the turret had turned and nothing was fired. Measured (Titan, Epoch, Karganeth): each button targets only its group; after the release no weapon has a target and no reload frame changes; the weapon has its target 4 to 7 frames after the click (turret and reload are the engine's); Peewee against Peewee at 150 Elmo: 370 -> 118 health in 4 s. Every weapon can fire at a point in the air (Total Annihilation style, a hit is luck): a Pawn fired at a point 99 Elmo up, the weapon had its target and reloaded.

**Which weapon on which button (`slotsFor`, per unit definition, cached):**
- The table: the block `WEAPON_BUTTONS` (between `-- BEGIN WEAPONS` and `-- END WEAPONS`; made by `renegade_weapons.py` from the columns Group and Fire button of `renegade_weapons.csv`) lists for a unit code the weapon numbers of `L`, `R`, `M`; a Scavenger copy uses the entry of the normal unit. 497 units, 1035 weapons.
- Without an entry the rule (the python proposal is the same): weapons with the same weapon definition are one group (they fire together); dummies (no damage: footsteps, `krogweaponaim`), shields and interceptors are no weapons. Missiles (`MissileLauncher`, `StarburstLauncher`, `TorpedoLauncher`) and anti-air weapons count as missiles, all others as "others"; both are sorted by range. With both kinds: the shortest of the others on the left button, the rest of the others on the right (the missiles take the right button when there is no second one), the missiles in the middle. With one kind only: the shortest left, the next right, all further ones in the middle. Census of the units with a weapon (Scavenger and Raptor copies left out; `lanrenotest` logs it): 18 units without a usable weapon, 320 with one button, 84 with two, 124 with three: three buttons do for every unit. Titan: impulsion blaster left, long-range laser right, starburst rocket middle; Epoch: medium plasma (3 guns) left, heavy plasma (2) right, Ferret missiles (anti-air) middle; Thor: 2 EMP beams left, lightning right, EMP missile middle.
- The main weapon is no longer a concept (an earlier version had "left = the strongest, right = all others").

### 5.3 Anti-air and weapons that also hit aircraft
- `aa`: default damage <= 2 and more damage against vtol (flak, anti-air missiles). `hy`: damage against the ground and against vtol and a description with "g2a" or "a2a" (the Titan's laser and starburst: "g2g/g2a"). Both are published per unit (`renAA`, `renHY`).
- With a lock (the `unit` of the message is an enemy): `aa` weapons get it as their target (`SetUnitTarget(unit, enemy, false, true, weaponNumber)`; homing missiles), `hy` weapons only when it flies (`canFly`), otherwise the point as every weapon; `aa` weapons without a lock do not fire. When the engine refuses the unit for a weapon (the Titan starburst: `SetUnitTarget` returns false) the point where the aircraft is becomes the target. Measured: anti-air turret `armrl` against a hovering Brawler 250 Elmo ahead and 100 up: crosshair 3 degrees beside it -> lock, weapon target type 1, the Brawler lost health (1780 -> 1665 in 1.3 s), looking away: no lock, no fire; Titan laser (right button): lock, target type 1, the Brawler destroyed.

### 5.4 Debug messages (only with `lanrenedebug`)
- `ren|unit|<name>` (`turnInto`): every unit with a weapon (aircraft, turrets that stand still and shoot, ships: they lie on the land and fire) is made at the place and facing of the old one with the same share of health, the old one is removed without wreck (`units[team]` is the new one first: no respawn); groups and parameters are worked out again.
- `ren|spawn|<name>`: the unit for the first team not allied to the player, 1000 Elmo ahead of the player's view (yaw of the last message), a ground unit on the ground, an aircraft 200 Elmo above, `CMD.FIGHT` toward the player.

## 6. The weapon table (`game-modes/renegade_weapons.csv`, `renegade-weapons.md`)

- **The csv is the source** (semicolons, UTF-8 with BOM, open it in Excel and import it with "Semicolon" only as the separator, no "Space", text columns as text: "-" becomes a number otherwise): the columns Faction, Unit, Code, #, Weapon (description), Type, Target, Range, Reload, Damage, Weapon name, **Group**, **Fire button**. Group = a letter per unit (weapons with the same letter belong together, empty = no button), Fire button = LMB, RMB, MMB or empty (a group has one button: the first row of the group counts; an old "-" or "-0" counts as empty). Target = what the weapon hits: the tokens of the description (g2g, g2a, a2g, g2s ...) count first, the damage against aircraft alone does not (many ground missiles have the same damage against every armor class: Janus, Ambassador), without tokens the damage and the type.
- `game-modes/update_renegade_weapons.bat` (`renegade_weapons.py update`) writes the table into the md **only between the comment lines `BEGIN TABLE` and `END TABLE`** (the text around may be edited; a file without the markers is made whole once) and the block `WEAPON_BUTTONS` into the gadget. `renegade_weapons.py table <infolog>` makes the csv new from the dump of `zz_weapondump.lua` (`[zzwep]` lines; the Group and Fire button of rows that are in the csv are kept, new rows get the proposal); `renegade_weapons.py lua` writes only the block.

## 8. Not done and open

- **PoC 5:** two players in the LAN (host + one joiner): each steers one unit, they fight, no desync. Needs the lobby button, the game option for every player, `LAN_VERSION`, teams, one unit per human without a commander, scoring.
- **Jumping:** the engine has no jump for ground units; ideas: a short hop with `Spring.SetUnitVelocity` (the movement type may overwrite it), or `Spring.MoveCtrl` only for the duration of the jump (own ballistic curve, back to normal movement on landing), or the unit scripts (`CallCOBScript`) for the animation. To decide: how ground movement reacts to a velocity impulse, landing detection, firing in the air, determinism; the input message would get a key bit (Space = 16).
- Not checked by a human or not seen: the barrel lines on a picture, the Tab key as a commander, flying units as the player's unit (steering by move orders), whether the Titan starburst can hit an aircraft at all, how the lock feels against fast aircraft.
- Open questions: a feel for the move orders (lag, the unit's heading against the view), traffic and determinism of the messages with many players, what the lobby and team setup need.
- Not planned for the first steps: hundreds of players, an own lobby/matchmaking/dedicated server, new weapons, projectiles or damage model, full HUD, sound, animations, progression.
