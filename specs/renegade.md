# Renegade

A game mode in the making (first test, one human against computer units; not yet in the LAN Play room): every human steers **one original BAR unit in the first person** (mouse look, W A S D, crosshair, three mouse buttons for the weapons), like the units of a real-time strategy game played as a shooter (named after C&C Renegade). Models, speed, weapons, range, armor and damage stay those of the game; the engine does movement, collision, weapons, projectiles and damage, Lua only sends the intent. User view: [Renegade manual](../LevelEditor/game-modes/renegade.md), the weapon table: [renegade-weapons.md](../LevelEditor/game-modes/renegade-weapons.md). Related: [Evolution](evolution.md) (one unit per player, same gadget pattern), [LAN Play](lan-play.md).

Rules of thumb: local things stay local (camera, mouse, crosshair, HUD: a game widget); everything that changes the game goes through the synchronized gadget (`Spring.SendLuaRulesMsg` -> `gadget:RecvLuaMsg`), so every computer simulates the same game. Scaling target (long term, not promised): 1 -> 2 -> 4-8 -> 20-40 players, measure network load, latency, sim rate and desyncs before going further; hundreds of players are not a goal of the first steps.

## 1. Parts

| Part | File | Job |
|---|---|---|
| Game widget | `LevelEditor/scripts/renegade.lua` (`luaui/widgets`) | camera on the eye of the unit, mouse and keys, crosshair, ray, HUD, anti-air circle, debug menu, sends the input |
| Gadget | `LevelEditor/scripts/renegade_game.lua` (`luarules/gadgets`) | unit of every human, moving, shooting (the buttons), respawn, energy, bots, debug messages |
| Weapon table | `LevelEditor/game-modes/renegade_weapons.csv` (source), `renegade-weapons.md` (made from it) | which weapon of which unit is fired with which button |
| Table tools | `test-data/tools/renegade_weapons.py`, `zz_weapondump.lua`, `game-modes/update_renegade_weapons.bat` | table <-> `renegade_game.lua` |
| Start | `LevelEditor/start_renegade.bat`, `scripts/start_renegade.ps1` | a game at once (see 2) |
| Lobby | `lan_lobby.lua` | not done: button and game option like `lanevolution` (needs a `LAN_VERSION` bump) |

Widget and gadget are in `$ScenarioGameFiles` (`shared/bar_common.ps1`) together with `editor_common.lua` and `area_attack.lua` (the unit menu of the debug mode; `Get-EditorGameEntries` in `editor_manifest.ps1` skips what the extra game "Level Editor" has already). Tests: sandbox `test-data/tools/pve_test.ps1 -Ren [-RenTest] [-RenBots n] -Widget zz_ren*.lua` (section 7).

## 2. Game options and start

- `lanrenegade=1`: the mode (gadget and widget load only with it). `lanrenebots=<n>` (0 to 30): computer Peewees that hunt the players. `lanrenedebug=1`: the debug menu (turn into a unit, spawn an enemy). `lanrenotest=1`: test hooks (section 7).
- **Quick start:** `LevelEditor\start_renegade.bat [map] [AI] [bots]` (default `Hooked 1.1`, `NullAI`, 3 bots) runs `ensure_installed.ps1` and `scripts\start_renegade.ps1`, which writes `LevelEditor\renegade_script_installed.txt` (ignored by git) and starts the engine on it: you in team 0 (Armada), the computer player in team 1 (Cortex), options `lanrenegade=1; lanplay=1; deathmode=neverend; lanrenebots=<n>; lanrenedebug=1` (`-DebugMode 0` without the debug menu). Do not change the bat file while the game runs (cmd reads it by position).

## 3. Messages and parameters

Widget -> gadget (`SendLuaRulesMsg`; the sender's team must own a unit):

- `ren|<yaw>|<pitch>|<keys>|<fire>|<x>|<y>|<z>|<unit>`: the view in whole degrees (yaw 0 looks along +z, 90 along +x), keys W 1, A 2, S 4, D 8, `fire` bits left 1, right 2, middle 4; always (also without a button: the turret follows the view) the point under the crosshair, or a far point in the sky, and the unit there (an aircraft in the anti-air circle: the lock) or -1. Sent at once when keys or buttons change, otherwise at most every 3 frames and only when the text changed.
- `ren|unit|<name>`: debug, turn into that unit. `ren|spawn|<name>`: debug, an enemy of that kind. `ren|test|1`, `ren|test|2`, `ren|test|3`: `lanrenotest` only.

Parameters (gadget -> widget): team rules `renUnit` (the unit, 0 = none), `renRespawn` (frame of the return after a loss, 0 = alive); unit rules `renSlots` ("left;right;middle", each a comma list of weapon numbers), `renAA` and `renHY` (comma lists, section 5.3).

## 4. The widget (`renegade.lua`)

- **Camera:** the engine camera `fps`, set every frame (`Update`) by `Spring.SetCameraState({name = "fps", mode = 0, oldHeight = 0, px, py, pz, rx, ry, rz}, 0)`. **The direction comes from `rx` and `ry`, not from `dx, dy, dz` (ignored):** `rx = pi/2 - pitch`, `ry = pi - yaw`. Without `mode` and `oldHeight` the engine fell back to the `spring` camera; `free`, `ta` and `spring` did not take over by name. Eye = `GetUnitViewPosition` + 0.85 x `GetUnitHeight`. The own unit is hidden (`SetUnitNoDraw`) and unselectable (`SetUnitNoSelect`; otherwise the screen ray answered with the own unit in many directions and a click selected it); the selection is cleared (`SelectUnitArray({})`) so the game draws no range rings.
- **Mouse and keys:** each frame the cursor is read (`GetMouseState`) and warped to the middle (`WarpMouse`); the way it moved is the turn (`SENS` 0.15 degrees per pixel, mouse up = look up, right = yaw down), the cursor is "none". `MousePress`, `MouseRelease` and `MouseWheel` return true while the view is on (the RTS does nothing), W A S D too. The buttons are read every frame as well (a lost release must not keep the unit firing). **Tab** (debug menu: free mouse, no look, no steering, no fire) is polled with `GetKeyState(9)`: as a commander the press never reached `KeyPress` (the game's own use came first). **Insert** or `/renegade` switches the view off and on; `/renegade log` writes the camera state, `/renegade flip` turns the yaw offset by 180 degrees.
- **Ray (`aim`):** `TraceScreenRay(middle, false, false, true)` gives `"unit", id` or `"ground", {x, y, z}` (the table also with `onlyCoords`). The engine answered "sky" for slopes of the heightmap (ground 337 to 560 Elmo away at pitch 3 degrees), so `march` follows the view ray over `GetGroundHeight` in steps of 24 Elmo (bisected at the hit, inside the map only); mountains outside the map have no heightmap and stay "sky". `R.hit` = unit or ground point, distance from the eye and from the unit (`udist`); `R.shot` = `R.hit`, or a point 3000 Elmo along the ray in the sky.
- **Crosshair and weapon rows (`reach`, `dropper`):** four lines; for every group of weapons (its first weapon) `reach` tells whether it is valid for what `R.hit` is (an aircraft: only anti-air weapons `renAA` and the hybrid ones `renHY`; anything else: not the anti-air-only ones) and compares the distance from the unit (`udist`) with its range: **green** up to 90% of the range, **yellow** up to 110% (`EDGE` 0.1), **red** beyond or when the weapon cannot hit this target. The crosshair has the best colour of all groups (green as soon as one valid weapon reaches the target), white for the sky; the rows of the panel get the colour of their own weapon as a tint (none for the sky, and none for an aircraft or a bomber: `dropper`). Text under the crosshair: "Pawn 100%  151 m" / "ground  84 m" / "sky" (the distance; no IN RANGE text any more). `R.best` and `R.states` hold the colours for the tests. Measured with `zz_ren33.lua` (Titan with ranges 465, 800, 860, an enemy walks up): distance 1819-1138 all red, 871 yellow (rows red, yellow, yellow), 742 green (red, yellow, green). The range rings are only drawn with `/renegade rings` or the debug button "Range rings: on/off" (third button above the panel, `R.btn3`; `R.rings`, off at the start).
- **Anti-air circle (`aaPick`):** shown when the unit has weapons in `renAA` or `renHY`: an orange circle of 15 % of the screen height (`AA_RADIUS`) round the crosshair. Of the visible enemy units (`GetVisibleUnits(ENEMY_UNITS)`) that fly (`canFly`), are in front of the camera and within the longest range of those weapons, the one whose picture (`WorldToScreenCoords`) is nearest to the middle inside the circle is the lock `R.aaTarget` (an orange square and "AA LOCK <name>"); with a lock the circle **glows** (bright yellow, 3.5 pixels, three wider translucent rings that pulse). The lock is the `unit` of the message.
- **Panel (`panel`):** right of the middle at the bottom (the game's buttons are left of it): the health bar (red to green, "HEALTH 370 / 370"), then one row per button group: description of its weapon ("x3" for several), tag LMB red / RMB yellow / MMB green, range (the longest of the group), reload time, READY / reloading and a bar in the color of the button (from `reloadFrame` and `reloadTime` of the first weapon; a `reloadFrame` of 500000 or more is the gadget holding a weapon that only aims: READY); an orange "AIR ONLY" under the tag for anti-air groups (they fire only at an aircraft in the circle) or "(aircraft in the circle: lock; ground: aim)" for those groups. The groups come from `renSlots` (cached by the three parameter texts: a Pawn and an anti-air turret both have "1;;").
- **Facing arrow (`facingArrow`):** a small thick green arrow on the ground in front of the unit (25 to 100 Elmo, black outline) in the direction the unit faces (`GetUnitDirection`): the way it walks or drives when W is pressed; a tank has to turn first when you look behind you.
- **Rings and barrel lines (`DrawWorld`, depth test off, thickest first):** for each group a ring (`gl.DrawGroundCircle`) of its range and a line on the ground from the unit in the direction its barrel points now (`GetUnitWeaponVectors` of the first weapon: straight up while it is not aiming, then the aim direction; a nearly vertical direction is replaced by the unit's facing; at most 260 Elmo): you look round faster than the turret turns, fire when the line points where you look. Left red 3 pixels, right yellow 5, middle green 7, so all show when they lie on each other. The lines were not seen on a picture yet.
- **Loss:** while `renRespawn` is in the future "YOU DIED" and "respawn in 5" ... "1" in big letters (`countdown`, also without the view); the view comes back by itself when the unit appears.
- **Debug menu (`lanrenedebug`):** above the panel two buttons: "Spawn enemy v" and "Debug unit: <name> v". A click (with the mouse free, Tab) opens the unit menu of the Level Editor (`Shared.newUnits` of `editor_common.lua`, loaded by `VFS.Include("luaui/Include/editor_common.lua")`): search field (`ownText`, `widget:TextInput`; Enter = done, Esc = clear, Tab leaves), rows faction (Armada, Cortex, Legion), group (Turrets, Bots, Vehicles, Hover, Air, Ships), tech level, the pictures of the units that have a weapon, the mouse wheel scrolls, no 3D preview. In the mode of "Debug unit" a click on a picture sends `ren|unit|<name>` and leaves the menu; in the mode of "Spawn enemy" (`R.pickMode = "enemy"`) it sends `ren|spawn|<name>` and the menu stays open.
- Test hooks: `WG.renegade` is the state table (`fake` = the test widget steers: yaw, pitch, keys, fire; `menu`, `list`, `pickMode`, `hit`, `shot`, `aaTarget`, `aaCircle`, `unit`).

## 5. The gadget (`renegade_game.lua`)

### 5.1 Units, moving, respawn, energy
- **Units:** from frame 30 to 300 every team with a human and a commander gets an `armpw` at the commander's place instead (`take`, `giveUnit`; fire state hold fire: the unit shoots only what the player aims at). `units[team]`, `kind[team]`, `input[team]`.
- **Moving:** `steer` gives `CMD.MOVE` to a point 200 Elmo ahead in the wished direction (forward `(sin yaw, cos yaw)`, right `(-cos yaw, sin yaw)`; again after 10 frames or when the direction turns by more than 6 degrees), `CMD.STOP` when no key is down. No `MoveCtrl`. W, A, S, D move the unit the right way (measured: 211 and 327 Elmo in about 4 s game time); pathfinding decides at cliffs, ships are not steered specially. **Aircraft** never land by themselves: `CMD.IDLEMODE` 0 (fly) from the first key on; they take off once (see the height below) and only Space and Ctrl change the height afterwards.
- **Impact preview (`impactPreview`, in `DrawWorld`):** for each button group whose first weapon is lobbed (type MissileLauncher, StarburstLauncher, ArtilleryShell, or a Cannon with `highTrajectory` >= 1 or range >= 800; not anti-air) the point under the crosshair (`R.hit`: ground or unit; nothing in the sky), shortened to the reach of the weapon, is drawn as a translucent disc of the explosion size (`damageAreaOfEffect`, at least 16) with a black-edged ring, a cross (no beam any more: it was in the way) and a thin line from the unit, all in the color of the button. **Bombs** (type `AircraftBomb`): the preview shows where a bomb dropped now would land: the position of the aircraft moved by its velocity (`GetUnitVelocity`) for the fall time over the ground height (gravity `Game.gravity` / 900 per frame, four passes), no aim point needed. The gadget sets the same point (`bombPoint`, refreshed every frame for aircraft) as the target of a bomb weapon instead of the crosshair point, so the bombs fall at once: measured with a Thunder at 426 Elmo height: the first bomb 4 frames after the press (`zz_ren18.lua`). Not measured with a picture yet; the scatter of the weapon is not drawn.
- **Aircraft and range colours:** a unit that flies (`canFly`: gunships, fighters, bombers; the range of a bomb is tiny, the impact preview shows where it lands) has no range colours: the crosshair stays green and the rows of the panel have no tint. Enemy aircraft out of the reach of the anti-air weapons are not shown at all (it would give away where aircraft fly).
- **Gunships:** the guns are fixed to the body, so the player has to fly so that the nose points at the target (the aircraft turns toward where it moves). The unit gets no move order from firing (a `faceTarget` that turned it with short move orders was taken out: it disturbed the flying). `SetUnitRotation` has no effect on aircraft (neither yaw nor pitch: the move type overwrites it every frame; measured), so the body cannot be tilted toward the view; see the steepness limit below.
- **Height of an aircraft (`lift` in the gadget, altimeter in the widget):** keys bit 16 (Space, polled with `GetKeyState(32)`) = higher, bit 32 (Ctrl, `GetModKeyState`) = lower; the message carries 0 to 63. **Landing:** with the lower key (Ctrl) held all the way down (`MIN_ALT` 4; the aircraft stops at about 12 Elmo) for `LAND_HOLD` 60 frames (2 s) it lands (`CMD.STOP` and idle mode 1; the height goes to 0 within a second); the next key other than Ctrl takes it off again (measured with `zz_ren28.lua`: from 426 down to 12 in about 6 s, landed at 0, W took it up to 430 and settled at 400). **Terrain following (`followGround` in the gadget):** the move type of an aircraft follows the ground only slowly, so every frame the height it should have is worked out (wished height `inp.alt` above the ground under it when going down; above the highest ground in the next second, 3 samples of 20 frames of its velocity, when going up) and its vertical speed is pushed toward it with `SetUnitVelocity` (at most `FOLLOW_MAX` 4 Elmo a frame, only in the needed direction; not while Space or Ctrl are held, not for 45 frames after letting them go, not on the ground; no climbing when it is already at its highest height over the ground). Measured with `zz_ren34.lua` (bomber armthund, W held, over a cliff from ground 4 to 202 and back on Hooked 1.1): after the take-off it stays at 393-408 above the ground, over the cliff it climbs ahead of it (peak 488, under the highest height 495) and is back at about 400 within 1-2 s, down the cliff it sinks (peak 467 over the lower ground, then 393-408). The vertical speed of a fixed-wing aircraft takes the push only partly (the engine sets it too), the result is as described.
- **Bombs are dropped by the gadget (`dropBombs`, `processBombs`):** the engine's bomb weapon fires only when the aircraft is low (measured with `zz_ren36.lua` / `zz_ren37.lua`, see below), so a button press drops the salvo itself: `salvoSize` x `projectiles` bombs, `salvoDelay` apart (Tsunami: 5 bombs, 5 frames apart, reload 7 s), each with `Spring.SpawnProjectile(weaponDef, { pos = unit position - 8 in height, speed = the unit's velocity, owner, team, ttl = 1200, gravity = -myGravity })` (without `gravity` the bombs fly straight on, measured; `myGravity` of the Tsunami's bomb is 0.4, not the map gravity 0.133; the five bombs of `zz_ren38.lua` all fall and explode after about 50 frames, at the predicted place within about 10 Elmo). The reload is set with `SetUnitWeaponState(reloadFrame)` (the panel shows it), a button that stays down drops the next salvo as soon as it is ready, the weapon gets no target (so the engine's own release stays quiet). The preview in the widget uses the same `myGravity`. At any height one click is enough. Earlier finding (the reason): (measured with `zz_ren36.lua`, Tsunami armsb, weapon `armsb_arm_seaadvbomb`: AircraftBomb, range 1280, onlyForward, maxAngleDif -1):** with the left button held at 340-550 above the ground the weapon does not fire (40 frames); it fires only when the aircraft has sunk to about 110-150 above the ground (frame 650 at height 106 in one run, frame 629 at about 150 in another); the same with the trigger target directly under the aircraft instead of the landing point (`bombPoint`), so it is not the position of the target. Not known why (the engine's bomb dropper); to decide: a hint on the crosshair (too high to bomb) or release the bombs by hand with `Spring.SpawnProjectile` (position, the unit's velocity, owner; reload, salvo and the reload bar to be done by the gadget).
- **Pictures of the weapons (panel):** the categories of `renegade-weapon-categories.md` (made by `test-data/tools/weapon_categories.py`) get a picture each: `LevelEditor/game-modes/weapon-images/weapon_<category>.png` (the picture of a whole panel row, 6 : 1, 768 x 128 is what `weapon_art.py` writes: the weapon and its beam over the whole width on a dark background; drawn by `test-data/tools/weapon_art.py` with Pillow and numpy, or delivered from outside: any png with that name). All 39 categories have a picture: the lasers and the heat ray (below) and, drawn by `test-data/tools/weapon_art2.py` (a launcher or gun with its projectile far to the right, the trail runs from the muzzle: the same position in every picture so that the rows of the panel read as one column), `cannon-*` (a shell with muzzle flash and smoke), `missile-*` (a white rocket with red nose and fins, a single tube), `heavy-rocket` (starburst: a rocket and its burst of bomblets), `rocket-salvo` (a round rocket pod with 19 openings, seven small rockets), `plasma-*` (a violet ball with a trail of smaller balls) and `torpedo` (in water, bubbles only behind it); the sizes light, medium, heavy and ultra. The beam weapons: `laser-heavy` (green beam), `laser-medium` (blue), `laser-light` (red), `laser-ultra` (the heaviest: blue, a very thick beam; tachyon weapons, "ultra" in the description or 2500 damage and more: the Pulsar, the Bulwark's tachyon accelerator; 14 weapons) and `heatray` (yellow, thick; "heat ray" in the description: the Juggernaut, the Adjudicator, Thermite, Armageddon; 27 weapons; EMP beams are `stun-beam`). Measured: the Pulsar shows `1=laser-ultra`, the Juggernaut `2=heatray` (`zz_ren44.lua`); `weapon_art.py` draws the cannon once (`gun_body`, a 2D drawing with shading, not a 3D model; its body is kept as the bodies of the weapons (the cannon, the launchers, the rocket pod) are not kept as files: `weapon_art_build.py` draws them from the code in 2 seconds each) and makes the sizes with `beam_fx` (colour, thickness of the beam) and a different part of the picture in the row (`SIZES`: the lighter the weapon, the smaller it is in the row). Measured with the Bulwark (cordoom: `renPics 1=laser-heavy,2=laser-medium,3=laser-light`, rows red, blue, green). **Categories and sizes** (`weapon_categories.py`, `renegade-weapon-categories.md` has the rules and the limits): the size of laser, plasma, cannon, missile and machine-gun weapons (light, medium, heavy, ultra) comes from the tech level of the unit (`renegade_unit_tech.csv`: code and tech level, read from the game by `zz_tech.lua`: T1 light, T2 medium, T3+ heavy), one step down for a weak and up for a strong weapon, ultra above the last limit (`renegade_weapon_limits.csv`, columns Weak up to, Normal up to, Strong up to; above Strong up to is ultra; in damage per second = damage of one shot / reload: up to Weak a size less than the tech level gives, up to Normal that size, up to Strong a size more; start values (found without the commanders of all levels and the Epic Commander, whose DPS is far above everything: they stay in the table and are ultra by their DPS, but they do not set the limits; laser without them: light towers (Guard, Sentry, Exploiter) 150 DPS, T2 units 250 to 500, Titan 800, Overlord 1071, Epic Bulwark 1235, Thor 1500, Epic Pulsar 3200) laser 100/600/1500, plasma 60/400/1500, cannon 60/250/550, missile 40/150/800, machine-gun 20/80/empty = no ultra; the commander lasers from level 4 or 5 up are above 1500 and so ultra; the cannon limits keep a factor of more than two between strong and ultra (there are only 52 cannon weapons; by DPS: 666 the Cortex Commander level 10 (two weapons), 600 Perdition: these three are ultra; 350 Sol Invictus, 300 Shiva, 257 Tzar, 250 Sharpshooter are heavy; 24 light, 16 medium, 8 heavy, 3 ultra); the Mine Detonator of the Martyr counts as self-destruct; the lasers also by words: tachyon, ion accelerator, "ultra"). **Every category has a picture now** (39 of 39, with `anti-nuke`; one picture each for the six that are drawn last, none of them needs sizes: the weapons of a category are alike). Drawn by `test-data/tools/weapon_art3.py`: `railgun` (a hair-thin white-hot slug with a glowing streak and chevron shock waves), `flamethrower` (a stream of fire widening from the muzzle), `depth-charge` (a barrel sinking in blue water, bubbles), `aa-missile` (a slim missile with a smoke trail in the sky and a jet in front of it), `bomb` (an aircraft wing with three bombs falling away) and `nuclear` (a big missile with a flame and a mushroom cloud); an empty Picture cell in `renegade-weapon-categories.md` would mark a category without a picture. Drawn by `test-data/tools/weapon_art3.py` (same style, same far-right place of the effect; ART_ONLY=name draws only some): `d-gun` (a huge fire ball with a trail of fire; the Disintegrator of the commanders), `stun-beam` (a thin cyan beam with pulse rings), `flak` (muzzle flash, shells, three air bursts), `lightning` (a branching violet bolt), `machine-gun-light/medium/heavy` (muzzle flash and tracers in one, two, three lines), `gauss` (a glowing slug with shock rings), `artillery` (the dotted arc of the shell and the explosion where it lands), `shotgun` (a spray of pellets), `emp-grenade` (a grenade with blue arcs and a pulse ring), `self-destruct` (a bomb with a burning fuse and an explosion). Only one picture each for the families without sizes; the machine gun has three sizes like the table; not looked at in the game yet (only pictures; loading was measured with the other pictures). Measured with `zz_ren45.lua`: Ambassador `heavy-rocket`, Rocko `missile-light`, Stumpy `plasma-light`, Bulldog `plasma-medium`, Buzzsaw `plasma-ultra`; the picture of the Ambassador is shown in its row. `update_renegade_weapons.bat` makes the categories first, then the gadget block. **Muzzle and nuclear missile:** the guns with a muzzle flash (cannon, artillery, flak, machine gun, shotgun) have an orange glow in the opening of the muzzle like the d-gun (a dark muzzle looked cut off); the nuclear missile is drawn in the middle of the picture, all white with a yellow and black radiation sign, a yellow ring and dark fins (`nuke_missile`, `trefoil` in `weapon_art3.py`). **Which weapon is shown:** the column Fire button of `renegade_weapons.csv` is the flag: a weapon with a button (LMB, RMB, MMB) is a row of the panel and is fired; an empty cell means the weapon is not shown and not fired by the player (helper and dummy weapons of the engine such as the smart-trajectory dummy of the Amputator, the crawling bomb dummy, footsteps; weapons with 0 damage; the anti-nuke launchers, which fire by themselves; the stomp of the Juggernaut). The start value comes from `usable()` in `renegade_weapons.py` (range above 0, not a shield, not an interceptor, damage above 2 against default or aircraft armour); change the cell in Excel to show a weapon. On the page `renegade-weapons.md` the Picture cell of such a weapon says `not shown`. **Anti-nuke** (`anti-nuke`: description with ICBM and intercept: 12 launchers of the Citadel, Haven, Umbrella, Oasis, Prevailer, Saviour, Aegis, Hecate, Hera, Rampart): a slim interceptor missile and an incoming white nuclear warhead hit in an explosion; the weapon has no button (it fires by itself). **The panel shows it as a row with the tag `AUTO`** (grey, the picture, the name, `range N   fires by itself`, or `range: the whole map` from 20000; no cooldown, no reaction to a button): the gadget publishes the weapons with the interceptor flag as the rules parameter `renAuto` (`<weapon number>,...`, in `renegade_game.lua` next to `renPics`), the widget adds one row per weapon definition after the rows of the buttons. Measured (`zz_ren46.lua`): Citadel, Haven (carrier), Prevailer, Hera and Umbrella have `renAuto=1` and `renPics 1=anti-nuke`; the Ambassador has none; the picture of the Citadel shows the row `ICBM intercepting missile launcher ... Down: `SetUnitVelocity` pushes the unit down (`DOWN_SPEED` 2.3 Elmo a frame) because the move type sinks slowly; a landed aircraft takes off with the first key; on letting go the wished height becomes the real one and the vertical speed is taken away for 45 frames. Not built: an attack order on the aim point while firing (the engine would tilt, but also fly the unit) or a MoveCtrl flight model (the rotation can be held, see below).

So the guns of the gunship look where the player looks (in the yaw; the pitch is the steepness limit below), and it flies in every direction. Other units: a tank or bot already turns only its chassis with the movement while the turret follows the view; a ground unit with fixed guns was not looked at.

### 5.2 Shooting and the three buttons (`shoot`)
Like in a shooter, never a "target". While a button is down every weapon of its group gets the point the player aims at (`Spring.SetUnitTarget(unit, x, y, z, false, true, weaponNumber)`, a user target), shortened along the line from the unit to the point to the reach of that weapon (`shortened`), so it fires toward the crosshair where nothing is in reach, into the sky, at far mountains. An enemy unit under the crosshair is not chosen as a target (the earlier unit target made the weapon wait; the point does not); only the anti-air lock is (5.3). The target is set at once when the message arrives (`RecvLuaMsg` calls `shoot` with force) and renewed every 3 frames. **The turret follows the view ("aim only"):** every weapon of the three buttons that is not pressed (not anti-air, not stockpile) gets the point the player looks at as its target (shortened to its reach; `aimable`, `inp.aimed` from the first message) so the turret turns with the mouse, and its reload is held: once it is ready its `reloadFrame` is set to `BLOCK` = 1000000, so it aims but does not fire (a weapon that is reloading is left alone and blocked when ready). Pressing the button sets `reloadFrame` to now (`unblock`), the weapon fires as soon as it is aimed. Measured with `zz_ren15.lua` (Pawn): the barrel direction (`GetUnitWeaponVectors`) followed yaw 180, 90, 180 without a button and `reloadFrame` stayed 1000000 (no shot); a click: the weapon fired 2 frames after the press (the turret was aimed already), then it was held again. **One click is one shot:** a weapon keeps its target while its button is down (continuous fire, as fast as it reloads); when the button goes up before the weapon has fired (the turret was still turning, the weapon was reloading) the target stays until the weapon has fired (its `reloadFrame` changed) or its time is up (45 frames plus the reload time, at most 8 s; `inp.hold` per weapon in `shoot`), then it is cleared; a weapon that has fired is let go at once. A target set for one weapon number stays after `SetUnitTarget(unit, nil)`, so clearing is a stop order (`clearTargets`), which also stops a walking or flying unit; therefore it is given only while the turret does not yet follow the view (`inp.aimed` false). From the first message on the weapons that are not pressed get the view point as target and a held reload (aim only), so nothing keeps firing and there is no stop order (no stutter); the weapons still held get their targets again after a clear. Measured with `zz_ren14.lua` (a click of 3 frames, the aim far behind the facing; the deadline is now 150 frames plus the reload time, at most 390): Pawn: the target was still set 10 frames later, the weapon had fired by 90 frames and the target was cleared; Titan laser: fired, cleared; held buttons: the reload frame advances several times (continuous fire). Before this a short click cleared the target before the turret had turned and nothing was fired. Measured (Titan, Epoch, Karganeth): each button targets only its group; after the release no weapon has a target and no reload frame changes; the weapon has its target 4 to 7 frames after the click (turret and reload are the engine's); Peewee against Peewee at 150 Elmo: 370 -> 118 health in 4 s. Every weapon can fire at a point in the air (Total Annihilation style, a hit is luck): a Pawn fired at a point 99 Elmo up, the weapon had its target and reloaded.

**Which weapon on which button (`slotsFor`, per unit definition, cached):**
- The table: the block `WEAPON_BUTTONS` (between `-- BEGIN WEAPONS` and `-- END WEAPONS`; made by `renegade_weapons.py` from the columns Group and Fire button of `renegade_weapons.csv`) lists for a unit code the weapon numbers of `L`, `R`, `M`; a Scavenger copy uses the entry of the normal unit. 497 units, 1035 weapons.
- Without an entry the rule (the python proposal is the same): weapons with the same weapon definition are one group (they fire together); dummies (no damage: footsteps, `krogweaponaim`), shields and interceptors are no weapons. Missiles (`MissileLauncher`, `StarburstLauncher`, `TorpedoLauncher`) and anti-air weapons count as missiles, all others as "others"; both are sorted by range. With both kinds: the shortest of the others on the left button, the rest of the others on the right (the missiles take the right button when there is no second one), the missiles in the middle. With one kind only: the shortest left, the next right, all further ones in the middle. Census of the units with a weapon (Scavenger and Raptor copies left out; `lanrenotest` logs it): 18 units without a usable weapon, 320 with one button, 84 with two, 124 with three: three buttons do for every unit. Titan: impulsion blaster left, long-range laser right, starburst rocket middle; Epoch: medium plasma (3 guns) left, heavy plasma (2) right, Ferret missiles (anti-air) middle; Thor: 2 EMP beams left, lightning right, EMP missile middle.
- **The D-gun** (weapon type `DGun`, the commanders' Disintegrator) is the exception: always on the right button; the shortest of the other groups is then on the left, everything else in the middle (Commander: laser left, Disintegrator right, the underwater laser / torpedo / anti-air missile in the middle). A manual fire weapon: it gets its target with the dgun flag (`SetUnitTarget(unit, x, y, z, true, true, weapon)`) and no aim-only target before the button. Measured with `zz_ren16.lua` (Armada Commander, an enemy Pawn 150 Elmo ahead): right button: the D-gun fired 4 frames after the press and the Pawn was gone; left button: the laser fired. The same rule is in `renegade_weapons.py` (`propose`): a unit with a D-gun always gets the rule, entries of the csv for such units are replaced when the table is made new.
- The main weapon is no longer a concept (an earlier version had "left = the strongest, right = all others").

### 5.3 Anti-air and weapons that also hit aircraft
- `aa`: default damage <= 2 and more damage against vtol (flak, anti-air missiles), or a description with only air tokens (g2a / a2a / s2a and no x2g / x2s: the Demon's and Kagan's shoulder rockets have ground damage but are air only). `hy`: damage against the ground and against vtol and a description with "g2a" or "a2a" (the Titan's laser and starburst: "g2g/g2a"). Both are published per unit (`renAA`, `renHY`).
- With a lock (the `unit` of the message is an enemy): `aa` weapons get it as their target (`SetUnitTarget(unit, enemy, false, true, weaponNumber)`; homing missiles), `hy` weapons only when it flies (`canFly`), otherwise the point as every weapon; `aa` weapons without a lock do not fire. When the engine refuses the unit for a weapon (the Titan starburst: `SetUnitTarget` returns false) the point where the aircraft is becomes the target. Measured: anti-air turret `armrl` against a hovering Brawler 250 Elmo ahead and 100 up: crosshair 3 degrees beside it -> lock, weapon target type 1, the Brawler lost health (1780 -> 1665 in 1.3 s), looking away: no lock, no fire; Titan laser (right button): lock, target type 1, the Brawler destroyed.

### 5.4 Debug messages (only with `lanrenedebug`)
- `ren|unit|<name>` (`turnInto`): every unit with a weapon (aircraft, turrets that stand still and shoot, ships: they lie on the land and fire) is made at the place and facing of the old one with the same share of health, the old one is removed without wreck (`units[team]` is the new one first: no respawn); groups and parameters are worked out again.
- `ren|spawn|<name>`: the unit for the first team not allied to the player, 1000 Elmo ahead of the player's view (yaw of the last message), a ground unit on the ground, an aircraft 200 Elmo above, `CMD.FIGHT` toward the player.

## 6. The weapon table (`game-modes/renegade_weapons.csv`, `renegade-weapons.md`)

- **The csv is the source** (semicolons, UTF-8 with BOM, open it in Excel and import it with "Semicolon" only as the separator, no "Space", text columns as text: "-" becomes a number otherwise): the columns Faction, Unit, Code, #, Weapon (description), Type, Target, Range, Reload, Damage, Weapon name, **Fire button**, **Weapon image**. Fire button = LMB, RMB, MMB or empty (weapons of a unit with the same button fire together and make one row of the panel; an old "-" or "-0" counts as empty); Weapon image = empty for now (a picture of the weapon for the panel, for when the interface is made nicer; not read by the game). Target = what the weapon hits (empty = nothing; **no cell of a csv holds "-" for "empty"**: a spreadsheet takes it for a formula or a number, an empty cell stays empty): the tokens of the description (g2g, g2a, a2g, g2s ...) count first, the damage against aircraft alone does not (many ground missiles have the same damage against every armor class: Janus, Ambassador), without tokens the damage and the type.
- `game-modes/update_renegade_weapons.bat` (`renegade_weapons.py update`) writes the table into the md **only between the comment lines `BEGIN TABLE` and `END TABLE`** (the text around may be edited; a file without the markers is made whole once) and the block `WEAPON_BUTTONS` into the gadget. `renegade_weapons.py table <infolog>` makes the csv new from the dump of `zz_weapondump.lua` (`[zzwep]` lines; the Fire button and Weapon image of rows that are in the csv are kept, new rows get the proposal); `renegade_weapons.py lua` writes only the block.

## 8. Not done and open
